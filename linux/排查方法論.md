## 一、兩條核心原則

### 原則一：先驗證「它該在那裡」，而不是先找「它跑去哪」

找不到東西時，本能是加大搜尋力度。但**多數情況下錯的是預期，不是系統**。

驗證方法是**找對照組**——同類東西裡挑兩三個你確定正常的，看它們有沒有：

```bash
for m in usbcore nvidia bridge nvidia_drm; do
  printf "%-12s " "$m"
  [ -d /sys/module/$m/parameters ] && echo "有" || echo "無"
done
```
```
usbcore      有
nvidia       無
bridge       無          ← 最普通的 in-tree 模組也沒有
nvidia_drm   有
```

**只看 nvidia，結論是「nvidia 很怪」；加上對照組，結論變成「這目錄本來就是條件性存在的」。**

問題於是從「nvidia 壞了」（不可查證，且會導向亂修）重新框定為「這目錄的建立條件是什麼」（可查證）。**找對照組成本極低、收益極高，是投報率最高的一步。**

### 原則二：不要問「它在哪」，要問「誰負責把它放在那裡」

`parameters/` 不是 nvidia 建的，是**核心的 `module_param()` 巨集在載入模組時建的**：

```c
module_param(foo, int, 0444);   // 第三個參數是 sysfs 權限 → 建立節點
module_param(bar, int, 0);      // 權限 0 → 不建立，/sys 裡完全看不到
```

一旦問題變成「誰建立、依什麼條件」，答案自己就浮現了，而且**一次解釋所有模組的行為，不只眼前這一個**。

這個轉換的適用範圍遠超模組：

| 現象 | 別問 | 要問 |
|---|---|---|
| log 不見了 | log 在哪 | 誰寫的？journald / 程式自己 / logrotate 搬走了？ |
| 設定沒生效 | 設定檔在哪 | 誰讀的？什麼時候讀？讀完後有沒有被覆蓋？ |
| 指令找不到 | 執行檔在哪 | `PATH` 誰設的？哪個 shell 啟動檔？ |

## 二、技巧速查表

| 情境 | 技巧 | 侷限 |
|------|------|------|
| 東西**已存在**，只是不知在哪 | `find` 掃命名空間 | 找不到執行時才建立的 |
| 想知道程式**將會**去哪找 | `strings` 二進位檔 | 拼接出的路徑不會有完整字串 |
| 想知道程式**實際**做了什麼 | `strace -e trace=file` | 只能用於使用者空間 |
| 東西由套件提供 | `dpkg -L` / `dpkg -S` | 不含執行時生成的檔案 |
| 程式正在跑，想知道它開著什麼 | `lsof -p <pid>` | 只看得到當下開啟的 |

## 三、技巧 1：find 掃命名空間

最笨但最有效：**拿關鍵字掃整個相關命名空間**。

```bash
find /proc /sys -maxdepth 4 -name '*nvidia*' 2>/dev/null
find /etc /usr/share /var/lib -maxdepth 4 -iname '*關鍵字*' 2>/dev/null
```

實測第一行就是答案：

```
/proc/driver/nvidia          ← 完全不需要事先知道 NVIDIA 有 proc 介面
/proc/driver/nvidia-uvm
/sys/module/nvidia
/sys/bus/pci/drivers/nvidia
...
```

往下鑽即得 `/proc/driver/nvidia/params`。

**兩個必要細節：**

- **`-maxdepth` 必加**——`/proc` 有上千個 PID 目錄、`/sys` 有 symlink 迴圈，不限深度會跑到天荒地老
- **`2>/dev/null`**——濾掉權限雜訊，否則錯誤訊息會淹沒結果

## 三之二、掃出一堆結果後：三層篩法

`find` 給 23 條結果，怎麼收斂到 1 條？由粗到細三層。

| 層 | 手段 | 效果 | 何時用 |
|---|---|---|---|
| 1. 型別 | `find ... -type d` / `-type f` | 23 → 14 | 永遠先做，零成本 |
| 2. 路徑語義 | 判斷「誰建立這個命名空間」 | 14 → 1 個首選 | 不必跑命令，靠理解 |
| 3. 內容反查 | `grep -rl '<已知關鍵字>' <限定子樹>` | 直接命中 | **有已知關鍵字時優先用** |

### 第 1 層：型別篩掉一半

**symlink 是交叉引用，不是內容本身**——`holders/`、`drivers/`、`slab/` 都只是指回別處的指標：

```bash
find /proc /sys -maxdepth 4 -name '*nvidia*' -type d 2>/dev/null    # 23 → 14
```

想先看每條是什麼型別，再決定怎麼篩：

```bash
find /proc /sys -maxdepth 4 -name '*nvidia*' 2>/dev/null | \
  while read p; do printf "%-12s %s\n" "$(stat -c '%F' "$p" 2>/dev/null)" "$p"; done
```

### 第 2 層：靠路徑語義判斷「誰建的」

這層不用跑命令，靠的是知道**每個命名空間由誰負責、因此裡面會有什麼**：

| 路徑 | 誰建立 | 內容性質 | 可能有廠商自訂資料嗎 |
|---|---|---|---|
| `/sys/module/<m>/` | **核心自動生成** | 固定 schema：`refcnt`、`sections`、`taint`… | 只有 `parameters/`，且受權限限制 |
| `/proc/driver/<name>/` | **驅動自己呼叫 `proc_mkdir` 建的** | **任意**——廠商想放什麼放什麼 | ✅ **最可能** |
| `/sys/bus/pci/drivers/<d>/` | 核心驅動模型 | `bind`/`unbind`/裝置連結 | ✗ 是綁定介面 |
| `/proc/irq/<n>/` | 核心中斷子系統 | 中斷親和性 | ✗ 無關 |
| `/sys/fs/cgroup/…` | systemd | 資源控制 | ✗ 無關 |
| `/sys/kernel/slab/` | 記憶體配置器 | 配置統計 | ✗ 無關 |

**關鍵推理：核心生成的命名空間 schema 固定，廠商塞不進東西；驅動自建的目錄則完全自由。**
要找「廠商自訂的東西」，就去廠商能自由發揮的地方 → `/proc/driver/nvidia/` 立刻成為第一順位。

> 這就是**原則二**在實戰中的樣子：**問「誰負責建立」，答案自動幫你排序了候選清單。**

### 第 3 層：不猜路徑，直接按內容搜

前兩層仍帶推理成分。**最確定的一招是繞過路徑，用「你知道會出現的內容」去搜。**

```bash
$ grep -ril 'modifydevice' /proc/driver --exclude-dir=gpus
/proc/driver/nvidia/params
```

**通則：**

> 找不到檔案位置時，先問「**這個檔案裡一定會有什麼字串？**」
> 設定檔有選項名、log 有時間戳或錯誤碼、快取有你查過的值。
> 拿那個字串去 grep 限定的子樹，比猜路徑可靠得多。

但這招有兩個必須知道的坑，兩個都是實際踩到的。

### 坑一：同一個東西在不同介面叫不同名字 ← 最容易白忙

**直覺做法是拿 `modinfo -p` 給的參數名去搜，結果是搜不到任何東西：**

```bash
$ modinfo -p nvidia | grep -i modifydevice
NVreg_ModifyDeviceFiles: (int)              # ← modinfo 說它叫這個

$ grep -i modifydevice /proc/driver/nvidia/params
ModifyDeviceFiles: 1                        # ← proc 裡卻沒有 NVreg_ 前綴

$ grep -rl 'NVreg_ModifyDeviceFiles' /proc/driver
                                            # ← 無結果
```

不是偶發，是系統性的：

```bash
$ modinfo -p nvidia | grep -c '^NVreg_'          # 45
$ grep -c '^NVreg_' /proc/driver/nvidia/params   # 0
```

**原因：** 驅動用 `module_param_named(NVreg_Foo, Foo, ...)` 註冊——
modprobe 選項名是 `NVreg_Foo`，驅動內部變數是 `Foo`，proc 介面印的是後者。

**對策：搜「片段」，不要搜完整名稱，並加 `-i` 忽略大小寫。**

```bash
grep -ril 'modifydevice' /proc/driver --exclude-dir=gpus     # ✓
```

> 這跟[技巧 2 的坑二](#坑二找片段不要找完整路徑)是**同一個道理**：
> 完整字串常因前綴、拼接、大小寫而對不上。**關鍵字砍短，命中率大增。**

### 坑二：`/proc`、`/sys` 裡有「硬體背書」的偽檔案

不只是「別掃 `/proc` 根目錄」那麼簡單。先講根目錄的兩顆明雷：

```
128T  /proc/kcore      ← 代表全部實體記憶體的稀疏偽檔案
-r--  /proc/kmsg       ← 讀取永久阻塞，等待新核心訊息
```

**但子樹裡也有暗雷。** 本機實測，`/proc/driver` 只有 22 個檔案，其中一個是：

```
/proc/driver/nvidia/gpus/0000:01:00.0/information
```

| 讀取時的 dGPU 狀態 | 耗時 |
|---|---|
| 已喚醒 | **0.002 秒** |
| runtime suspend（省電休眠） | **1.8 秒**——讀取動作觸發喚醒 |
| 更深的省電狀態 | 實測曾 **超過 120 秒** |

Optimus 雙顯卡筆電的獨顯平常會 runtime suspend，**`grep -r` 掃過 `gpus/` 就等於強迫喚醒顯卡**。

> **通則：`/proc` 和 `/sys` 裡有些偽檔案是「硬體背書」的——讀取會觸發真實硬體動作**
> （喚醒裝置、查詢韌體、輪詢感測器）。它們不會永久阻塞，但可能慢到像當機，
> 而且**耗時取決於當下電源狀態，無法穩定重現**——這讓它特別難診斷。

**對策：**

```bash
# 1. 排除硬體相關子目錄
grep -ril 'kw' /proc/driver --exclude-dir=gpus

# 2. 不確定時加 timeout 保險，一次一檔
find <子樹> -type f 2>/dev/null -exec timeout 1 grep -l '<kw>' {} + 2>/dev/null

# 3. 事後找出是誰卡住的
find <子樹> -type f 2>/dev/null | while read f; do
  timeout 1 cat "$f" >/dev/null 2>&1; [ $? -eq 124 ] && echo "阻塞: $f"
done
```

**第 2 層與第 3 層互補：推理決定 grep 哪個子樹（順便避開地雷），內容搜尋決定答案。**

## 四、技巧 2：strings 挖硬編碼路徑

`find` 只能找**已存在**的東西。若路徑是執行時才建立，或你想知道程式**將會**去讀哪裡，就問二進位檔本身——**路徑字串幾乎一定硬編碼在裡面**。

```bash
zstdcat "$(modinfo -n nvidia)" | strings | grep -oE '/(proc|sys)/[a-zA-Z0-9_/-]+' | sort -u
strings $(which foo) | grep -E '^/|\.conf|\.d/'      # 一般執行檔
```

### 坑一：壓縮 = 假陰性

```bash
$ strings /lib/modules/.../nvidia.ko.zst | grep -c '/proc/driver'
0                                    # ← 不是沒有，是根本沒解壓
```

`.ko.zst`、`.gz`、`.xz`、`.jar`、UPX 殼都一樣。**搜不到時先 `file <檔案>` 確認是不是壓縮的。**

### 坑二：找片段，不要找完整路徑

解壓後 grep `/proc/driver` 仍是 0 筆。改找片段才有：

```bash
$ zstdcat "$(modinfo -n nvidia)" | strings | grep -oE '[a-z/]*driver/nvidia[a-z/-]*' | sort -u
driver/nvidia                        ← 沒有 /proc/ 前綴！
driver/nvidia-caps
/driver/nvidia/capabilities/
```

原因：核心 API `proc_mkdir("driver/nvidia", NULL)` 收的是**相對於 `/proc` 的路徑**，`/proc/` 前綴從未出現在檔案中。

**通則：路徑常在執行時被組合（拼接、`sprintf`、變數展開），完整字串根本不存在。找不到就把關鍵字砍短再試。**

### 附帶收穫：符號名稱本身就是文件

```bash
$ zstdcat "$(modinfo -n nvidia)" | strings | grep -E '^proc_(mkdir|create)' | sort -u
proc_create_data
proc_mkdir_mode
```

看到這兩個符號，就知道機制是「模組主動呼叫 proc API 建目錄」，不是核心自動生成的——**直接回答了原則二的「誰負責建立」**。

## 五、技巧 3：strace 看實際行為

**對一般程式（非核心模組），這是最強的一招。** 不用猜設定檔在哪，讓程式自己說：

```bash
strace -e trace=file <命令> 2>&1 | grep ENOENT
```

實測 `git config --list`：

```
access("/etc/gitconfig", R_OK)               = -1 ENOENT    ← 系統層
access("/home/set/.config/git/config", R_OK) = -1 ENOENT    ← XDG 層
access("/home/set/.gitconfig", R_OK)         = 0            ← 命中
openat(AT_FDCWD, "/home/set/.gitconfig", O_RDONLY) = 3
```

**`ENOENT`（Error NO ENTry，POSIX 系統呼叫的標準錯誤碼，意指「找不到該檔案或目錄」）那些行才是重點——它們是「程式找過但沒找到」的完整清單，等於搜尋順序與優先級。**
要新增設定檔時照這清單挑位置，保證被讀到；要覆蓋既有設定時，挑排在前面的位置。

### 坑：不要只抓 openat

```bash
strace -e trace=openat git config --list    # ← 什麼都抓不到！
```

git 用 `access()` 先探測再開檔。**一律用 `trace=file`**，它涵蓋 `openat`/`access`/`stat`/`newfstatat` 全部檔案相關呼叫。

### 其他常用開關

```bash
strace -f ...                    # 跟進子程序（多程序程式必加）
strace -e trace=network ...      # 只看網路，查連不上哪個位址
strace -p <pid>                  # 附加到執行中的程序
strace -o out.txt ...            # 輸出到檔案（stderr 量大時）
```

**侷限：核心模組沒有系統呼叫可攔，用不了 strace**——那種情況回到技巧 1、2。

## 六、技巧 4：問套件管理員

```bash
dpkg -L <套件>          # 正查：這套件裝了哪些檔案
dpkg -S <檔案路徑>       # 反查：這檔案屬於哪個套件
dpkg -L <套件> | grep -E '\.conf|/etc/|\.service'    # 只看設定檔
```

實測：

```bash
$ dpkg -S /usr/bin/nvidia-smi
nvidia-utils-580: /usr/bin/nvidia-smi
```

**反查特別有用**：找到一個檔案後想知道來龍去脈，先查屬於哪個套件，再 `dpkg -L` 看同套件還裝了什麼——設定檔、文件、systemd unit 通常都在旁邊。

**侷限：只涵蓋套件登記過的檔案。** 執行時生成的（`depmod` 索引、快取、log）查不到——參見 [核心模組檢查.md](./核心模組檢查.md) 第十節的孤兒目錄，正是「dpkg 不認得所以刪不掉」的實例。

## 七、技巧 5：lsof 看執行中程序

適合「服務正在跑，但不知道它讀的是哪個設定檔」。

```bash
sudo lsof -p <pid>              # 該程序開著的所有檔案
sudo lsof -c nginx              # 依程序名
sudo lsof <檔案>                 # 反查：誰開著這個檔案（查 umount 失敗）
```

**坑：`pgrep <name>` 對超過 15 字元的程序名會失效**（核心 comm 欄位上限），要用 `pgrep -f` 比對完整命令列：

```bash
$ pgrep -n nvidia-persistenced
pgrep: pattern that searches for process name longer than 15 characters will result in zero matches
$ pgrep -f nvidia-persistenced       # ← 正確用法
```

## 八、完整決策流程

```
找不到預期的東西
   │
   ├─0. 找 2-3 個同類對照組 ─── 也沒有？ → 前提錯了，改查「建立條件」
   │                                       多數在此結案
   │                                       （查條件：man / 原始碼 / 符號名稱）
   ├─1. find 掃命名空間（-maxdepth 必加，2>/dev/null）
   │      └─ 結果太多 → 三層篩法：
   │           1) -type d/f 濾掉 symlink
   │           2) 路徑語義判斷「誰建的」→ 決定 grep 哪個子樹
   │           3) grep -rl '<已知關鍵字>' <子樹>  ← 有關鍵字時直接跳這層
   │
   ├─2. 還是沒有 → 它可能執行時才生成
   │      ├─ 使用者空間程式 → strace -e trace=file，看 ENOENT 清單
   │      └─ 核心模組       → strings 二進位檔（先解壓、找片段）
   │
   ├─3. 想知道來源脈絡 → dpkg -S 反查套件 → dpkg -L 看同套件其他檔案
   │
   └─4. 程式正在跑 → lsof -p 看它實際開著什麼
```

**貫穿全程的一句話：**

> 不要停在「找不到」，要推進到「為什麼不在那裡」。
> 前者是死路；後者總能導向一個可查證的機制問題——而機制問題的答案，
> 通常能一次解釋一整類現象，不只眼前這一個。

## 九、附錄：本篇的完整實例

**問題：** `/sys/module/nvidia/parameters/` 不存在，但 `modinfo -p nvidia` 明明列出 48 個參數。

| 步驟 | 動作 | 結果 |
|---|---|---|
| 0 | 對照 `usbcore`/`bridge`/`nvidia_drm` | `bridge` 也沒有 → **前提錯誤，非 nvidia 專屬問題** |
| 0' | 查建立條件 | `module_param()` 第三個參數為 `0` 就不建節點 |
| 1 | `find /proc /sys -maxdepth 4 -name '*nvidia*'` | 23 條結果，需收斂 |
| 1a | 加 `-type d` 濾掉 symlink | 23 → 14 |
| 1b | 路徑語義：`/proc/driver/<name>/` 是驅動自建、內容任意 | 鎖定 `/proc/driver/nvidia` |
| 1c | `ls /proc/driver/nvidia/` | **`params` ← 答案** |
| 1' | 或直接 `grep -ril 'modifydevice' /proc/driver --exclude-dir=gpus` | **一步命中，免推理** |
| 2 | `strings` 驗證機制 | 找到 `driver/nvidia` + `proc_mkdir_mode` |

**結論：** NVIDIA 的 48 個 `NVreg_*` 參數全部用權限 `0` 宣告，故 `/sys` 無節點；
NVIDIA 改為自建 proc 介面暴露這些值：

```bash
cat /proc/driver/nvidia/params      # 42 行，免 sudo
```

四支 nvidia 模組的實況對照：

| 模組 | `/sys/module/<m>/parameters/` |
|---|---|
| `nvidia` | **無**（48 個參數全宣告為權限 0） |
| `nvidia_drm` | 有，2 個（且權限 `0400`，需 sudo） |
| `nvidia_modeset` | 有，14 個 |
| `nvidia_uvm` | 有，53 個 |

**通則：`/sys` 沒有時，先看該驅動有沒有自己的 `/proc/driver/<name>/` 或 `/sys/class/` 介面。**

## 速查

```bash
# 0. 對照組（最先做）
for x in <樣本1> <樣本2> <樣本3>; do ...檢查... ; done

# 1. 掃命名空間
find /proc /sys -maxdepth 4 -name '*<kw>*' 2>/dev/null
find /etc /usr/share /var/lib -maxdepth 4 -iname '*<kw>*' 2>/dev/null

# 1'. 結果太多 → 三層篩
find ... -type d                              # ① 濾掉 symlink（交叉引用非內容）
                                              # ② 想「誰建的」，決定該搜哪個子樹
grep -ril '<關鍵字片段>' <限定子樹>             # ③ 有關鍵字時直接跳這層，最確定
                                              #    -i + 搜「片段」：不同介面的名字常有前綴差異
                                              #    （modinfo 的 NVreg_Foo = proc 裡的 Foo）
grep -rl 'kw' /proc                           # ✗ 絕不要：撞上 kcore(128T) / kmsg(阻塞)
grep -ril 'kw' /proc/driver --exclude-dir=gpus  # ✗→✓ 子樹也有暗雷：讀 gpus/ 會喚醒獨顯

# 2. 挖二進位檔（先 file 確認壓縮；找片段，不要找完整路徑）
file <檔案>
strings <檔案> | grep -oE '/[a-zA-Z0-9_/.-]+' | sort -u
zstdcat <檔案>.zst | strings | grep -E '<短關鍵字>'

# 3. 看實際行為（trace=file，不是 openat）
strace -f -e trace=file <cmd> 2>&1 | grep ENOENT

# 4. 套件溯源
dpkg -S <路徑>          # 反查套件
dpkg -L <套件>          # 該套件所有檔案

# 5. 執行中程序
pgrep -f <名稱>          # -f！名稱超過 15 字元時 pgrep <name> 會失效
sudo lsof -p <pid>
```

## 本篇用到的工具，選項涵蓋範圍說明

> 這篇是方法論，用到的 `find`／`strace`／`grep`／`strings`／`lsof` 每一個都有龐大的選項集
> （`find` 超過 80 個、`strace` 超過 40 個）。**這裡只列本文方法會用到的那些，不是完整清單**；
> 完整內容請看各自的 `man`。

### `find`（本文用到的部分）

| 選項 | 作用 |
|---|---|
| `-name <樣式>` / `-iname` | 依檔名比對（後者不分大小寫） |
| `-path <樣式>` | 比對完整路徑 |
| `-type f\|d\|l` | 只找檔案／目錄／符號連結 |
| `-maxdepth <n>` / `-mindepth <n>` | 限制深度（**放在其他條件之前才有效**） |
| `-mtime <n>` / `-mmin <n>` | 依修改時間（天／分鐘） |
| `-size <n>[ckMG]` | 依大小 |
| `-user` / `-group` / `-perm` | 依擁有者／群組／權限 |
| `-exec <指令> {} \;` / `-exec ... {} +` | 對結果執行指令（`+` 是批次，快很多） |
| `-print0` | 以 `\0` 分隔（配 `xargs -0`，**檔名含空白時必用**） |
| `-prune` | 剪掉不要進入的子樹 |
| `2>/dev/null` | 不是 find 的選項，但實務上必加（濾掉 Permission denied） |

**完整清單：`man find`。**

### `strace`（本文用到的部分）

| 選項 | 作用 |
|---|---|
| `-f` | **追蹤子行程**（大多數情況必加） |
| `-e trace=<集合>` | 只追蹤某類呼叫（`file`／`network`／`process`／`openat,stat`…） |
| `-p <PID>` | 附加到既有行程 |
| `-o <檔>` | 輸出到檔案 |
| `-s <長度>` | 字串顯示長度（**預設 32 會截斷，通常要調大**） |
| `-t` / `-tt` / `-ttt` | 時間戳 |
| `-T` | 顯示每個呼叫耗時（**找慢在哪** ） |
| `-c` | **只印統計摘要**（哪個呼叫最多／最慢） |
| `-y` | 把 fd 顯示成實際路徑（**很好用**） |

**完整清單：`man strace`。**

### `strings`

| 選項 | 作用 |
|---|---|
| `-n <長度>` | 最短字串長度（預設 4） |
| `-t d\|o\|x` | 顯示偏移量（十進位／八進位／十六進位） |
| `-a` | 掃描整個檔案（預設只掃已載入區段） |
| `-e <編碼>` | 字元編碼（`s`／`S`／`b`／`l`／`B`／`L`） |
