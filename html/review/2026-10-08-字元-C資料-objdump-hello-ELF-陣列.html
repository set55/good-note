【第五節】

核心關鍵（答到這幾點就算對）：

  1. 兩個人都對：以 char（byte）算是 3 個，以 Unicode 字元算是 1 個。

【第七節〈-Wtype-limits 只抓「永遠成立／永遠不成立」的比較〉、第八節〈另一種寫法：x + y < x 被改寫成 y < 0〉】

核心關鍵（答到這幾點就算對）：

  1. len < used 時，len - used 回繞成很大的正數，判斷誤以為「還有空間」。
  2. 無號數 < 0 永遠為假，所以 gcc 警告；> 0 等於 != 0，結果不固定，是合法寫法，所以不警告。
  3. 有號溢位是 UB，gcc 假設它不會發生，把 x + y < x 改寫成 y < 0；真的溢位時（y 是正的），這個檢查抓不到。

詳細說明：len == used 時結果是 0，> 0 為假，所以不是「永遠為真」，只有 len < used 這種情況會出錯。警告來自 -Wtype-limits（-Wextra 會開啟），它只抓「永遠成立／永遠不成立」的比較。溢位那一問：gcc 不是把檢查當成「必為假」直接刪掉，而是在「不會溢位」的假設下，把它化簡成等價的 y < 0。正確的溢位檢查要在運算之前，用不會溢位的式子判斷，例如 y > 0 && x > INT_MAX - y。

【第四節、第二節】

核心關鍵（答到這幾點就算對）：

  1. 連結時是 ld 在找：照 -L./lib 找到 libfoo.so，在執行檔寫下 NEEDED libfoo.so，只有名字、沒有路徑。
  2. 執行時是動態載入器在找：它不知道當初的 -L，只找自己的預設路徑（加上 LD_LIBRARY_PATH 等），所以找不到。
  3. objdump -p 照樣列出 NEEDED libfoo.so（看不出問題）；ldd 顯示 libfoo.so => not found。

詳細說明：-L 只影響連結時的 ld，不會被記進執行檔。執行時找函式庫的是另一個程式（ld-linux-x86-64.so.2），它的搜尋順序是：執行檔裡的 RUNPATH、LD_LIBRARY_PATH、/etc/ld.so.cache、預設目錄（/lib、/usr/lib）。所以修法是在連結時加 -Wl,-rpath,… 把路徑寫進執行檔，或執行時設 LD_LIBRARY_PATH。objdump -p 只讀檔案，看到的是需求單；ldd 是請載入器實際找一次，所以才看得到 not found。

大致對（盒子 1 → 1）。核心對：執行時由 kernel 先載入 interpreter，再由 interpreter 照需求單載入函式庫、檢查版本，本機的 libc.so.6 沒有那個版本就報錯。-static 不會發生，也對。缺的跟 10-04 一樣：「要哪個版本」是連結時 ld 寫進執行檔的（readelf -V 看得到 GLIBC_2.34），完整的說法是「連結時記下要求、執行時才被檢查」。另外，-static 不是「補上 .text 的洞」，而是把 libc 的程式碼整份複製進執行檔，執行時根本不需要外部的 libc.so.6。

參考答案

【第九節〈自我測驗第 5 題延伸：「找不到版本符號」是怎麼回事〉】

核心關鍵（答到這幾點就算對）：

  1. 連結時：ld 把需要的符號版本（例如 GLIBC_2.34）寫進執行檔。
  2. 執行時：動態載入器檢查目標機器的 libc.so.6 有沒有提供這個版本，沒有就報 version `GLIBC_2.34' not found。
  3. -static 不會發生：libc 的程式碼已經整份複製進執行檔，不再找外部的 libc.so.6。
