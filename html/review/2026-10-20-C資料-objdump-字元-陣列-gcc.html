批改

大致對（盒子 1 → 1）。8 byte 對；kernel 位址對，而且這次把 0xffff888102a4c000 當成一整個位址（10-11 拆成兩段、說成 signed long，這次改正了）。缺的是兩個「為什麼」：

  • 上面 4 位十六進位為什麼一定是 0：x86-64 的虛擬位址只用 48 bit，使用者空間的位址上面 16 bit 一定全是 0；%p 不補前導零，所以只印 12 位。
  • 為什麼看得出是 kernel：上面 16 bit 全是 1，代表它在位址空間的核心那一半。
參考答案

【第二節〈位址看起來只有 6 byte？——%p 不補零，而且最上面 2 byte 一定是 0〉】

核心關鍵：

  1. 指標佔 8 byte。
  2. x86-64 虛擬位址只用 48 bit，使用者空間的位址上面 2 byte 一定是 00 00，%p 不補前導零，所以只印出 12 位。
  3. 0xffff888102a4c000 整個是一個位址；上面 16 bit 全是 1，表示它在位址空間的核心那一半，所以是 kernel 的位址。

詳細說明：canonical address 規定上面 16 bit 必須跟第 47 bit 相同，所以合法的位址只有兩段：0x0000000000000000～0x00007fffffffffff（使用者空間）與 0xffff800000000000～0xffffffffffffffff（核心），中間那一大段不合法。形式上像把第 47 bit 往上複製，但這是 CPU 對位址格式的規定，跟 C 的有號、無號型別無關。

  • 第三問又寫成「永遠為 false」，跟 10-08、10-11 錯在同一處（第三次）。gcc 不是把它變成常數假，而是把 x + y < x 代數化簡成 y < 0（不溢位時兩者等價）。真的溢位時 y 是正的，y < 0 為假，所以抓不到；但 y 是負數時這個判斷照樣會成立，不是「永遠」為假。
參考答案

【第七節〈-Wtype-limits 只抓「永遠成立／永遠不成立」的比較〉、第八節〈另一種寫法：x + y < x 被改寫成 y < 0〉】

核心關鍵：

  1. len < used 時，len - used 回繞成很大的正數，判斷誤以為「還有空間」。
  2. 無號數 < 0 永遠為假，所以 gcc 警告；> 0 等於 != 0，結果不固定，是合法寫法，所以不警告。
  3. 有號溢位是 UB，gcc 假設它不會發生，把 x + y < x 改寫成 y < 0；真的溢位時（y 是正的），這個檢查抓不到。

詳細說明：警告來自 -Wtype-limits（-Wextra 會開啟）。記法：「x + y < x」在數學上（沒有溢位）跟「y < 0」完全等價，gcc 只是做了這個代數化簡，而這個化簡只在「不會溢位」時才成立。正確的溢位檢查要在運算之前，用不會溢位的式子判斷，例如 y > 0 && x > INT_MAX - y。

【第四節〈怎麼確定一個常數的型別？比較時以誰為準？〉】

核心關鍵：

  1. a < b 為真：long 裝得下所有 unsigned int 的值 → 兩邊轉成 long，值不變，−1 < 1。
  2. c < d 為假：無號那邊（unsigned long）的等級 ≥ 有號那邊（int）→ 兩邊轉成 unsigned long，−1 變成 18446744073709551615。
  3. 只對 c < d 警告：只有它把有號的值轉成無號，負數的值會變；a < b 轉成 long，值不變。

詳細說明：要看的是轉換的方向，不是「< 兩邊有一邊是 signed」（a < b 的 a 也是 signed，卻沒有警告）。有號轉無號不是 UB：位元不變，換成無號的讀法（第六節）；UB 是有號溢位。

參考答案

【第六節】

核心關鍵：

  1. u = 4294967295（0xffffffff，2³² − 1）。
  2. 擴展時補什麼由原本的型別決定：signed char 是有號的，做符號擴展，符號位是 1 就補 1；補完再以無號讀。
  3. 改成 unsigned char c = 0xff：原本的型別無號 → 零擴展補 0 → 0x000000ff = 255。

詳細說明：順序是「先依來源型別擴展到 32 bit，再換成目標型別的讀法」。目標型別 unsigned int 是無號的，並不會讓擴展改成補 0——同樣是 -1，來源 signed char 就補 1。c 在記憶體裡都是 0xff，兩個 u 不同完全是來源型別造成的。

參考答案

【第四節、第二節】

核心關鍵：

  1. 連結時是 ld 在找：照 -L./lib 找到 libfoo.so，在執行檔寫下 NEEDED libfoo.so，只有名字、沒有路徑。

#include <stdio.h>

int sum_to(int n)
{
    int total = 0;
    for (int i = 1; i <= n; i++)
        total += i;
    return total;
}

int answer(void)
{
    return sum_to(100);
}

int main(void)
{
	printf("answer:%d\n", answer());
	return 0;
}

-O0 與 -O2 的 answer（本機 gcc 13.3 實際輸出，刪掉組譯指示）：

# -O0

	endbr64
	pushq	%rbp
	movq	%rsp, %rbp
	movl	$100, %edi         # 第一個參數 = 100
	call	sum_to             # 呼叫 sum_to
	popq	%rbp
	ret                        # 回傳值就是 sum_to 留在 %eax 的結果

# -O2
answer:
	endbr64
	movl	$5050, %eax        # 回傳值直接設成 5050
	ret

大致對（盒子 2 → 2）。「不對」、-O2／-O3 求速度、-Os／-Oz 犧牲速度換空間都對（是字母 -Os，不是數字 0s）。第三問沒答到：

  • 「多寫迴圈」「更多的迴圈」說反了。迴圈展開（loop unrolling）是把迴圈本體複製好幾份、一圈做好幾次的工作，圈數變少、指令變多——少做幾次「i <= n 判斷＋跳回去」，換來更長的程式碼。
  • 「直接記下、少了計算」比較像 answer() 直接回傳 5050（常數摺疊），那反而讓程式變小，不是變大的原因。變大的原因是：展開迴圈、向量化（一條指令處理好幾個數）、內嵌（把函式本體複製到每個呼叫處），都是用更多指令換更少的判斷與呼叫，空間換時間。

【第二節〈大小（.text 區段，size -A 實測）〉、〈-O2：答案在編譯時就算好了〉】

核心關鍵：

  1. 不對：-O2／-O3 編出來的程式可能比 -O0 還大。
  2. -O2／-O3 的目標是速度；-Os／-Oz 的目標才是大小。決定大小的是最佳化的目標，不是等級的數字。
  3. 為了跑得快，編譯器會改寫迴圈（展開、一次處理好幾個元素、向量化）、內嵌函式，用更多指令換來更少的迴圈判斷與呼叫，也就是用空間換時間。
