C資料 5. 情境題：你從網路封包裡讀到 4 個 byte，依序是 00 00 01 00。協定規定數字用大端序，所以它代表 256。如果直接用 int * 把這 4 個 byte 讀進本機（x86-64），會得到多少？為什麼？

盒子 1｜過去的作答：s1-02 quiz.md 第 5 題、10-10 複習、10-24 複習

作答（🔒 已批改）
🔒 已批改，不能再修改
批改

對。抓到：65536；小端序是整個 byte 的順序反過來，拼回來是 0x00010000（10-24 把 byte 裡的 01 也翻成 10 的錯改正了）。小修（不扣分）：你寫的「00 01 00 00」是反過來之後照大端序的寫法讀出的數字，記憶體裡的 byte 本身沒動。

參考答案

【第三節】

核心關鍵：

  1. 會得到 65536（0x00010000），不是協定要的 256。
  2. x86-64 是小端序：位址最低的 byte 當最低位，記憶體從低到高的 00 00 01 00 拼回來是 0x00010000。

詳細說明：反過來排的單位是整個 byte（兩個十六進位數字一組），byte 裡面的 01 不會變成 10。網路上的位元組順序（network byte order）是大端序，所以讀網路資料要用 ntohl（network to host long）之類的函式轉換。在大端序的機器上這個函式什麼都不做，在 x86-64 上會把 4 個 byte 反過來。

#include <stdio.h>

__attribute__((noinline)) int widen_char(signed char c) { return c; }   /* noinline：不准內嵌，才看得到真的呼叫 */

int main(void)
{

}

	sub	$0x8,%rsp
	mov	$0xffffffff,%edi       # 呼叫的人：把 -1 放進 %edi（第 1 個參數）
	lea	0xf90(%rip),%rsi       # 準備 printf 的參數，跟本題無關
	call	widen_char         # 呼叫 widen_char
	...
widen_char:
	endbr64                    # 給 CPU 的控制流程保護標記，跟計算無關
	movsbl	%dil,%eax          # 被呼叫的人：只讀 %dil（1 byte），有號擴展成 4 byte 放進 %eax
	ret                        # 回傳 %eax

參考答案

【第三節〈組合語言裡只有 %edi、%dil，為什麼 gdb 印得出 $rdi？〉】

核心關鍵：

  1. %edi、%di、%dil 不是另外的暫存器，都是 %rdi 這一個暫存器的一部分的名字；組合語言沒寫出 %rdi，只代表那個指令只碰它的一部分。

詳細說明：延伸：gdb 不只印得出 $rdi，任何暫存器都印得出來——程式停下時，gdb 請核心把整組暫存器讀出來，跟程式有沒有用到無關。

組語 9-2. 為什麼這樣補，signed char 的 −1 變成 int 之後才會還是 −1（用二補數的權重解釋）？

作答（🔒 已批改）
🔒 已批改，不能再修改
批改

對。抓到：最高位權重是負的，8 位元 −2⁷ ＋ (2⁷ − 1) ＝ −1、32 位元 −2³¹ ＋ (2³¹ − 1) ＝ −1，所以高位要補 1 才維持 −1（10-24 指數錯一位的地方改正了）。小修（不扣分）：要補 1 的是第 8～31 位元（第 31 位就是那個 −2³¹），你寫「第 8 位元到第 30 位元」少算了最高位，但算式裡已經用到它。

參考答案

【第三節〈%dil 是 0xff，為什麼 %eax 變成 0xffffffff：符號擴展補的是第 7 位元〉】

核心關鍵：

  1. 二補數的最高位權重是負的：8 位元 0xff ＝ −2⁷ ＋ (2⁷ − 1) ＝ −1；32 位元 0xffffffff ＝ −2³¹ ＋ (2³¹ − 1) ＝ −1。
  2. 所以高位全補 1，值還是 −1。

詳細說明：對照：補 0 的話 0x000000ff ＝ 255，值就變了。一般化：前面多補一個 1，新的最高位權重是 −2⁸，原本那一位從 −2⁷ 變成 +2⁷，合起來 −2⁸ ＋ 2⁷ ＝ −2⁷，跟原來一樣，值不變；補幾個都同理。

【第一節〈上面說的「符號」到底是什麼〉】
