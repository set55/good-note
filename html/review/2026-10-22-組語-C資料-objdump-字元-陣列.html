組語 8. 暫存器的名字 vs 暫存器本身

盒子 1｜過去的作答：s1-04 quiz.md 第 8 題、10-13 複習

用到的程式（檔案：dil.c）：

#include <stdio.h>

__attribute__((noinline)) int widen_char(signed char c) { return c; }   /* noinline：不准內嵌，才看得到真的呼叫 */

int main(void)
{
    printf("%d\n", widen_char(-1));
    return 0;
}

gcc -O2 -g dil.c -o dil
objdump -d --no-show-raw-insn dil

main 呼叫 widen_char(-1) 的那幾行，objdump 節錄：

main:
	endbr64
	sub	$0x8,%rsp
	mov	$0xffffffff,%edi       # 呼叫的人：把 -1 放進 %edi（第 1 個參數）
	lea	0xf90(%rip),%rsi       # 準備 printf 的參數，跟本題無關
	call	widen_char         # 呼叫 widen_char
	...
widen_char:
	endbr64                    # 給 CPU 的控制流程保護標記，跟計算無關
	movsbl	%dil,%eax          # 被呼叫的人：只讀 %dil（1 byte），有號擴展成 4 byte 放進 %eax
	ret                        # 回傳 %eax

參考答案

【第三節〈組合語言裡只有 %edi、%dil，為什麼 gdb 印得出 $rdi？〉】

核心關鍵：

  1. %edi、%di、%dil 不是另外的暫存器，都是 %rdi 這一個暫存器的一部分的名字；組合語言沒寫出 %rdi，只代表那個指令只碰它的一部分。

詳細說明：延伸：gdb 不只印得出 $rdi，任何暫存器都印得出來——程式停下時，gdb 請核心把整組暫存器讀出來，跟程式有沒有用到無關。實驗裡 widen_char 沒用到 %rcx，info registers rcx 照樣印得出來，是之前留下來的值。

組語 11. gdb 的 break *位址

break deref+4 會得到 Function "deref+4" not defined.，break *deref+4 卻可以。

盒子 1｜過去的作答：s1-04 quiz.md 第 11 題、10-13 複習

用到的程式（檔案：paren.c）：

#include <stdio.h>

__attribute__((noinline)) long copy_val(long x)  { return x; }    /* 回傳 x 本身 */
__attribute__((noinline)) long deref(long *p)    { return *p; }   /* 回傳 p 指向的值 */

int main(void)
{
    long v = 1234;
    printf("%ld %ld\n", copy_val(v), deref(&v));
    return 0;
}

gcc -O2 -g paren.c -o paren
objdump -d --no-show-raw-insn paren

-O2 編出的 deref：

deref:
	endbr64                 # 控制流程保護標記（佔 4 byte，所以下一條是 deref+4）
	mov	(%rdi),%rax         # 把 %rdi 當位址，讀 8 byte 放進 %rax
	ret                     # 回傳 %rax

組語 11-1. * 讓 gdb 怎麼理解後面的東西？

作答（🔒 已批改）
🔒 已批改，不能再修改

不完整。「找 deref 的位址」說得不精確：不加 * 的 break deref 一樣會去找 deref 的位址，所以這不是 * 的作用。兩個核心都沒答到：(1) * 表示後面是一個算出位址的式子，gdb 把 deref + 4 算成一個數字、停在那個位址；(2) 沒有 * 時，後面被當成函式名或行號（linespec），deref+4 整串被當成一個函式名，所以 not defined（跟 10-13 缺同一點）。

  2. 沒有 * 時，後面被當成函式名或行號（linespec），deref+4 整串被當成函式名，所以 not defined。

不完整。第 2 點對：break *deref 停在第一條指令 endbr64（0x117b）。第 1 點錯：break deref 不是停在「堆疊最高處」，也不在 0x1180。它會跳過函式開頭的準備工作（序言，prologue）——push %rbp、mov %rsp,%rbp，有 -g 時連「把參數存進堆疊」也算進去——停在 0x1187。今天重跑題目的指令，實測輸出：

Breakpoint 1 at 0x1187: file paren.c, line 4.
Breakpoint 2 at 0x117b: file paren.c, line 4.

參考答案

【第三節〈上面 break *widen_char+4 的 *：為什麼要加？〉的「break 函式名 和 break *函式名 不一定停在同一個地方」】

核心關鍵：

  1. break deref（函式名）會把中斷點下在函式開頭的準備工作之後（-O0 的 push %rbp、mov %rsp,%rbp 等；這些指令照常執行，停下時已經跑完）。準備工作算到哪裡看有沒有 -g：有 -g 照行號表，連「把參數存進堆疊」也算進去，停在 0x1187；沒有 -g 由 gdb 分析序言，停在 0x1183。
  2. break *deref 不跳過任何東西，停在函式的第一條指令 endbr64（實測 0x117b）。

詳細說明：-O2 沒有這些準備指令，所以兩者剛好都是 0x11f0。用法：看 C 用函式名或行號；看組合語言、要精確停在某一條指令時用 *位址。

【第八節〈三種應對方式〉、〈kernel 怎麼處理：-fno-strict-overflow〉】

核心關鍵：

  1. 有號溢位是未定義行為（UB），C 標準允許編譯器假設它不會發生。
  2. -O0 照字面算，INT_MAX + 1 回繞成 INT_MIN，y > x 為假 → 0；-O2 依這個假設推論 x + 1 一定大於 x，直接回傳 1。
  3. 不是 gcc 的 bug：標準對發生 UB 的程式沒有任何要求，兩種結果都合法。
  4. kernel 用 -fno-strict-overflow（等於 -fwrapv -fwrapv-pointer），讓溢位照二補數回繞、變成有定義的行為；代價是少了依賴「不會溢位」的最佳化，程式可能稍慢。

詳細說明：連 -O0 也不保證照字面算：第四節的 overflow.c 把同一件事寫成一行 return x + 1 > x;，-O0 也回傳 1，因為 gcc 在最佳化之前的化簡階段就把它改掉了（筆記第八節用 -fdump-tree-original 看到）。所以本題的 bigger 才故意拆成兩行。UBSan 的代價才是「每個運算旁多一個檢查、變慢」，那是你寫的代價，但它屬於除錯工具，不是 kernel 的做法。
