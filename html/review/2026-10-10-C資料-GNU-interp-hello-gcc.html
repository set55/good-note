參考答案

【第一節〈unsigned 單獨寫就是 unsigned int：整數型別的所有寫法〉】

核心關鍵：

  1. unsigned x、unsigned int x 都是 unsigned int；signed x 是 int（＝ signed int）。
  2. char 有號還是無號，C 標準交給平台決定（x86-64 有號、ARM 通常無號），標準沒辦法把它定成 signed char 或 unsigned char 其中之一，所以 char 是第三個獨立的型別。型別相不相同看標準的規定，不看範圍。
  3. gcc 沒搞錯：unsigned long 和 long unsigned int 是同一個型別。指定字的順序不重要、有其他指定字時 int 可以省略，gcc 印型別時用它自己的固定寫法（大小在前、有號無號居中、int 放最後）。

詳細說明：如果把 char 定義成 signed char，換到 ARM 這種 char 無號的平台就錯了，定成 unsigned char 則在 x86-64 錯，所以標準只好讓它自成一個型別。同一個函式先宣告成吃 char、再定義成吃 signed char，gcc 會報 conflicting types。same.c 實驗裡 unsigned f(unsigned x) 也被 gcc 印成 unsigned int(unsigned int)。

【第三節】

  1. 會得到 65536（0x00010000），不是協定要的 256。

批改

不完整。第二、三問對：-1 < 0x80000000 假（-1 轉成 unsigned int 變很大），-1 < 2147483648 真（-1 轉成 long 還是 −1），理由也對。第一問錯：原因不是「0x80000000 轉成 long 需要高位補 1」。0x80000000 當成 long 是正的 2147483648，補的是 0，long 也裝得下，仍是同一個數。型別不同的原因是：十進位和十六進位常數的候選型別清單不同，十六進位會先試 unsigned int，十進位永遠不會變成無號。09-30 這題答對過，這次第一問忘了。

參考答案

【第四節〈常數也有型別：0u 的 u 是什麼〉、〈怎麼確定一個常數的型別？比較時以誰為準？〉】

核心關鍵：

  1. 沒有後綴的常數，依序嘗試、選第一個裝得下的型別。十進位的清單是 int → long → long long（永遠不變成無號），2147483648 超過 INT_MAX，所以是 long。
  2. 十六進位的清單是 int → unsigned int → long → …，0x80000000 裝得進 unsigned int，所以是 unsigned int。
  3. -1 < 0x80000000 為假：int 與 unsigned int 比，-1 轉成 4294967295。
  4. -1 < 2147483648 為真：int 與 long 比，-1 轉成 long 還是 −1。

詳細說明：十六進位清單多放無號型別，是因為寫十六進位的人通常在寫位元樣式（例如遮罩 0x80000000），要的是那個 bit 樣式，不是負數。

參考答案

【第五節】

核心關鍵：

  1. copyleft：可以自由使用、修改、散布，但散布修改後（或以它為基礎）的版本時，必須用同樣的授權（GPL）並提供原始碼。
  2. 只是使用、或改了自己用、不給別人，沒有義務。
  3. glibc 用 LGPL：允許非自由的程式連結它而不必開放自己的原始碼，所以商業軟體都能連結 libc.so.6；如果 glibc 是 GPL，連結它的程式在散布時就得整個用 GPL 開放。

詳細說明：copyleft 的目的是讓「自由不能在傳遞途中被拿走」：拿到 GPL 軟體的人，也要拿得到原始碼、有同樣的權利。例子：公司內部改了 GPL 的工具自己用，不必公開；把改過的版本賣給客戶，就要給客戶原始碼，並讓客戶同樣能以 GPL 再散布。

interp 2. ld 和 ld.so（ld-linux-x86-64.so.2）各在什麼時間點、做什麼事？

盒子 1｜過去的作答：s1-01 quiz.md 第 2 題、10-06 複習

🔒 已批改，不能再修改
批改

不完整。時間點對：ld 在連結時、ld.so 在執行時被核心載入。ld 的部分：答到合併同權限的區段、把 interpreter 路徑與函式庫版本寫進檔頭（接近「需求單」）；但沒講 ld 的主要工作「決定每個符號的位址、把 call 的洞填上」，也沒講填不了的（puts）才只寫 NEEDED。ld.so 的部分：載入直接與間接依賴的函式庫，對；「填入程式碼」錯，ld.so 填的是位址（把 puts 的真實位址填進 .got，這叫接線），程式碼是函式庫檔案映射進記憶體時就在了。最後也漏了「跳到程式的進入點 _start」。跟 10-06 錯在同一處（接線）。

參考答案

【第二節〈「跳進程式」是什麼意思：進入點（entry point）〉、第 1 課第五節】

核心關鍵：

  1. ld：連結時（gcc 的最後一步，只做一次）合併各 .o 的區段、決定每個符號的位址、把 call 的洞填上。
  2. 位址在共享函式庫裡的符號（例如 puts），ld 填不了真實位址，只寫需求單：NEEDED libc.so.6、INTERP 路徑。連結完 ld 就結束，執行時不會出現。
  3. ld.so：執行時（每次執行都做）由核心先啟動，依 NEEDED 找到函式庫（含間接依賴）映射進記憶體。
  4. ld.so 把 puts 等符號的真實位址填進 .got（接線），最後跳到程式的進入點 _start（不是 main）。

詳細說明：ld 也會產生程式標頭表，把同權限的區段打包成載入段；ld.so 載入時會檢查函式庫版本（GLIBC_2.34 這種需求）。「填入程式碼」的誤會：ld.so 不搬程式碼，函式庫的程式碼映射進記憶體就在那裡了；它填的是「去哪裡找那段程式碼」的位址。

【第四節、〈交給直譯器的是「路徑」，不是內容：三個實驗〉】

核心關鍵：

  1. 相同：核心在 execve 時讀到「請先執行這支程式」，先啟動直譯器，而不是檔案本身。
  2. 不同：寫的地方（文字檔第一行的 #! vs 程式標頭的 INTERP）；直譯器拿到檔案後做的事（sh 逐行讀文字、執行命令 vs ld.so 載入函式庫、接線後跳進程式本身，之後由 CPU 執行程式的指令）。
  3. 核心交給直譯器的是腳本的路徑（當作命令列參數）：實際執行的是 /bin/cat ./catscript，cat 用這個路徑自己打開檔案，才把整個檔案（含第一行）印出來。

詳細說明：兩個實驗可以證明交的是路徑、不是內容：#!/usr/bin/echo 的腳本印出的是 ./echoscript.sh 這個路徑（echo 只印參數，不讀檔）；把腳本改成 chmod 111（只能執行、不能讀），錯誤訊息是 /usr/bin/cat: ./catscript.sh: Permission denied——cat 自己開檔被擋。如果核心交的是內容，cat 根本不必開檔，這個錯誤就不會發生。

參考答案

【第四節】

核心關鍵：

  1. 組譯器一次只處理 hello.s 這一個檔案，puts 的程式碼在別的檔案（libc.so.6），組譯時不知道它的位址，只能先填 0 占位。
  2. 組譯器同時記下一筆重定位項目 13: R_X86_64_PLT32 puts-0x4（「位移 0x13 的地方，將來填上 puts 的位址」）；連結器照這筆項目去找名叫 puts 的符號，把位址填進那 4 個 byte。

詳細說明：objdump -dr 的 -r 會把重定位項目印在對應指令的下面。同一段裡的 lea 0x0(%rip),%rax 也是同樣情況：字串 "hello, world" 放在 .rodata，位址到連結時才決定，所以也有一筆 R_X86_64_PC32 .rodata-0x4。

對。抓到：O 是最佳化、0 是等級 0（不最佳化），不加任何 -O 就等於 -O0。

參考答案

【第一節】

核心關鍵：

  1. O 是大寫字母 O，代表 Optimize（最佳化）；0 是等級 0，即不最佳化。
  2. 不加任何 -O 時 gcc 就用 -O0，所以它是預設值。

詳細說明：man gcc 在 -O0 底下寫著 This is the default。注意 -O0 是字母 O 加數字 0，不是兩個零。
