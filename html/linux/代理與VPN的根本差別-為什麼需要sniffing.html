代理與 VPN 的根本差別 —— 為什麼 v2ray 需要 sniffing 取出域名？

日期：2026-09-21
情境：做 TPROXY 時被告知要開 sniffing，但直覺上「把封包原封不動丟給遠端伺服器」不就好了？
適用範圍：概念通用；範例為 v2ray 5.40 的 vmess over WebSocket over TLS
相關：用dokodemo-door做TPROXY透明代理、 TPROXY與REDIRECT的差別與原理、 路由器上的透明代理-為什麼不是TUN模式

一句話結論：因為 v2ray 不是 VPN。VPN 轉發的是IP 封包，代理轉發的是連線—— vmess／vless／trojan／socks 這類協定，每建立一條連線都必須先告訴伺服器「請幫我連到 <位址>:<埠>」，協定裡根本沒有「這是一個封包，請幫我路由」這種語意。所以目的地一定要給；sniffing 決定的只是「給 IP，還是給域名」。

一、兩種架構，從根本上不同

【L3 隧道 / VPN】WireGuard、OpenVPN、TUN 模式
   程式 → IP 封包 → 加密整個封包 → 對端拆開 → 對端「像路由器一樣」轉發出去
   傳輸的單位：IP 封包
   對端要做的事：路由

【L7 代理】vmess、vless、trojan、shadowsocks、socks5、http
   程式 → TCP 連線 → 代理讀出「你要連哪裡」→ 告訴伺服器 → 伺服器自己去連 → 轉送位元組
   傳輸的單位：一條連線的位元組串流
   對端要做的事：建立新連線（它是 client，不是 router）

你的路由器上兩種都有：OpenVPN 的 tun0（L3 隧道，防火牆裡的 ovpnsetwall zone 就是它）與 v2ray（L7 代理）。它們解決同一個問題，但機制完全不同。

二、所以「直接給封包」為什麼不可能

你的出站設定是：

vmess → WebSocket → TLS → :443

這是一條 TCP 連線。它承載的是 vmess 協定，而 vmess 的請求標頭長這樣（概念上）：

[驗證資訊][指令: TCP/UDP][目的位址][目的埠][...][資料...]
                              ↑
                    這個欄位不是選配，是必填

協定裡沒有「原始 IP 封包」這個型別。 伺服器收到請求後做的事是 connect(目的位址, 目的埠)——它扮演的是一個 client，不是 router。你給它一個 IP 封包，它不知道該拿來幹嘛。

要做到「直接給封包」，那就是 VPN——需要對端有 TUN 介面、開啟 ip_forward、做 NAT、管路由表。那是另一套架構（也就是 OpenVPN 在做的事）。

三、TPROXY 交給 v2ray 的也不是封包

這裡有個常見誤解。TPROXY 雖然是在 IP 層攔截，但它「交付」給 v2ray 之後：

核心：收下封包 → 完成 TCP 三向交握 → 組成一條 socket
v2ray：accept() 到一個 socket，從裡面 read() 出位元組
       原始目的地是透過 IP_RECVORIGDSTADDR 拿到的「中繼資料」

v2ray 拿到的是一條已經建立好的 TCP 串流，不是一堆封包。 它甚至看不到 IP 標頭——那是核心處理掉的。（TUN 模式才是真的拿到原始封包，所以它要自己實作一整套 TCP/IP 堆疊，用的是 gVisor netstack。）

四、於是真正的問題是：給 IP，還是給域名？

目的地一定要填。差別只在填什麼：

不開 sniffing 開 sniffing
v2ray 知道的目的地 只有 IP（來自 IP_RECVORIGDSTADDR） 域名（從第一段資料還原）
怎麼得到 核心給的中繼資料 偷看 TLS ClientHello 的 SNI／HTTP 的 Host／QUIC 的 SNI
vmess 標頭填什麼 1.2.3.4:443 example.com:443
誰做 DNS 解析 LAN 客戶端（本地） 遠端伺服器

給域名的三個好處

① 對 DNS 污染免疫

不開 sniffing 時，域名是 LAN 客戶端在本地解析的——走的是你路由器的 dnsmasq → 上游 DNS。那條路如果被污染，客戶端拿到錯的 IP，v2ray 只會忠實地把你送去那個錯的 IP。 代理再完美也救不了，因為錯誤發生在連線建立之前。

開了 sniffing，域名交給遠端伺服器解析——它在牆外，解析結果是對的。

② 分流規則才能運作

v2ray 的 routing.rules 多半是域名規則（domain:、geosite:）。只有 IP 時，這些規則一條都比對不到，只剩 geoip 之類的 IP 規則有用。

你目前的設定是靠 inboundTag 分流（tproxy-in → vmess-out-s03），所以「走不走代理」不受影響。但你之後想做「國內直連、國外走代理」時就一定需要域名。

③ CDN 會給到離伺服器近的節點

同一個域名在不同地理位置解析出的 IP 不同。由遠端伺服器解析，它拿到的是離它近的 CDN 節點，伺服器→源站那一段會更快。

五、sniffing 的運作方式與代價

運作方式：v2ray 收到連線後先不急著轉發，讀取第一段資料，嘗試用 destOverride 指定的解析器辨識：

解析器 從哪裡取域名
tls TLS ClientHello 的 SNI（Server Name Indication）擴充
http HTTP 請求的 Host 標頭
quic QUIC Initial 封包裡的 SNI
fakedns 從 fake-ip 反查（搭配 v2ray 自己的 DNS 用）

三個代價：

  1. 要等第一段資料才能決定路由——多一個小延遲（通常可忽略，但不是零）。
  2. 嗅不到就退回 IP：純 TCP 協定（SSH、資料庫、遊戲）沒有 SNI 也沒有 Host， sniffing 幫不上忙，還是只有 IP。
  3. destOverride 會真的改寫目的地——如果客戶端故意連某個特定 IP （例如內網服務、或你手動指定的節點），被嗅出域名後重新解析可能連到別的地方。較新版本提供 routeOnly 選項：只用嗅到的域名做路由判斷，不改寫實際連線目標，這是比較安全的預設。

六、什麼時候真的可以不開

  • 全部流量都走同一個出口、而且 DNS 沒被污染：例如你現在的 inboundTag 分流，對「能不能通」沒影響。
  • 內網專用的代理：目的地都是 IP，本來就沒有域名。

但只要你有以下任一需求，就必須開： 分域名走不同出口、繞過 DNS 污染、需要正確的 CDN 節點、想在 log 裡看到域名而不是一串 IP。

七、回到最初的直覺

「把封包丟給遠端就好」這個直覺沒有錯——它描述的就是 VPN。選擇代理協定而不是 VPN，換來的是：

L3 隧道（VPN） L7 代理
對端要做什麼 路由、NAT、轉發封包 建立新連線
需要告知目的地 ❌ 封包裡就有 ✅ 每條連線都要明說
能不能分流 只能靠 IP／路由表 可依域名、協定、使用者細分
偽裝成一般流量 難（流量特徵明顯） 容易（vmess over ws over TLS 看起來就是 HTTPS）
UDP／ICMP 天生支援 要協定額外支援，ICMP 多半不支援

代理需要「明說目的地」這個看似麻煩的設計，正是它能做細緻分流與流量偽裝的原因。 sniffing 只是在透明代理的情境下，把「客戶端沒機會告訴你的域名」補回來。

自我測驗

  1. 為什麼說「把封包原封不動丟給遠端」在 vmess 上做不到？從 vmess 請求標頭的組成回答。
  2. TPROXY 是在 IP 層攔截的，那為什麼 v2ray 拿到的不是封包？它實際拿到什麼？原始目的地又是怎麼來的？
  3. 不開 sniffing 時，域名是誰解析的？這在什麼情況下會造成「代理有通但連到錯的地方」？
  4. sniffing 從哪三種流量取得域名？哪一類流量它完全幫不上忙？
  5. 情境題：你的設定是全部流量走同一個 vmess 出口，目前不開 sniffing 也能正常上網。請說出兩個「之後一定會需要開」的情境，以及開了之後可能踩到的一個副作用。
