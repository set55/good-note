mtr 可以不走 ICMP 嗎？——-T／-u 換掉的只有「去程探測封包」，回話的永遠是 ICMP

日期：2026-09-10
情境：用 mtr 追路徑時中段一片 ???，懷疑是 ICMP 被濾掉，想知道能不能改走 TCP
對應檔案：無（純指令操作）
適用範圍：mtr 0.95（Linux）；實測目標 1.1.1.1，實測網路為本機家用寬頻

一句話結論：mtr 預設送 ICMP ECHO，-T 可以改送 TCP SYN、-u 改送 UDP；但中途每一跳回給你的訊息永遠是 ICMP time exceeded——換協定改變的是「封包能不能出得去」，不是「路由器願不願意回話」。

一、可以，指令長這樣

mtr 1.1.1.1                     # 預設：ICMP ECHO request（type 8）
mtr -T -P 443 1.1.1.1           # TCP SYN 打 443
mtr -u -P 33434 1.1.1.1         # UDP datagram
mtr -S -P 80 1.1.1.1            # SCTP（少用，但 mtr 0.95 有）

-T 是 --tcp，-P 是目標埠（target port）。TCP 模式下 -s（封包大小）會被忽略，因為 SYN 封包不帶資料。

最基本的用法：文法骨架、兩種執行方式、輸出每一欄在講什麼

2026-10-09 提問：「請問mtr怎麼用?」（上面四行指令都是在換協定，這段補上「mtr 本身怎麼跑、輸出怎麼讀」）

文法骨架（mtr --help 第一行就是 mtr [options] hostname）：

mtr [選項] <主機名或 IP>
  • [選項]：可以全部省略，省略時就是「ICMP 探測、互動畫面、每秒送一輪、做反向 DNS」。全部選項見文末 mtr 完整選項。
  • <主機名或 IP>：必填，就是你要追的目標；給主機名時 mtr 先自己做 DNS 解析。唯一的例外是用 -F <檔> 從檔案讀目標清單。

mtr 有兩種執行方式，差在「什麼時候結束、輸出到哪裡」：

方式 指令 行為 什麼時候用
互動模式（預設） mtr 1.1.1.1 全螢幕畫面，一直送、一直更新統計，按 q 離開；跑的時候可以按鍵切換（按鍵見文末互動模式的按鍵） 自己盯著看、等偶發丟包出現
報表模式 mtr -r -c 5 1.1.1.1 不開畫面，送滿 -c 輪後印一次結果就結束 貼給別人、寫進筆記、放進腳本

報表模式最常用的組合是 -rwn -c <次數>：-r 報表、-w 寬版（主機名不截斷）、-n 不做反向 DNS（快很多，也不會因為 DNS 卡住）。本機實測（2026-10-09，家用寬頻 → 1.1.1.1）：

二、為什麼換協定有時有效、有時完全沒用

traceroute 家族（含 mtr）的原理只有一句話：送出 TTL（Time To Live，存活跳數）刻意設小的封包，讓它在第 N 跳「死掉」，逼那台路由器回報錯誤。 路由器回報用的是 ICMP（Internet Control Message Protocol）的 time exceeded（type 11）。

關鍵在於這個流程有兩個方向、而只有一個方向是你能換的：

方向 內容 能不能換協定
去程探測 ICMP echo／TCP SYN／UDP datagram，由 -T／-u 決定 可以
中途跳點的回覆 一律是 ICMP time exceeded（type 11） 不行，沒有替代品

由此推出兩個重要結論：

  • -T 有效的情境：防火牆／ACL 是按「去程封包長什麼樣」決定丟不丟。很多網路會丟棄 ICMP echo 與 UDP 高位埠，卻放行往 443 的 TCP SYN（因為那看起來就是一般的 HTTPS 連線）。換成 TCP，封包走得更遠，就能逼出更多跳點。
  • -T 救不了的情境：若對方是「不產生 ICMP 錯誤訊息」或「入向 ICMP 全擋」，那不論你送什麼協定都看不到那一跳。這時 ??? 是物理上無解的，不是指令下錯。

三、實測三種模式的差異

同一條路徑（家用寬頻 → 1.1.1.1）、同一時間、-c 2 -m 12，三種模式抓到的跳點差很多：

4 100.76.3.1 100.76.3.1 100.76.3.1
5 14.147.203.26 14.147.203.26 ???
6 14.147.203.25 ??? ???
7 14.147.127.29 ??? ???
9 202.97.12.45 202.97.66.25 ???
10 110.94.123.118 ??? 110.94.123.118
12 172.69.117.60 172.69.117.60 172.69.117.39

三件事值得注意：

  1. TCP 模式抓到最多跳點，UDP 最少。這就是上一節說的「按去程長相過濾」。
  2. hop 9 在 TCP 和 ICMP 模式下是不同的 IP（202.97.12.45 vs 202.97.66.25）。不是哪個錯，而是骨幹有多條等價路徑（ECMP，Equal-Cost Multi-Path），不同的五元組（5-tuple）會被雜湊到不同鏈路。換了協定就換了路徑，所以跨模式比較「同一跳」本身要很小心。
  3. hop 12 在同一次報告裡出現兩個 IP（172.69.117.60 與 .39），那是同一跳有並行鏈路。

把這些 IP 再丟去做 ASN 對照（方法見 查詢請求經過哪些AS與ISP），路徑的真實面貌才出來：

14.147.x / 202.97.x  AS4134 CHINANET  ← 同一家電信商的骨幹，連續好幾跳
110.94.123.118    NA                  ← 有註冊紀錄但查不到 BGP 前綴，典型的互連網段／未公告位址
172.69.117.60     AS13335 CLOUDFLARENET

四、終點的判定方式各自不同

中途跳點的判定三種模式都一樣（等 ICMP type 11），但「到了沒有」的判定不同：

模式 抵達終點的證據
ICMP 目標回 ICMP echo reply（type 0）
UDP 目標回 ICMP port unreachable（type 3 code 3）——因為故意打一個沒人聽的高位埠
TCP 目標回 SYN/ACK（埠開著）或 RST（埠關著）

所以 TCP 模式有個附帶好處：它同時在測「這個服務埠到底通不通」。 mtr -T -P 443 最後一跳有回應，等於 TCP 層握得起來；而 ICMP 模式只證明主機活著，不代表你的 HTTPS 連得上。反過來說，TCP 模式不會完成三向交握——mtr 收到 SYN/ACK 就算完成量測，核心隨後送 RST 把半開連線收掉，所以對端的應用層通常不會留下存取紀錄。

五、權限：為什麼不用 sudo 也能跑

這些模式都要自己組封包、自己收 ICMP，需要 raw socket（原始通訊端），一般要 root。 mtr 的做法是把這件事切出去給一個小程式 mtr-packet，只對它授予能力（capability）：

$ getcap /usr/bin/mtr-packet
/usr/bin/mtr-packet cap_net_raw=ep

cap_net_raw 就是「可以開 raw socket」這一項權限，ep 表示 effective + permitted。所以一般使用者直接跑 mtr -T 就行。若你在某台機器上發現非 root 跑不動，先查這個能力是不是掉了（例如從原始碼自行編譯安裝、或檔案被 cp 過導致 capability 沒跟著複製）。

六、兩個容易搞混的旗標

-I 在 mtr 和 traceroute 裡意思完全不同，這個坑踩過一次就會記得：

旗標 traceroute mtr
-I 用 ICMP echo 探測 指定網路介面（--interface）
-T 用 TCP SYN 探測 用 TCP SYN 探測（一致）
-P 搭 -T 時是目標埠 目標埠（--port）

mtr 不需要「指定用 ICMP」的旗標，因為那本來就是預設值。另外 -L 是 UDP 的來源埠，跟 -P 不要弄反——想固定來源埠以繞過某些負載平衡雜湊時才會用到。

七、中間跳點的 Loss% 和 RTT 不要當真

同一份 TCP 模式實測報告裡：

  6.|-- 14.147.203.25   50.0%   2   3078.  ← 50% 遺失、RTT 3 秒
 12.|-- 172.69.117.60    0.0%   2     57.1 ← 終點 0% 遺失、57ms

如果中間真的丟掉一半封包、延遲三秒，終點不可能是 0% 和 57ms。原因是路由器轉送封包靠硬體（資料層 data plane），而「產生一則 ICMP 錯誤訊息」是交給 CPU 做的（控制層 control plane），且依規範會被速率限制（rate limit）。所以中間跳點的數字反映的是那台設備回應探測的意願，不是轉送品質。

判讀原則：

  • 只有最後一跳的 Loss% 和 RTT 有意義。
  • 中間某跳 Loss 高、後面每一跳都正常 → 那跳只是懶得回你，沒問題。
  • 從某跳開始、之後每一跳 Loss 都維持高檔 → 這才是真的在丟包，問題出在那一跳前後。

八、該選哪個模式

想做的事 用法
一般看路徑、延遲 預設 ICMP，通過率通常最好
中段一片 ???，想多挖出幾跳 mtr -T -P 443（或 80）
確認某個服務埠真的通 mtr -T -P <該服務的埠>
懷疑 ICMP 被特別對待（例如被降速） 用 TCP 對照一次，兩者差很多就是證據
古早 traceroute 的相容行為 -u，但現代網路常被擋，最沒用

務實做法：同一個目標跑兩種模式對照。差異本身就是資訊——它告訴你路上的設備是按協定在做政策。

  1. -T 換掉的是整個量測流程中的哪一半？另一半是什麼、為什麼換不掉？從這個區分推論出「-T 在什麼情況下一定救不了 ???」。

r 把所有計數歸零（改完網路設定後想重新統計時用）
o <欄位> 設定要顯示的欄位，預設 LRS N BAWV（字母見下表）
j 在延遲統計（LS NABWV）與抖動統計（DR AGJMXI）兩組欄位之間切換
c <n> 跑滿 n 輪就停，預設無限
i <n> 探測間隔改成 n 秒，預設 1
f <n> 從第 n 跳開始（初始 TTL），預設 1
m <n> 最多追到第 n 跳（最大 TTL）
s <n> 封包大小改成 n；n 為負數表示隨機大小
b <c> payload 的位元樣式改成 c（0～255）；負數表示隨機
Q <t> IP 標頭的 TOS（Type of Service，服務類型）欄位改成 t
u 在 ICMP ECHO 與 UDP 之間切換
y 切換顯示的 IP 額外資訊（同 -y）
z 開關 ASN 顯示（同 -z）
q 離開

-o 與互動鍵 o 用的欄位字母（全部 14 個，依 man mtr 的 --order 一節）：

字母 欄位 字母 欄位
L 遺失率（Loss%） W 最慢 RTT（Wrst）
D 掉了幾個（Drop） V 標準差（StDev）
R 收到幾個（Rcv） G 幾何平均（Gmean）
S 送出幾個（Snt） J 目前抖動（Jttr，最近兩次 RTT 的差）
N 最新一次 RTT（Last） M 平均抖動（Javg）
B 最快 RTT（Best） X 最大抖動（Jmax）
A 平均 RTT（Avg） I 到達間隔抖動（Jint）

欄位字串裡的空白也會照樣顯示成欄與欄之間的空隙，所以 "LSD NBAW" 會在 Drop 與 Last 中間多一個空欄。
