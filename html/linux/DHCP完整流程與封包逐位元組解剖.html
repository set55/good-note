DHCP 完整流程與封包逐位元組解剖 —— 一次租約從 DISCOVER 到 ACK 到底交換了什麼

日期：2026-09-11
情境：知道網卡是靠 DHCP 拿 IP，但不知道那四個封包實際長什麼樣、每個欄位為什麼要那樣填
對應檔案：無（協定解析；hex dump 為依 RFC 2131／2132 規格組出的教學範例封包，非真實抓包檔，欄位值與校驗和皆已計算驗證）
適用範圍：DHCPv4（RFC 2131 / RFC 2132）；DHCPv6 只在第十二節做對照
關聯：確認網路介面是否使用DHCP（怎麼判斷這台在用 DHCP）、 查詢轉發表與路由表（DHCP 派下來的 default route 長什麼樣）、 查詢目前使用的DNS伺服器（option 6 派下來的 DNS 去了哪裡）

一句話結論：DHCP（Dynamic Host Configuration Protocol，動態主機設定協定）整個設計都在解一個先有雞還是先有蛋的問題——「還沒有 IP 的機器要怎麼用 IP 網路去要一個 IP」。答案是全部靠廣播（broadcast）＋把自己的 MAC 位址寫進封包內容裡當身分證。四步 DORA 中真正成立租約的只有 REQUEST／ACK 這一對，DISCOVER／OFFER 只是「有誰在？」「我在，這個給你要不要？」的詢價階段。

一、先有雞還是先有蛋

一台剛接上網路線（或剛連上 Wi-Fi）的機器，處境是這樣的：

  • 它沒有 IP 位址，所以不能當來源位址去送任何一般的 IP 封包。
  • 它不知道 DHCP 伺服器的 IP，所以不知道目的位址要填誰。
  • 它不知道路由器（default gateway）是誰，所以送不出這個子網路。
  • 它連子網路遮罩（subnet mask）都不知道，所以連「誰算是同一個子網路」都判斷不了。

DHCP 的每一個設計怪癖，幾乎都是為了繞開這四點：

問題 DHCP 的解法
沒有來源 IP 來源位址填 0.0.0.0（RFC 791 定義的「本主機、本網路」）
不知道伺服器 IP 目的位址填 255.255.255.255（受限廣播，limited broadcast，路由器不會轉送）
不知道 gateway 廣播根本不需要 gateway，交換器（switch）會把它送到同一個廣播網域的每一台機器
沒有 IP 就沒辦法用一般 socket 收封包 客戶端直接開 raw socket／AF_PACKET，繞過核心的 IP 協定堆疊
伺服器要回話，但客戶端還沒有 IP，沒辦法用 ARP 問到 MAC 客戶端把自己的 MAC 寫在 DHCP 內容的 chaddr 欄位裡，伺服器直接拿它當第二層目的位址

最後一點是整個協定的靈魂。 一般網路通訊「IP → ARP → MAC」的順序在這裡完全走不通，所以 DHCP 把 MAC 位址搬進應用層封包內容裡，變成一張隨封包附上的身分證。這也是為什麼 DHCP 封包裡會有一個看起來很多餘的 chaddr（client hardware address）欄位—— 外層乙太網路標頭明明已經有來源 MAC 了，但那個標頭在經過 relay（中繼代理）之後會被換掉， chaddr 才是那個能一路傳到底、不會被改寫的身分。

心法：DHCP 之所以長得這麼怪，是因為它是一個「必須在網路層還沒設定好之前就能運作」的協定。它不能依賴任何它自己正要去設定的東西。

還有一個副作用值得記住：因為客戶端在拿到 IP 之前必須用 raw socket 直接收送原始乙太網路訊框，所以 DHCP 客戶端行程（dhclient、dhcpcd、NetworkManager 內建的客戶端）都需要 root 權限或 CAP_NET_RAW 能力（capability）。這跟 mtr 需要 cap_net_raw 是同一個原因，細節見 mtr改用TCP或UDP探測 的權限一節。

二、DORA 四步全景

DHCP 取得租約的四個步驟合稱 DORA，取四個訊息的字首：

客戶端 (nb-set)                                          伺服器 (192.168.1.1)
3c:58:c2:4a:1b:7e                                        74:da:88:9f:02:10
      |                                                          |
      |  1. DHCPDISCOVER                                         |
      |     Ethernet: → ff:ff:ff:ff:ff:ff  (廣播)                |
      |     IP: 0.0.0.0 → 255.255.255.255                        |
      |     UDP: 68 → 67                                         |
      |     「有沒有 DHCP 伺服器？我的 MAC 是 3c:58:...」          |
      |--------------------------------------------------------->|
      |                                                          |
      |  2. DHCPOFFER                                            |
      |     Ethernet: → 3c:58:c2:4a:1b:7e （單播，靠 chaddr）     |
      |     IP: 192.168.1.1 → 192.168.1.151                      |
      |     UDP: 67 → 68                                         |
      |     「我在。192.168.1.151 給你用 12 小時，附遮罩/GW/DNS」  |
      |<---------------------------------------------------------|
      |                                                          |
      |  3. DHCPREQUEST                                          |
      |     Ethernet: → ff:ff:ff:ff:ff:ff  (仍然是廣播！)         |
      |     IP: 0.0.0.0 → 255.255.255.255                        |
      |     「我要 192.168.1.151，選 192.168.1.1 這家。            |
      |      其他有出價的伺服器請把位址收回去」                     |
      |--------------------------------------------------------->|
      |                                                          |
      |  4. DHCPACK                                              |
      |     「成交。租約 43200 秒從現在開始算」                     |
      |<---------------------------------------------------------|
      |                                                          |
      |  5. （客戶端自行）ARP probe 確認沒人在用這個 IP            |
      |     然後才真的把 IP 掛上網卡                              |

四步的分工必須說清楚，這是最多人搞混的地方：

步驟 誰送 這一步「成立」了什麼
DISCOVER 客戶端廣播 什麼都沒成立。只是在問「這個廣播網域裡有誰能發 IP？」
OFFER 伺服器 還沒成立租約。 這只是報價。伺服器通常會暫時保留這個 IP，但那是實作善意，不是協定保證
REQUEST 客戶端廣播 客戶端公開宣告「我選這一家」。廣播是關鍵，落選的伺服器靠這個廣播知道自己沒被選上
ACK 伺服器 租約在此刻成立，租約計時從客戶端收到 ACK 開始算

為什麼要四步而不是兩步？ 因為同一個網段可能有多台 DHCP 伺服器（例如公司有主備兩台，或有人不小心接了一台家用路由器上來）。兩步的話，每台伺服器都會自作主張配一個 IP 給你，你會拿到好幾個互相衝突的位址。四步把流程拆成「詢價」和「下單」，並且刻意讓下單那一步用廣播，好讓所有出價者都聽得到結果。

不是每次都要走完四步。 客戶端重開機時如果本機還存著上次的租約檔（lease file），會直接從 REQUEST 開始（稱為 INIT-REBOOT 狀態），變成兩步的 REQUEST／ACK。續約也是兩步。真正跑完整套 DORA 的時機其實只有「這張網卡第一次接觸這個網路」。

三、封包的三層外殼

DHCP 是應用層協定，所以每個 DHCP 封包外面包了三層：

+--------------------------------------------------+
| Ethernet 標頭 14 bytes                            |
| dst MAC(6) | src MAC(6) | EtherType 0x0800 (2)    |
+--------------------------------------------------+
| IP 標頭 20 bytes                                  |
| 版本/長度 | ToS | 總長度 | ID | 旗標 | TTL | 協定 17 |
| 檢查碼 | 來源 IP | 目的 IP                          |
+--------------------------------------------------+
| UDP 標頭 8 bytes                                  |
| 來源埠 | 目的埠 | 長度 | 檢查碼                     |
+--------------------------------------------------+
| DHCP／BOOTP 內容 至少 300 bytes                    |
| 固定欄位 236 bytes + magic cookie 4 + options      |
+--------------------------------------------------+

幾個必須解釋的設計：

（1）為什麼是 UDP（User Datagram Protocol，使用者資料包協定）不是 TCP？ TCP 需要三次握手，而握手需要雙方都有 IP——客戶端沒有。而且 TCP 不能廣播。 UDP 沒有連線狀態，可以直接廣播，正好符合需求。可靠性由 DHCP 自己用「逾時重送」補起來。

（2）為什麼是 67 和 68 兩個埠，而不是像其他協定那樣「伺服器固定埠、客戶端隨機埠」？ 因為回覆是廣播送出去的。如果客戶端用隨機埠（例如 51234），那台網段上所有機器都會收到這個廣播，但只有那個剛好開著 51234 的客戶端會收——問題是伺服器在回覆時可能得廣播給一台還沒有 IP 的機器，核心協定堆疊沒辦法把封包對應到 socket。把客戶端埠固定成 68，收送雙方才能在完全沒有 IP 的狀態下用 raw socket 精確過濾出「這是給 DHCP 客戶端的」。

  • 67：伺服器埠（bootps）。客戶端 → 伺服器的封包，目的埠一律 67。
  • 68：客戶端埠（bootpc）。伺服器 → 客戶端的封包，目的埠一律 68。

所以抓包過濾條件永遠是 port 67 or port 68。

（3）為什麼 IP 的 TTL（Time To Live，存活跳數）常常是 255 或 64？ 兩者都看得到。ISC dhclient 送 255（historical，確保不會被中途丟掉）， Linux 核心預設 64。TTL 在這裡沒有實質意義，因為封包本來就不會離開本網段。

（4）為什麼 DHCP 內容至少 300 bytes？ 繼承自 BOOTP（Bootstrap Protocol，開機協定）。BOOTP 規定最小訊息 300 bytes，因為早年有些 BOOTP 實作是寫死在網路卡的開機唯讀記憶體裡，收到短封包會出事。所以現在的 DHCP 封包尾端常常有一大串 00 填充（pad）——那不是資料，是為了湊到 300。

四、BOOTP 固定欄位 236 bytes

DHCP 不是全新的協定，它是在 BOOTP 上長出來的（RFC 2131 明說 DHCP 是 BOOTP 的擴充）。所以 DHCP 內容的前 236 bytes 完全沿用 BOOTP 的固定欄位格式，很多欄位在 DHCP 時代已經沒用了，但為了相容還是留著。逐一解釋（偏移量從 DHCP 內容起算）：

偏移 長度 欄位 意義與注意事項
0 1 op 操作碼。1 = BOOTREQUEST（客戶端→伺服器），2 = BOOTREPLY（伺服器→客戶端）。只分方向，不分訊息類型——DISCOVER 和 REQUEST 的 op 都是 1，真正的訊息類型在 option 53
1 1 htype 硬體類型。1 = Ethernet（乙太網路），沿用 ARP 的編號表
2 1 hlen 硬體位址長度。乙太網路 MAC 是 6
3 1 hops 經過幾個 relay。客戶端送出時填 0，每經過一個 DHCP relay 就 +1。用來防止 relay 迴圈
4 4 xid 交易編號（transaction ID）。客戶端隨機產生，同一輪 DORA 四個封包的 xid 必須相同。客戶端就是靠這個把收到的廣播回覆認出來「這是回我的」
8 2 secs 客戶端從開始嘗試取得位址到現在經過幾秒。多數客戶端填 0 或很小的值。用途：某些備援設計會讓備用伺服器只回應 secs 超過門檻的請求（代表主伺服器沒回應）
10 2 flags 只有最高位元有意義：broadcast flag（廣播旗標，B）。設為 1 表示「我還不能收單播，請用廣播回我」。其餘 15 bits 保留為 0
12 4 ciaddr client IP address。只有在客戶端已經有可用 IP 而且能收單播時才填（也就是續約 RENEWING／REBINDING 狀態）。DISCOVER 和第一次的 REQUEST 必須填 0.0.0.0
16 4 yiaddr "your" IP address。伺服器要配給你的 IP 就在這裡。客戶端送出的封包這欄一律 0
20 4 siaddr next server IP。不是 DHCP 伺服器的位址！ 這是網路開機（PXE，Preboot Execution Environment，開機前執行環境）流程中「下一步去哪台抓開機映像檔」的位址。DHCP 伺服器自己的身分是用 option 54 表達的。這是最常被誤讀的欄位
24 4 giaddr gateway IP address，其實是 relay agent 的位址。客戶端永遠填 0；如果封包經過 DHCP relay，relay 會把自己面向客戶端那一側的 IP 填進去。伺服器靠它判斷「這個請求來自哪個網段，該從哪個位址池撈 IP」，並且知道回覆要送回給誰
28 16 chaddr client hardware address。客戶端 MAC，靠左對齊，後面補 0 到 16 bytes（乙太網路只用前 6 bytes）。這是客戶端的身分證
44 64 sname 伺服器主機名稱字串，選填。PXE 場景會用，一般 DHCP 全填 0。（option overload 機制可以把它借來塞 options，罕見）
108 128 file 開機檔名，選填。PXE 用來指定開機映像檔路徑（例如 pxelinux.0）。一般 DHCP 全填 0
236 4 magic cookie 固定四個位元組 63 82 53 63（十進位 99.130.83.99）。這是 BOOTP 與 DHCP 的分界線：解析器看到這四個位元組，才知道後面是 DHCP options 而不是 BOOTP 的 vendor 欄位
240 變動 options TLV 編碼的選項，見下一節

注意 ciaddr／yiaddr／siaddr／giaddr 這四個名字非常容易混淆，但它們的填法就是判斷「這個封包處在租約流程哪一個階段」最可靠的依據。 之後的封包解析會反覆用到這一點。

五、Options 的 TLV 編碼

Magic cookie 之後全部是 options，用 TLV（Type-Length-Value，類型—長度—值） 編碼：

+--------+--------+--------+--------+--- ... ---+
|  code  | length |      value (length bytes)   |
+--------+--------+--------+--------+--- ... ---+
   1 byte  1 byte

兩個例外不帶長度欄位：

  • 0x00 Pad：單獨一個位元組，用來對齊或填充，沒有 length、沒有 value。
  • 0xff End：單獨一個位元組，代表 options 結束。之後的位元組全部忽略。

長度只有 1 byte，所以單一 option 的值最多 255 bytes。要塞更長的資料就得靠拆分或 option overload（把 sname／file 欄位借來當 options 空間）。

常用 options 對照表（本文封包會用到的都在裡面）：

六、封包一：DISCOVER

6.2 兩個要記住的重點

（1）option 55 決定了你會拿到什麼。 伺服器就算設定了 NTP 伺服器，如果客戶端沒在 option 55 裡問，多數伺服器就不會給。「路由器明明設了但客戶端沒拿到某個參數」，第一個要查的就是客戶端有沒有去要。

（2）flags 的廣播旗標是個雞生蛋問題的殘留。 有些老舊的 TCP/IP 協定堆疊在 IP 位址設定好之前，沒辦法接收目的位址不是自己的單播封包。這種客戶端必須把 B 位元設成 1，要求伺服器改用廣播回覆。現代 Linux 客戶端用 raw socket 收封包，不受這個限制，所以填 0。抓包時看到 flags 是 80 00，就代表對方要求廣播回覆。

6.3 沒收到回覆怎麼辦：重送策略

RFC 2131 規定用指數退避（exponential backoff）：第一次等 4 秒，然後 8、16、32、64 秒，之後固定 64 秒重試，而且每次都要再加上 −1 到 +1 秒的隨機抖動（randomization），避免整棟大樓停電復電後所有機器同時廣播（thundering herd，驚群效應）。

所以「插上網路線後大約 5 秒、13 秒、29 秒各看到一個 DISCOVER」是正常的重送節奏，不是客戶端壞掉。

7.4 為什麼 siaddr 是 0 但 option 54 有值

這是本節最重要的一句：siaddr 不是 DHCP 伺服器位址。

  • siaddr（next server）：PXE 網路開機時「去哪台 TFTP 伺服器抓開機檔」，跟 DHCP 身分無關。
  • option 54（Server Identifier）：這台 DHCP 伺服器的身分。客戶端在 REQUEST 裡就是複製這個值來宣告「我選這一家」；續約時也是拿它當單播目的位址。

如果同時有兩台伺服器發 OFFER，客戶端會收到兩個 OFFER（xid 相同、yiaddr 不同、option 54 不同）。 RFC 沒有規定選哪一個——多數實作是「先到先選」。這也是為什麼網路上多一台流氓 DHCP 伺服器（rogue DHCP server）會造成隨機性的災難：誰快誰贏。

客戶端收到 ACK 之後才做這幾件事：

  1. 記錄租約起算時間 = 收到 ACK 的那一刻（不是伺服器送出的時刻，DHCP 不同步時鐘）。
  2. 算出 T1、T2 的絕對時間點。
  3. 做 ARP 衝突偵測（下一節）。
  4. 把 IP、遮罩、路由、DNS 真的套用到系統上。
  5. 把租約寫進 lease 檔，供下次開機直接 INIT-REBOOT 用。

十、拿到 ACK 之後客戶端做了什麼

協定沒有結束在 ACK。RFC 2131 要求客戶端在套用位址前先確認沒有別人在用它：

10.1 ARP probe（衝突偵測）

客戶端送出一個特殊的 ARP（Address Resolution Protocol，位址解析協定）請求：

ARP Request
  sender MAC = 3c:58:c2:4a:1b:7e
  sender IP  = 0.0.0.0            ← 刻意填 0，因為我還沒真的擁有這個 IP
  target IP  = 192.168.1.151      ← 我要問的，就是我即將使用的位址

sender IP 填 0.0.0.0 是重點：如果填 192.168.1.151，就會污染別人的 ARP 快取，萬一真的有衝突反而把對方的連線弄壞。填 0 的 ARP 只問不宣告。

  • 沒人回應 → 這個位址沒被佔用，可以用。
  • 有人回應 → 有人已經在用了（通常是有人設了靜態 IP 撞進 DHCP 位址池）。客戶端必須送 DHCPDECLINE 給伺服器，然後回到 INIT 狀態重跑整個 DORA。伺服器收到 DECLINE 會把這個位址標記成有問題、暫時不再發放。

10.2 Gratuitous ARP（無償 ARP）

確認沒衝突之後，客戶端會廣播一則「無償 ARP」：sender IP 和 target IP 都填 192.168.1.151。沒人需要回答，目的是主動更新整個網段的 ARP 快取，讓大家知道這個 IP 現在對應到我的 MAC。換機器接手同一個 IP 時，這一則廣播能讓別人不必等 ARP 快取逾時。

10.3 套用到系統上

Linux 上這一步的成果，就是 確認網路介面是否使用DHCP 裡看到的那些痕跡：

DHCP 帶來的東西 在系統上呈現成
yiaddr + option 1（遮罩） ip addr 的 inet 192.168.1.151/24 加上 dynamic 旗標
option 51（租約） valid_lft 的有限秒數（靜態 IP 是 forever）
option 3（router） ip route 裡的 default via 192.168.1.1 ... proto dhcp
option 6（DNS） resolvectl status 裡該介面的 DNS Servers
option 121 額外的靜態路由，同樣標 proto dhcp

「proto dhcp」這個標記就是核心在說：這條路由是 DHCP 客戶端寫進去的。

十一、租約生命週期與續約封包

租約不是拿到就永久有效。三個時間點：

收到 ACK                T1 = 50%              T2 = 87.5%          租約到期
   |                     |                       |                    |
   |<---- BOUND -------->|<--- RENEWING ------->|<-- REBINDING ----->|
   0                  21600s                 37800s              43200s
                          |                       |                    |
              單播 REQUEST 給原伺服器    廣播 REQUEST 給任何伺服器   放棄位址
              失敗就繼續重試到 T2        失敗就重試到到期          回到 INIT 重跑 DORA

為什麼要分兩階段？ 這是一個很優雅的降級（graceful degradation）設計：

  • T1 到 T2（RENEWING）：先假設「原本那台伺服器還在，只是我該去續了」，用單播去問，不打擾網段上其他機器。這時候租約還有一半可用，慢慢試沒關係。
  • T2 之後（REBINDING）：既然原伺服器一直不回應，可能它掛了或被換掉了，改成廣播，讓網段上任何一台 DHCP 伺服器都有機會接手。
  • 到期：必須立刻放棄位址、拆掉路由，回到 INIT 從 DISCOVER 重來。這是協定裡少數強制的動作——不能繼續用過期的位址。

如果租約中途成功續約，計時全部歸零重算。 正常運作的網路，客戶端每過租約的一半就續一次，永遠不會走到 REBINDING，所以抓包時看到 REBINDING 就代表 DHCP 伺服器出過問題。

跟第八節那個 REQUEST 對照，四個決定性差異：

欄位 SELECTING 的 REQUEST RENEWING 的 REQUEST
目的 MAC（0x00） ff ff ff ff ff ff 廣播 74 da 88 9f 02 10 單播給伺服器
來源／目的 IP 0.0.0.0 → 255.255.255.255 c0 a8 01 97 → c0 a8 01 01，即 192.168.1.151 → 192.168.1.1

xid（0x2e） 3d 1a 7f 56 7c 04 e9 12——新的一輪交易，換新編號

沒有 option 50 和 54，是因為兩者的資訊都已經隱含在封包裡了：想要哪個位址？就是 ciaddr 這個我正在用的。要問誰？就是這個單播封包的目的位址。

xid 換新的：xid 的作用範圍是「一輪交易」，DORA 是一輪，每次續約是新的一輪。不要誤以為 xid 是整個租約的識別碼。

伺服器同意續約，就回一個 ACK（單播），租約計時重新開始。

NAK 有幾個獨特之處：

特徵 值 為什麼
目的位址 廣播 ff:ff:... / 255.255.255.255 因為 NAK 的意思就是「你那個位址是無效的」，所以不能拿那個無效位址當目的位址送過去

客戶端收到 NAK 的反應是強制的：立刻拆掉現有 IP 設定，回到 INIT 狀態重跑 DORA。 「筆電從公司帶回家，一開蓋網路斷一下才會通」——那一下就是 NAK 加上重跑 DORA。

十二、其他訊息類型

DORA 之外還有四種訊息，都是短命但關鍵的角色：

DHCPDECLINE（option 53 = 4）

時機：客戶端在 ARP probe 時發現要給它的位址已經有人在用。 內容：option 50 填那個有問題的位址，option 54 填那台伺服器。廣播送出。 後果：伺服器把該位址標記為「有問題」並保留一段時間不發放；客戶端等 10 秒後重跑 DORA。 排查價值：抓包看到 DECLINE，就是「位址池跟某台靜態 IP 撞了」的鐵證。

DHCPRELEASE（option 53 = 7）

時機：客戶端主動放棄租約（dhclient -r、正常關機、nmcli con down）。 內容：ciaddr 填自己正在用的位址、option 54 填伺服器，單播送給伺服器。 注意：RELEASE 沒有回覆——是 UDP 單向通知，送出去就算數。所以它不可靠，封包掉了伺服器就不知道你走了，那個位址會一直保留到租約自然到期。 這也是為什麼路由器上常看到一堆已經不在的裝置還佔著位址。

DHCPINFORM（option 53 = 8）

時機：機器已經有靜態 IP，但想跟 DHCP 伺服器要其他參數（DNS、WPAD proxy 設定等）。 內容：ciaddr 填自己的靜態 IP，option 55 列出想要的參數，不含 option 50/51。 回覆：伺服器回 ACK，但不含 option 51（租約時間）——因為沒有位址被租出去，沒有租約可言。 判別技巧：看到一個 ACK 沒有 option 51，八成是在回應 INFORM。

對照：DHCPv6 完全是另一套

DHCPv4 DHCPv6（RFC 8415）
埠 67 / 68 547 / 546
定址 廣播 255.255.255.255 多播 ff02::1:2（All_DHCP_Relay_Agents_and_Servers）
四步名稱 DISCOVER / OFFER / REQUEST / ACK SOLICIT / ADVERTISE / REQUEST / REPLY
客戶端身分 MAC（chaddr） DUID（DHCP Unique Identifier，跨網卡穩定的識別碼）

是否必要 幾乎必要 常常不需要——IPv6 可以只用 SLAAC（Stateless Address Autoconfiguration，無狀態位址自動設定）靠路由器通告（RA）自己算出位址

IPv6 環境最容易踩的坑：位址是 RA 給的、DNS 可能是 DHCPv6 給的，兩套機制同時在跑。「IPv6 有位址但 DNS 不對」通常就是 RA 的 M／O 旗標設定跟 DHCPv6 伺服器不一致。

十三、跨網段：DHCP Relay 與 giaddr

DHCP 全靠廣播，而廣播不跨路由器。那企業裡幾十個 VLAN 難道要放幾十台 DHCP 伺服器？不用——用 DHCP relay agent（中繼代理，也叫 IP helper）。

客戶端                      路由器/L3 交換器                  DHCP 伺服器
(VLAN 20)                   (relay, 10.20.0.1)               10.0.0.5
   |                              |                              |
   | DISCOVER                     |                              |
   | 廣播, src 0.0.0.0            |                              |
   |----------------------------->|                              |
   |                              | DISCOVER                     |
   |                              | 單播, src 10.20.0.1           |
   |                              | dst 10.0.0.5                 |
   |                              | giaddr = 10.20.0.1  ★        |
   |                              | hops = 1                     |
   |                              |----------------------------->|
   |                              |                              |
   |                              |            OFFER (單播回 relay)|
   |                              |<-----------------------------|
   |          OFFER               |                              |
   |   (relay 依 giaddr 判斷該從哪個介面送出，還原成廣播/單播)      |
   |<-----------------------------|                              |

Relay 做了三件事：

  1. 改寫外殼：把廣播改成單播給設定好的伺服器位址，來源 IP 換成自己的。
  2. 填 giaddr：填入自己面向客戶端那一側的介面 IP。這是整個機制的核心。
  3. hops + 1：防迴圈。

giaddr 一個欄位同時承擔兩個任務：

  • 告訴伺服器該從哪個位址池挑位址。伺服器看到 giaddr = 10.20.0.1，就知道「這台客戶端在 10.20.0.0/24 這個網段」，於是從那個 scope 撈位址。 沒有 giaddr，跨網段的 DHCP 根本不可能運作——伺服器完全沒有別的線索知道客戶端在哪。
  • 告訴伺服器回覆要送去哪裡。伺服器把 OFFER／ACK 單播回 giaddr，由 relay 負責送到客戶端。

順帶一提 option 82（Relay Agent Information）：relay 可以額外塞進「這個請求是從哪台交換器的哪個埠進來的」，伺服器可以據此發放固定位址或做存取控制。企業網路的「這個網路孔只能給這台機器用」通常就是靠它。

排查關鍵：跨網段的 DHCP 出問題時，先在伺服器端抓包看 giaddr。

  • giaddr 是 0 → relay 沒設定或沒生效（路由器上少了 ip helper-address）。
  • giaddr 有值但伺服器沒回 → 伺服器上沒有對應那個網段的 scope。
  • 伺服器有回但客戶端沒收到 → relay 的回程路徑或防火牆有問題。

十五、常見誤解與陷阱

誤解一：「OFFER 就代表我拿到 IP 了」 不是。OFFER 只是報價。伺服器多半會暫時保留，但協定沒有規定它必須保留。租約成立的唯一時刻是客戶端收到 ACK。

誤解二：「siaddr 是 DHCP 伺服器的位址」 不是。siaddr 是 PXE 網路開機的「下一台伺服器」，跟 DHCP 身分無關，一般情況都是 0。伺服器身分永遠看 option 54。

誤解三：「REQUEST 應該單播給選中的伺服器」 DORA 裡的 REQUEST 必須廣播，這樣落選的伺服器才知道要把保留的位址放回去。只有續約（RENEWING）的 REQUEST 才是單播。

誤解四：「租約到期前客戶端會被通知」 不會。DHCP 沒有伺服器主動推送的機制，全部由客戶端計時、客戶端主動發起。伺服器完全是被動的。這也是為什麼改了 DHCP 設定（例如換 DNS）不會立刻生效—— 要等客戶端下次續約，或手動觸發。

誤解五：「同一台機器一定拿到同一個 IP」 不保證。多數伺服器會盡量把舊位址發回給同一個 MAC（affinity），但那是實作善意。要保證就得在伺服器上做 DHCP reservation（依 MAC 綁定固定位址）。注意：reservation 仍然是 DHCP，客戶端還是照跑 DORA、還是有租約，所以在客戶端上看起來仍然是 dynamic + 有限的 valid_lft。

誤解六：「MAC 隨機化不影響 DHCP」 影響很大。現代手機和筆電預設對每個 Wi-Fi SSID 用不同的隨機 MAC（randomized MAC）。因為 DHCP 的身分就是 MAC，換了 MAC 就是一台全新的機器：拿到新 IP、之前的 reservation 全部失效、位址池被吃光的速度變快。「我明明綁了 MAC 但手機還是拿到別的 IP」——先去手機的 Wi-Fi 設定關掉隨機 MAC。

誤解七：「DHCP 有身分驗證」 沒有。DHCP 完全沒有認證機制，這是它最大的安全弱點：

  • Rogue DHCP server：任何人接上網段就能發 IP，把 gateway 指向自己做中間人攻擊。防禦手段是交換器上的 DHCP snooping（只信任特定埠來的 OFFER／ACK）。
  • DHCP starvation：攻擊者偽造大量不同的 chaddr 狂送 DISCOVER，把位址池吃光，讓正常裝置拿不到 IP。防禦是交換器的 port security（限制每埠的 MAC 數量）。

陷阱八：容器與虛擬機的橋接 Docker 的 docker0 是自己配位址的，不走 DHCP（所以它的 valid_lft 是 forever）。但橋接模式的虛擬機會直接向實體網段的 DHCP 伺服器要位址，在位址池小的家用網路很容易把位址用光。

十六、自我測驗

  1. DORA 的第三步 REQUEST，客戶端明明已經從 OFFER 裡知道伺服器 IP 是 192.168.1.1 了，為什麼還要用廣播送、來源 IP 還填 0.0.0.0？兩個原因分別是什麼？
  2. 你抓到一個 option 53 = 3 的 REQUEST，ciaddr 是 0.0.0.0，有 option 50 但沒有 option 54，而且是廣播送出的。這台客戶端處在什麼狀態、剛剛發生了什麼事？如果 ciaddr 改成有值、而且是單播送出的，結論又變成什麼？
  3. 為什麼 DHCP 要把客戶端的 MAC 位址放進 chaddr 這個應用層欄位裡，而不是直接用乙太網路標頭的來源 MAC 就好？講出至少兩個乙太網路標頭不夠用的場合。
  4. siaddr 和 option 54 都是「一個 IP 位址」，很容易被當成同一件事。它們各自代表什麼？如果一台伺服器把 option 54 填錯成別人的位址，客戶端的續約會發生什麼事？
  5. 情境題：使用者回報「筆電在公司好好的，帶回家連家裡 Wi-Fi 要等十幾秒、而且中間網路圖示閃一下才通」。你抓包，發現一開始有一個 REQUEST，緊接著一個伺服器回的封包，然後才開始跑完整的 DORA。那個中間的封包最可能是哪一種訊息？它的哪個 option 能直接告訴你原因？整件事的機制是什麼？
  6. 情境題：某個網段裡有幾台機器「拿到 IP 後幾秒鐘又重新開始跑 DORA」，循環不斷。抓包發現每次 ACK 之後客戶端都送出一個 option 53 = 4 的封包。根因是什麼？你會怎麼縮小範圍找到那台肇事機器？
  7. 情境題：你把 DHCP 伺服器上的 DNS 從 192.168.1.1 改成 1.1.1.1，租約設定是 24 小時。改完之後有些機器立刻生效、有些過了大半天才變、有些重開機就好了。用租約狀態機解釋這三種行為，並說明為什麼「改了 DHCP 設定不會立刻全網生效」是協定設計的必然結果，而不是伺服器的 bug。
