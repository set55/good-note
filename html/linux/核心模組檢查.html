Linux 核心模組（kernel module）的查看與排查

日期：2026-07-25
環境：Ubuntu（HWE，Hardware Enablement，硬體支援堆疊）、核心 7.0.0-28-generic、NVIDIA + DKMS（Dynamic Kernel Module Support，動態核心模組支援）
用途：搞清楚「這個模組到底裝了沒／載入了沒／是誰裝的」，以及驅動沒作用時的排查順序

一、核心觀念：「安裝」有三層

同一個模組可以同時處在不同狀態，混淆這三層是排查時最常見的坑。

層次 意思 存在何處 查法
L3 載入中 已進核心記憶體，正在運作 /proc/modules lsmod
L2 檔案就位 .ko 檔在磁碟上，可被載入 /lib/modules/$(uname -r)/ modinfo / modprobe -n
L1 套件提供 由 dpkg 或 DKMS 佈署到 L2 dpkg 資料庫 / /var/lib/dkms dpkg -S / dkms status

lsmod 沒看到 ≠ 沒安裝。 兩種常見誤判：

  • 功能被編進核心（.config 裡是 =y 而非 =m）→ 根本不會出現在 lsmod
  • 模組存在但沒被觸發載入（沒有對應硬體、沒有程序需要它）

L1 → L2 → L3 是佈署方向；排查時通常反過來由 L3 往回追。

參見 dpkg與dkms的關係：L1 這層有兩套機制，dpkg 管 in-tree 模組，DKMS 管第三方模組。

二、L3：查看已載入的模組

lsmod                 # 目前載入的所有模組
lsmod | grep nvidia
cat /proc/modules     # lsmod 的原始資料來源，欄位更多

lsmod 三個欄位都要會讀：

Module              Size  Used by
usb_storage        86016  1 uas          ← refcount=1，被 uas 使用中
uas                32768  2              ← refcount=2，卸載不掉
bridge            421888  0 
stp                12288  1 bridge       ← bridge 依賴我
llc                16384  2 bridge,stp

怎麼看：

  • Used by 的數字就是 refcount，非 0 時 rmmod 一定失敗。
  • 數字後面的名字是「誰依賴我」——方向是反的。stp 那行代表 bridge 需要 stp，不是 stp 需要 bridge。要看「我依賴誰」得用 modinfo 的 depends:。
  • bridge 的 0 表示沒人用，可以直接 rmmod。

/proc/modules 多出的欄位裡，Live / Loading / Unloading 是模組狀態，卡在 Unloading 通常代表有 refcount 洩漏。

三、L2：查看模組檔案本身

modinfo nvidia                    # 最重要的單一命令
modprobe -n -v nvidia             # dry-run：只印「會載入哪些」，不真的載入
modprobe --show-depends nvidia    # 只列依賴鏈

實際輸出（本機 nvidia）：

filename:  /lib/modules/7.0.0-28-generic/updates/dkms/nvidia.ko.zst
version:   580.173.02
vermagic:  7.0.0-28-generic SMP preempt mod_unload modversions
signer:    set-Vector-17-HX-A14VFG Secure Boot Module Signature key

怎麼看，四個關鍵欄位：

filename: —— 判斷模組來源最快的方法

路徑片段 意義
/lib/modules/<kernel>/kernel/... 核心套件自帶（in-tree），由 dpkg 佈署
/lib/modules/<kernel>/updates/dkms/... DKMS 為這顆核心現場編譯的（out-of-tree）

看到 updates/dkms/ 就知道：換核心後這支要重編，出事要查 dkms status。

vermagic: —— 換核心後驅動失效的根本原因

模組編譯時綁定的核心版本與設定指紋。與執行中核心不符時，載入會失敗：

insmod: ERROR: could not insert module: Invalid module format
# dmesg 會補上真正原因：
# module: version magic '6.17.0-35-generic ...' should be '7.0.0-28-generic ...'

Invalid module format 本身沒有資訊量，一定要去 dmesg 看 version magic 的比對結果。

depends: —— modprobe 與 insmod 的分水嶺

$ modinfo bridge | grep depends
depends:  stp,llc

modprobe 會依這行遞迴載入依賴，insmod 不會。日常一律用 modprobe，insmod 只在測試單一 .ko 檔時才用。

intree: —— 是否為官方核心樹內模組

N（或缺此欄）會讓核心被標記 taint，cat /proc/sys/kernel/tainted 非 0。回報 bug 給上游時，taint 過的核心通常不受理。

查看模組可調參數

modinfo -p <mod>                          # 模組「宣告」了哪些參數（讀 .ko 內的靜態描述）
ls /sys/module/<mod>/parameters/          # 執行時「可讀」的參數 ← 不一定存在，見下
sudo cat /sys/module/<mod>/parameters/<p>  # 目前實際生效值

/sys/module/<mod>/parameters/ 是執行時的真實值，比翻設定檔可靠——設定檔改了但沒重新載入模組時，兩者會不一致。

坑一：parameters/ 目錄不一定存在

這個目錄只在該模組至少有一個參數宣告了非零 sysfs 權限時才會被建立。 模組原始碼裡：

module_param(foo, int, 0444);   // 第三個參數是 sysfs 權限 → 會出現在 /sys
module_param(bar, int, 0);      // 權限 0 → 不建立節點，/sys 裡完全看不到

所以 modinfo -p 列得出來 ≠ /sys 讀得到。本機實例：

模組 modinfo -p /sys/module/<m>/parameters/
nvidia 48 個 無此目錄（全部宣告為權限 0）
nvidia_drm — 有，2 個（modeset、fbdev）
nvidia_modeset — 有，14 個
nvidia_uvm — 有，53 個

NVIDIA 的替代查法是它自己的 proc 介面，48 個參數的實際生效值都在這裡，且免 sudo：

cat /proc/driver/nvidia/params

ResmanDebugLevel: 4294967295
RmLogonRC: 1
ModifyDeviceFiles: 1
...

注意兩個介面的參數名不一樣——modinfo 有 NVreg_ 前綴，proc 沒有：

$ modinfo -p nvidia | grep -c '^NVreg_'          # 45 個有前綴
$ grep -c '^NVreg_' /proc/driver/nvidia/params   # 0 個

原因是驅動用 module_param_named(NVreg_Foo, Foo, ...) 註冊：modprobe 選項名是 NVreg_Foo，proc 印的是內部變數名 Foo。

實務影響：/etc/modprobe.d/ 裡要寫帶前綴的 NVreg_*，但去 proc 查值時要用不帶前綴的名字。 用 modinfo 的名字去 grep proc 會一無所獲。

通則：/sys 沒有時，先看該驅動有沒有自己的 /proc/driver/<name>/ 或 /sys/class/ 介面。

這個位置是怎麼找出來的（不靠既有知識）、以及「東西不在該在的地方」的通用找法，見 排查方法論——本例是該篇的完整實例。

坑二：權限多半是 0400

$ ls -l /sys/module/nvidia_drm/parameters/
-r-------- 1 root root 4096 ... fbdev
-r-------- 1 root root 4096 ... modeset

一般使用者 cat 會 Permission denied，要加 sudo。權限若是 0644 則可直接寫入即時調整（少數模組支援），0444 則是唯讀、只能重新載入模組才能改。

四、L1：這個模組是誰裝的

# in-tree：查檔案屬於哪個 deb
dpkg -S /lib/modules/7.0.0-28-generic/kernel/net/bridge/bridge.ko.zst
# → linux-modules-7.0.0-28-generic: /lib/modules/...

# out-of-tree：查 DKMS
dkms status

實際輸出：

nvidia/580.173.02,            7.0.0-28-generic,  x86_64: installed
ovpn-dco/0.2.20260526-1+26.1, 6.17.0-35-generic, x86_64: installed
ovpn-dco/0.2.20260526-1+26.1, 7.0.0-28-generic,  x86_64: installed

格式是 模組/版本, 目標核心, 架構: 狀態。

怎麼看：逐行對照「哪個核心有、哪個沒有」。 上面 ovpn-dco 對兩個核心都有，但 nvidia 只有 7.0.0-28，缺 6.17.0-35 → 若從 grub 選 6.17.0-35 開機，NVIDIA 驅動不會載入（會退到 nouveau 或 llvmpipe，畫面能亮但沒有硬體加速）。

DKMS 狀態語意：

狀態 意思 能不能載入
installed 已編譯並複製到 /lib/modules/<kernel>/updates/dkms/ ✅
built 編好了但沒安裝到目標位置 ❌
added 只有原始碼在 /usr/src/<mod>-<ver>，還沒編 ❌
沒出現該核心 完全沒為那顆核心處理過 ❌

補救：

sudo dkms autoinstall -k 6.17.0-35-generic          # 為指定核心重建
sudo dkms install -m nvidia -v 580.173.02 -k 6.17.0-35-generic   # 指定單一模組

# 失敗時看建置 log，找第一個 error:（後面的多半是連鎖錯誤）
tail -50 /var/lib/dkms/nvidia/580.173.02/build/make.log

前提是 headers 在： ls /usr/src/linux-headers-6.17.0-35-generic，缺了就先 apt install linux-headers-<版本>。

完整的 DKMS 編譯失敗排查見 NVIDIA-DKMS核心升級失敗排查。

五、開機自動載入、參數與黑名單

模組通常由 udev 依偵測到的硬體自動載入，不需要手動設定。人為干預點有三處：

ls /etc/modules-load.d/       # 強制開機載入的模組清單
cat /etc/modules              # 同上，舊式寫法
ls /etc/modprobe.d/           # 參數（options）與黑名單（blacklist）
modprobe -c | less            # 所有設定合併後的最終結果 ← 最可靠

modprobe -c 會把 /etc/modprobe.d/、/lib/modprobe.d/、/run/modprobe.d/ 全部合併輸出。設定沒生效時先看這個，多半是被別的檔案覆蓋了。

options：只在載入的那一刻生效

options nvidia_drm modeset=1
options nvidia NVreg_PreserveVideoMemoryAllocations=1

改完設定檔，模組不重新載入就不會套用：

sudo modprobe -r nvidia_drm && sudo modprobe nvidia_drm
sudo cat /sys/module/nvidia_drm/parameters/modeset      # 驗證（0400，需 sudo）

驗證前先確認 parameters/ 目錄存在——很多模組（含 nvidia 本體）沒有，見第三節「坑一」。

但顯卡、儲存、根檔案系統相關的模組通常被打包進 initramfs，此時光改 /etc/modprobe.d/ 沒用，開機時讀的是 initramfs 裡的舊副本：

sudo update-initramfs -u -k all
lsinitramfs /boot/initrd.img-$(uname -r) | grep nvidia    # 確認有進去

blacklist 的陷阱

blacklist foo 只擋「依 alias 自動載入」，不擋「被其他模組當依賴拉進來」也不擋手動 modprobe foo。要真正封死：

install foo /bin/false

六、硬體與驅動的對應

lspci -k        # PCI（Peripheral Component Interconnect，週邊裝置互連匯流排）裝置 ↔ 驅動（-k 就是顯示 kernel driver）
lsusb -t        # USB（Universal Serial Bus，通用序列匯流排）樹狀結構 ↔ 驅動

實際輸出：

NVIDIA AD107M [RTX 4060 Max-Q]   Kernel driver in use: nvidia
Realtek RTL8125 2.5GbE           Kernel driver in use: r8169
Intel Wi-Fi 7 BE...              Kernel driver in use: iwlwifi
                                 Kernel modules: iwlwifi

怎麼看，兩行的差別是關鍵：

  • Kernel driver in use: —— 實際綁上這個裝置的驅動
  • Kernel modules: —— 系統認為可以用的候選模組

只有 Kernel modules 而沒有 Kernel driver in use，就是「驅動裝了但沒綁上」，這是「明明裝了驅動卻沒作用」的標準診斷點。常見原因：模組載入失敗、被 blacklist、韌體（firmware）缺失、或另一支驅動搶先綁走了。

七、Secure Boot 與模組簽章

modinfo 若出現這幾行，表示模組經過簽章：

sig_id:       PKCS#7
signer:       set-Vector-17-HX-A14VFG Secure Boot Module Signature key
sig_hashalgo: sha512

sig_id: PKCS#7（Public-Key Cryptography Standards #7，一種數位簽章封裝格式）是簽章使用的格式標準。 signer 是機器名稱 + Secure Boot Module Signature key → 這是 MOK（Machine Owner Key，機器擁有者金鑰）自簽，Ubuntu 的 DKMS 會自動處理。

mokutil --sb-state              # Secure Boot 是否啟用
mokutil --list-enrolled         # 已註冊的金鑰
cat /proc/sys/kernel/tainted    # 0 = 乾淨

Secure Boot 啟用時，未簽章或簽章不被信任的模組會被拒絕載入，dmesg 訊息：

Loading of unsigned module is rejected
Key was rejected by service

踩坑點：MOK 金鑰重新產生但沒在開機時 enroll（需要在 MOK Manager 藍畫面手動確認一次），DKMS 簽好的模組一樣載不進去。

八、載入與卸載

sudo modprobe bridge          # 自動處理依賴 ← 日常都用這個
sudo modprobe -r bridge       # 卸載，並順帶卸載沒人用的依賴
sudo insmod ./foo.ko          # 直接指定檔案，不處理依賴（測試用）
sudo rmmod bridge             # 只卸這一個

卸載失敗的三種原因，解法完全不同：

訊息 原因 解法
Module xxx is in use refcount 非 0 先停掉使用者（systemctl stop、umount、關掉程序）
Module xxx is builtin 編進核心了，不是模組 只能改核心設定重編
lsmod 顯示 [permanent] 該模組不支援卸載 只能重開機

查 refcount 是誰持有：lsmod | grep <模組> 的 Used by 欄位，或 /sys/module/<mod>/holders/。

九、實戰排查流程

「裝了驅動但硬體沒作用」的標準順序，由外往內、由現象往根源：

# 1. 硬體有沒有綁上驅動（最外層現象）
lspci -k | grep -A3 -i nvidia
#    有 in use → 驅動正常，問題在上層（使用者空間 / 設定）
#    只有 Kernel modules → 繼續往下

# 2. 模組載入了沒
lsmod | grep nvidia

# 3. 檔案在不在、版本對不對
modinfo nvidia | grep -E 'filename|vermagic'
uname -r                              # 跟 vermagic 比對

# 4. 手動載入，看真正的錯誤
sudo modprobe nvidia
sudo dmesg | tail -30                 # ← 真正的原因在這裡

# 5. 若是第三方模組，回到 L1 看 DKMS
dkms status
tail -50 /var/lib/dkms/nvidia/<ver>/build/make.log

兩個心法：

  1. modprobe 的錯誤訊息幾乎沒有資訊量，真正的原因永遠在 dmesg。 養成成對執行的習慣。
  2. dmesg -w（跟隨模式）配合插拔硬體，是觀察 udev 自動載入行為最直接的方法——能看到裝置事件、模組載入、韌體載入的完整時序。

十、附錄：/lib/modules 的孤兒目錄

核心套件移除後，/lib/modules/<版本>/ 目錄不一定會消失。檢查：

cd /lib/modules && for d in */; do k="${d%/}"
  dpkg -l "linux-image-$k" 2>/dev/null | grep -q '^ii' || echo "孤兒 $k  $(du -sh "$k" | cut -f1)"
done

本機結果：24 個目錄，但實際安裝的核心套件只有 linux-image-6.17.0-35-generic 與 linux-image-7.0.0-28-generic 兩個，其餘 22 個是孤兒。

但先別急著刪。 進去看內容：

$ ls -A /lib/modules/6.11.0-17-generic/
modules.alias  modules.alias.bin  modules.builtin.alias.bin  modules.builtin.bin
modules.dep    modules.dep.bin    modules.devname  modules.softdep
modules.symbols  modules.symbols.bin

全是 depmod 產生的索引檔，沒有任何 .ko。 每個約 1.2M，22 個加起來約 26M（/lib/modules 總計 369M）——佔用微不足道，不值得為了空間去刪。

它們的成因：apt autoremove 移除核心套件時，dpkg 只刪自己登記過的檔案，而這些索引是 depmod 在安裝後現場生成的，不在 dpkg 的檔案清單裡，於是留了下來。

真的要清（純粹為了 dkms status / ls 輸出乾淨）：

sudo apt autoremove --purge          # 先讓 apt 有機會自己收尾
sudo rm -rf /lib/modules/6.11.0-17-generic    # 再逐一刪，確認過內容沒有 .ko 才刪

絕對不要動： 執行中的核心（uname -r）與保留的備援核心。刪錯會導致該核心開機後所有模組載入失敗。

完整指令與選項清單

前面各節只挑了排查用得到的。以下是本機 --help 的完整內容（kmod 版），免得你以為那就是全部。

lsmod

沒有任何選項——Usage: lsmod，就這樣。它只是把 /proc/modules 排版印出來，要過濾自己接 grep。

modinfo

選項 作用
-a --author / -d --description / -l --license 只印該欄位
-p --parameters 只印模組參數（有哪些可調的 parm）
-n --filename 只印 .ko 檔路徑 ← 腳本取值常用
-F --field=<欄位> 只印指定欄位（例如 -F vermagic）
-0 --null 用 \0 分隔而非換行
-m --modname 把參數當模組名而非別名或檔名
-k --set-version=<版本> 查另一個核心版本的模組，而不是 uname -r
-b --basedir=<目錄> 換掉 /lib/modules 的根目錄
-V / -h 版本／說明

-k 特別實用：升級核心後、重開機前，先確認新核心底下模組在不在。

modprobe

管理類

選項 作用
-a --all 把每個非選項參數都當模組名處理
-r --remove 移除（含不再需要的相依模組）
--remove-holders 連同持有它的模組一起移除（配 -r）
-w --wait <毫秒> 移除時等 refcount 降到 0（配 -r）
--first-time 已載入／已移除就算失敗（腳本判斷用）
-i --ignore-install / --ignore-remove 忽略設定檔裡的 install／remove 指令
-b --use-blacklist 套用黑名單
-f --force 強制（＝ --force-modversion + --force-vermagic）
--force-modversion 忽略模組符號版本
--force-vermagic 忽略 vermagic 不符 ← 跨核心硬塞，很容易當機

查詢類（不會真的載入，排查好用）

選項 作用
-R --resolve-alias 只解析別名並印出
-D --show-depends 只印相依順序不載入 ← 想知道「載入它會連帶載入誰」
-c --showconfig 印出生效的設定（黑名單、options、install 指令都在裡面）
--show-modversions / --show-exports 符號版本／匯出符號

一般：-n／--dry-run、-v／--verbose、-q／--quiet、-s／--syslog、 -C／--config、-d／--dirname、-S／--set-version、-V、-h。

rmmod

選項 作用
-f --force 強制卸載，可能當機（需核心開啟 Forced Module Removal）
-s --syslog 輸出到 syslog 而非 stderr
-v --verbose 囉嗦模式
-V / -h 版本／說明

多數情況該用 modprobe -r 而不是 rmmod——前者處理相依關係，後者只拔單一模組。

depmod

選項 作用
-a --all 掃描所有模組（預設）
-A --quick 只在有新模組時才做事
-e --errsyms 回報未提供的符號 ← 排查「模組載不起來」很有用
-n --show 只印到 stdout，不寫檔
-C --config=<路徑> / -v / -w（警告重複） / -P（符號前綴）
-b --basedir / -o --outdir / -F --filesyms / -E --symvers 打包發行版用

dkms

dkms 沒有 --help，文法是 dkms [action] [options]：

動作 作用
add / build / install 登記原始碼／對指定核心編譯／安裝
uninstall / remove 反向操作
status 列出各模組對各核心的狀態 ← 最常用
match 把某核心的設定套到另一個核心
autoinstall 對目前核心自動編譯所有已登記模組
mktarball / ldtarball 打包／載入預編譯 tarball
選項 作用
-m <模組> -v <版本> 指定模組與版本（多數動作都要）
-k <核心版本> 指定核心，不給就是目前這個
-a <arch> / -c <dkms.conf> / -j <數字> 架構／設定檔位置／平行編譯數
-q / --verbose 安靜／囉嗦
--force / --force-version-override / --all 強制重做／強制覆蓋版本／套用到所有核心
--binaries-only / --source-only 只處理二進位／只處理原始碼
--no-depmod / --modprobe-on-install 編完不跑 depmod／裝完立刻 modprobe
--kernelsourcedir= / --config= / --archive= / --templatekernel= / --directive='k=v' 進階

速查總表

# L3 載入狀態
lsmod                                  # 已載入模組 + refcount
lsmod | grep <mod>                     # Used by 非 0 → rmmod 必失敗

# L2 檔案資訊
modinfo <mod>                          # filename/vermagic/depends/intree/signer
modinfo -p <mod>                       # 宣告的參數（≠ /sys 讀得到）
ls /sys/module/<mod>/parameters/       # 可讀的參數，權限 0 宣告的不會出現
sudo cat /sys/module/<mod>/parameters/<p>   # 執行時實際值（多為 0400）
cat /proc/driver/nvidia/params         # nvidia 專用替代介面
modprobe -n -v <mod>                   # dry-run 看依賴鏈

# L1 來源
dpkg -S <ko檔路徑>                      # in-tree 屬於哪個套件
dkms status                            # out-of-tree 對各核心的建置狀態

# 設定
modprobe -c | less                     # 所有 modprobe 設定的合併結果
ls /etc/modprobe.d/ /etc/modules-load.d/

# 硬體對應
lspci -k                               # in use vs Kernel modules 的差別是關鍵

# 簽章
mokutil --sb-state
cat /proc/sys/kernel/tainted           # 0 = 乾淨

# 操作
sudo modprobe <mod> && sudo dmesg | tail -30   # 一定要配 dmesg
sudo modprobe -r <mod>
sudo update-initramfs -u -k all        # 改了 initramfs 內模組的設定後必做
