./oob; echo "exit=$?" 在做什麼？—— 命令串接、結束狀態與 $?

課程：Linux 與系統程式系統化學習｜第 ① 站第 3 課・延伸提問
日期：2026-09-28
情境：第 ① 站第 3 課的延伸提問。陣列、字串與指標運算 第五節每個實驗都用 ./oob; echo "exit=$?" 執行，使用者問這個語法是什麼意思。
適用範圍：本機 Ubuntu 24.04，bash 5.2.21、zsh 5.9（使用者的登入 shell 是 zsh）。以下輸出都是本機實測，兩個 shell 結果不同的地方會分開列。
實驗檔案：放在 Claude 的 scratchpad，完整原始碼都附在下面，不入 git。

一句話結論：這是兩個命令。; 讓第二個命令不管第一個成功或失敗都會執行；$? 是「上一個命令」的結束狀態（exit status），每跑一個命令就被覆蓋一次，所以 echo 必須緊接在要觀察的程式後面。

一、逐段拆解

./oob   ;   echo   "exit=$?"
└─┬─┘   │   └─┬┘   └───┬───┘
命令 1  串接  命令 2   命令 2 的參數（一個字串）
片段 是什麼 誰處理 詳見
./oob 執行目前目錄裡叫 oob 的檔案 shell 找檔案，核心 execve 執行 第二節
; 命令分隔符號：前一個跑完，不論成敗都接著跑下一個 shell 第四節
echo shell 內建命令，把參數印出來、最後加換行 shell 本身（不是外部程式） 第七節
"..." 雙引號：裡面的 $ 仍會展開，但整段算一個參數 shell 第六節
$? 特殊參數：上一個前景命令的結束狀態 shell 在執行 echo 之前就換成數字 第三、五節

shell 讀到這一行時的順序：

  1. 看到 ;，知道這是兩個命令，先執行 ./oob，等它結束，記下它的結束狀態。
  2. 準備執行 echo 時先做展開："exit=$?" 裡的 $? 換成剛剛記下的數字，例如 exit=0。
  3. 執行 echo exit=0，印出來。

所以 echo 看到的從來不是 $? 這兩個字元，而是已經換好的數字。

二、./：為什麼不能只打 oob

只打一個名字（不含 /）時，shell 會依序到 PATH 這個環境變數列出的目錄去找，不會找目前目錄。本機的 PATH（節錄）：

$ echo "$PATH" | tr ':' '\n'
/home/set/.nvm/versions/node/v24.14.0/bin
...
/usr/local/bin
/usr/sbin
/usr/bin
/sbin
/bin
...

裡面沒有 .（目前目錄）。所以要執行剛編出來的程式，就得寫出路徑。./oob 的 . 是「目前目錄」，/ 是路徑分隔，名字裡只要有 /，shell 就不查 PATH，直接拿這個路徑去執行。

不把 . 放進 PATH 是刻意的安全設計：否則別人在某個目錄放一個叫 ls 的惡意程式，你一 cd 進去打 ls 就中招。

少打 ./ 的下場（實測，ret 是第三節的程式，在目前目錄裡）：

$ ret 1; echo "exit=$?"
bash: ret: command not found                   ← bash（互動）的訊息
zsh: command not found: ret                    ← zsh（互動）的訊息
exit=127                                       ← 兩個 shell 都是 127

127 是 shell 保留的值，代表「找不到命令」（第八節）。

三、結束狀態：0～255 這個數字從哪來

程式自己決定：return 或 exit() 的值

main 的 return n（或呼叫 exit(n)）就是把 n 交給核心，父行程（這裡是 shell）用 waitpid 系統呼叫拿回來。慣例是 0 代表成功，非 0 代表失敗——跟 C 的「0 是假」剛好相反，因為成功只有一種、失敗可以有很多種原因要分辨。

用一個「把第一個參數當結束狀態」的小程式實測。ret.c 完整原始碼：

#include <stdlib.h>

int main(int argc, char *argv[])
{
    if (argc < 2)
        return 0;
    return atoi(argv[1]);      /* 用第一個參數當結束狀態 */
}

$ gcc -Wall -Wextra -o ret ret.c
$ ./ret 3;   echo "exit=$?"
exit=3
$ ./ret 256; echo "exit=$?"
exit=0          ← 不是 256
$ ./ret 300; echo "exit=$?"
exit=44         ← 不是 300
$ ./ret -1;  echo "exit=$?"
exit=255        ← 不是 -1

（bash、zsh 結果完全相同。）

結束狀態只有 8 bit：main 回傳的 int 被截斷成最低的 1 個 byte，再當成無號數讀—— 正是第 2 課第六節〈變窄（截斷，truncation）〉的規則：

回傳值 十六進位 留下最低 1 byte 用無號讀
256 0x00000100 0x00 0
300 0x0000012c 0x2c 44
−1 0xffffffff 0xff 255

所以 return 256; 會被當成「成功」——程式要回報錯誤，一律用 1～125 之間的值。

被訊號殺掉：shell 設成 128 + 訊號編號

程式如果被訊號（signal）終止，它根本沒有執行到 return，也就沒有自己的結束狀態。這時 shell 用 128 + 訊號編號 代替（第 3 課〈結束狀態 139 和 134 是什麼〉）。 crash.c 完整原始碼：

int main(void)
{
    int *p = 0;
    return *p;                 /* 讀位址 0：segfault */
}

$ gcc -o crash crash.c
$ ./crash; echo "exit=$?"
exit=139                       ← 128 + 11（SIGSEGV）

那行 Segmentation fault (core dumped) 是誰印的？不是程式（它已經死了），是 shell 發現子行程被訊號殺掉後自己印的，兩個 shell 的措辭不同：

bash（互動）：Segmentation fault (core dumped)
zsh （互動）：zsh: segmentation fault (core dumped)  ./crash

實測發現：zsh 以非互動方式執行（zsh -c '...'、腳本）時不印這一行，只剩 exit=139；bash 在 bash -c 下仍然會印。所以看不到錯誤訊息不代表程式沒當掉——$? 才是可靠的判斷依據，這也是第 3 課每個實驗都要 echo "exit=$?" 的原因。

四、; 與其他串接命令的方式（完整清單）

man bash 的〈Lists〉一節：串接用的運算子只有 ;、&、&&、|| 四個，外加換行（等同 ;）。

寫法 名稱 意思 整串的結束狀態
A ; B 循序（sequential） 等 A 結束，不論成敗都跑 B 最後跑的那個（B）
A（換行）B 同上 換行和 ; 完全一樣 同上
A && B AND 串列 A 成功（狀態 0）才跑 B 最後實際跑的那個
A || B OR 串列 A 失敗（狀態非 0）才跑 B 最後實際跑的那個
A & B 非同步（asynchronous） A 丟到背景，不等它就跑 B A & 本身永遠是 0

zsh 另外多兩個：A &| 和 A &!，都是「丟到背景，而且立刻跟 shell 脫鉤（disown）」（man zshmisc 的〈SIMPLE COMMANDS & PIPELINES〉）。

實測（ret 見第三節；bash、zsh 輸出相同）：

$ ./ret 1 ; echo "分號：上一個是 $?"
分號：上一個是 1
$ ./ret 1 && echo "&&：不會印"                   ← 沒有輸出
$ ./ret 0 && echo "&&：上一個成功才印"
&&：上一個成功才印
$ ./ret 1 || echo "||：上一個失敗才印"
||：上一個失敗才印
$ ./ret 0 || echo "||：不會印"                   ← 沒有輸出

第 3 課為什麼用 ;，不用 &&？ 實驗的目的就是看程式失敗時的結束狀態。寫成 ./oob && echo "exit=$?"，只要 oob 當掉（139），echo 根本不會執行，什麼都看不到。

優先順序：&& 和 || 同級、由左往右結合；; 和 & 同級、比它們低。所以 A && B || C 是 (A && B) || C—— B 失敗時 C 也會跑，不是「A 成功跑 B、否則跑 C」的三元式：

$ ./ret 0 && ./ret 1 || echo "C 被執行了"
C 被執行了                                         ← A 成功，但 B 失敗，所以 C 也跑了

這個陷阱在 shell條件判斷測試〈陷阱：&& 後面那段自己失敗時，|| 也會跑〉有完整說明。

管線 | 不是串接，但 $? 會受它影響

A | B 把 A 的輸出接到 B 的輸入，兩個同時執行（見 輸出重新導向與dev-null）。它不屬於上面的串列運算子，而是更小的單位「管線（pipeline）」：串列是由管線串成的。相關符號也全部列出：

寫法 意思
A | B A 的 stdout 接到 B 的 stdin
A |& B 等於 A 2>&1 | B，stdout 和 stderr 都接過去（bash、zsh 都有）
! A 把管線的結束狀態反轉：0 變 1，非 0 變 0

管線的結束狀態是最後一個命令的，見第五節。

五、$?：只記得上一個命令

每跑一個命令就被覆蓋

$ ./ret 7; echo hi; echo "看到的是 $?"
hi
看到的是 0                     ← 是 echo hi 的狀態，不是 ret 的 7
$ ./ret 7; rc=$?; echo hi; echo "存起來的 rc=$rc"
hi
存起來的 rc=7                  ← 先存進變數，之後怎麼跑都不會變

echo 本身也是命令，它成功執行完，$? 就變成 0。要在好幾個命令之後還用得到，就要立刻存起來：rc=$?。

背景命令：$? 是 0，要用 wait 拿

$ ./ret 3 & echo "背景：\$? 立刻是 $?"; wait $!; echo "wait 之後 $?"
背景：$? 立刻是 0              ← 「成功把它丟到背景」的狀態
wait 之後 3                    ← wait 等它結束，把它的狀態當成自己的

（$! 是最近一個背景工作的行程 ID，見下表。）

管線：只看最後一個命令

$ ./crash | tee log.txt; echo "exit=$?"
exit=0                         ← crash 明明 segfault 了，但 tee 成功

管線中間的程式當掉，$? 看不出來。三種補救（本機實測）：

方法 bash zsh 輸出
看每一段的狀態 ${PIPESTATUS[*]} ${pipestatus[*]}（小寫） 139 0
讓管線「有一段失敗就算失敗」 set -o pipefail setopt pipefail $? 變成 3（用 ./ret 3 | ./ret 0 實測）

PIPESTATUS／pipestatus 一樣會被下一個命令覆蓋，要馬上讀。

zsh 的 $status

zsh 另有 $status，跟 $? 完全一樣（./ret 9; echo $status 印 9）；bash 沒有這個變數（印出空字串）。可攜的寫法一律用 $?，因為所有 POSIX shell（含 dash、BusyBox ash）都有。

$? 是 shell 的「特殊參數」之一：完整清單

man bash 的〈Special Parameters〉一共 8 個，只能讀、不能賦值：

參數 展開成 例子
$? 最近一個前景管線的結束狀態 本篇主角
$# 位置參數（腳本或函式收到的參數）個數 見 shell條件判斷測試 第九節〈九、實例拆解：[ $# -eq 0 ]——「有沒有給參數」〉
$* 全部位置參數；在雙引號裡合成一個字串（用 IFS 第一個字元隔開） "$*" → "a b c"
$@ 全部位置參數；在雙引號裡每個參數各自一個字串 "$@" → "a" "b" "c"，傳遞參數時用這個
$- 目前開啟的 shell 選項旗標 互動 shell 會含 i
$$ 這個 shell 的行程 ID（在子 shell 裡仍是原本 shell 的） 產生暫存檔名
$! 最近一個丟到背景的工作的行程 ID 上面的 wait $!
$0 shell 或腳本的名字 腳本裡印出自己的檔名

（$1、$2… 是位置參數，不在這 8 個裡。bash 5.2 把 $_ 歸在〈Shell Variables〉而不是特殊參數。 zsh 有同樣這 8 個，另外還有 $status、$pipestatus 等數十個 shell 自動設定的參數，完整清單見 man zshparam 的〈PARAMETERS SET BY THE SHELL〉。）

六、雙引號：為什麼寫成 "exit=$?"

三種寫法實測（前一個命令是 ./ret 5；bash、zsh 輸出相同）：

$ ./ret 5; echo "exit=$?"
exit=5            ← 雙引號：$ 照樣展開
$ ./ret 5; echo 'exit=$?'
exit=$?           ← 單引號：什麼都不展開，原樣印出
$ ./ret 5; echo exit=$?
exit=5            ← 不加引號：這裡也對，因為展開結果沒有空白
  • 單引號裡的東西一律是字面，$? 不會被換掉，所以要用雙引號。
  • 不加引號這裡也能跑，但養成加雙引號的習慣：展開結果如果含空白或 *，不加引號時會被拆成多個參數、或被當成檔名樣式展開。原因與實例見 錢字號展開的四種形式 第六節；雙引號擋不住哪些展開見同篇第四節。
  • exit= 只是給人看的標籤，沒有任何特殊意義，寫成 "狀態：$?" 也一樣。

七、echo：完整選項，以及 bash 與 zsh 的差別

echo 有兩個：shell 內建的，和 coreutils 的外部程式 /usr/bin/echo。打 echo 時用的是內建的：

$ type -a echo          （bash）
echo is a shell builtin
echo is /usr/bin/echo
echo is /bin/echo

文法：echo [-neE] [參數 ...]——把所有參數用一個空白隔開印出，最後加換行。

選項（bash 的 help echo，全部 3 個）：

選項 作用
-n 最後不加換行
-e 解讀反斜線跳脫序列（\t、\n…）
-E 不解讀反斜線跳脫序列

zsh 內建 echo 的選項也是這 3 個（man zshbuiltins）；/usr/bin/echo 多了 --help、--version。

bash 與 zsh 最大的差別：預設要不要解讀 \t（實測）：

bash:  echo "a\tb"     →  a\tb        （預設 -E，不解讀；要 -e）
zsh:   echo "a\tb"     →  a<Tab>b     （預設就解讀；要 -E 才不解讀）
/usr/bin/echo "a\tb"   →  a\tb        （預設 -E）

同一行在兩個 shell 印出不同結果，這就是寫腳本時建議改用 printf 的原因（/usr/bin/echo --help 自己也寫 printf(1) is a preferred alternative）。 printf 的用法見 在終端機怎麼計算。只是印一行固定字串或 "exit=$?" 這種沒有反斜線的內容，echo 在哪裡都一樣，放心用。

跳脫序列（bash help echo 全部列出，需 -e）：

序列 意思 序列 意思
\a 響鈴 \r 歸位（carriage return）
\b 退格 \t 水平定位（Tab）
\c 之後的輸出全部不印（含換行） \v 垂直定位
\e、\E ESC 字元 \\ 反斜線本身
\f 換頁（form feed） \0nnn 八進位 0～3 位數代表的字元
\n 換行 \xHH 十六進位 1～2 位數代表的字元
\uHHHH Unicode 字元（1～4 位十六進位） \UHHHHHHHH Unicode 字元（1～8 位十六進位）

zsh 的清單相同，只是不必加 -e。/usr/bin/echo 沒有 \E、\u、\U。

八、錯誤與結束狀態對照

看到某個結束狀態時，可以這樣反推（bash 的值來自 man bash〈EXIT STATUS〉，本機實測 zsh 相同）：

結束狀態 意思 本篇的實例 典型訊息（bash／zsh）
0 成功 ./oob（越界但沒當掉） —
1～125 程式自己回報的失敗 ./ret 3 程式自己印的
2 shell 內建命令用法錯誤（選項或參數不對） — —
126 找到了但不能執行（例如沒有 x 權限） ./noexec.c（權限 644） bash: ./noexec.c: Permission denied／zsh: permission denied: ./noexec.c
127 找不到命令 ret（忘了 ./） bash: ret: command not found／zsh: command not found: ret
128 + N 被訊號 N 終止 ./crash → 139（SIGSEGV 11）；第 3 課的 smash → 134（SIGABRT 6） Segmentation fault (core dumped)／zsh: segmentation fault

126 的更多成因（noexec 掛載、#! 直譯器不存在等）見 root執行腳本也Permission denied 第六節。

  1. 把第 3 課的寫法改成 ./crash && echo "exit=$?"，會印出什麼？為什麼第 3 課要用 ;？
  2. ./ret 7; echo hi; echo "exit=$?" 印出的是 exit=0 還是 exit=7？為什麼？如果中間一定要先印 hi，要怎麼改才看得到 7？
  3. 某個 C 程式最後寫 return 300;，shell 看到的結束狀態是 44。為什麼？這跟第 2 課的哪一個觀念一樣？如果寫 return 256;，呼叫它的腳本會以為成功還是失敗？
  4. 情境題：你執行 ./oob | tee log.txt; echo "exit=$?"，oob 明明 segfault 了，卻印出 exit=0。為什麼？在 zsh 裡要怎麼看出 oob 的真正狀態？
  5. 情境題：你用 zsh 跑一個腳本，腳本裡的程式 segfault 了，但畫面上沒有任何 segmentation fault 字樣。這代表程式沒有當掉嗎？你要怎麼確認？
