### 1. `gcc hello.c` 背後實際是哪幾個程式在接力？為什麼說 `gcc` 是「總指揮」？

```
1. 是cc1 負責前處理 擴大,引入include還是c語言
2. cc1 負責編譯稱組合語言
好像都是cc1做的?
3. as 負責變成二進制檔案
4. ld 弄成可執行擋
gcc 指揮這些程式
```

> **批改**：第一次大致對（誤以為前處理是獨立的 `cpp`）；第二次**對**。
>
> **參考答案**：本機實際接力的是 `cc1`（前處理＋編譯，C → 組合語言）→ `as`（組合語言 → 機器碼的 `.o`，但還有洞、不能執行）
> → `collect2` 呼叫 `ld`（連結成可執行檔）。`gcc` 自己不做這些轉換，只負責依序呼叫它們、在中間傳遞暫存檔，
> 所以叫總指揮（driver）；`gcc -v` 可以看到它實際執行的每個命令。

**第 3 次（複習，2026-09-23）**

```
- cc1(prprocess and compile) -> as assemble -> collect2 -dynamic-linker /lib64/ld-linux-x86-64.so.2 連接成 executable
- 因爲gcc負責去調用他們
```

> **批改（第 3 次，複習）**：**對**。接力順序正確，還從 `gcc -v` 找到了 `collect2`。
> 補一個小地方：`-dynamic-linker /lib64/ld-linux-x86-64.so.2` 是 `collect2` 轉交給 `ld` 的**參數**，
> 不是 `collect2` 自己做的一個步驟（第 2 題會用到這個區分）。參考答案同上。

**第 4 次（複習，2026-09-27）**
```
1. 前處理,還有轉成組合語言都是cc1
    組譯,組合語言轉機械碼 是 ac在做
    連接,ld在做

```

> **批改（第 4 次，複習）**：**對**。`cc1`（前處理＋編譯）→ `as`（組譯；你寫成 `ac`，筆誤）→ `ld`（連結），`gcc` 負責依序呼叫。
> 小地方：`ld` 實際是經由 `collect2` 呼叫的；「總指揮」的重點是 **`gcc` 自己不做任何轉換**，只負責呼叫與傳遞暫存檔。參考答案同上。

> **批改**：第一次部分錯（只答 `ld`，與自己的第 4 題矛盾）；第二次**大致對**（時間點對了，但沒點名執行時負責的角色）。
>
> **參考答案**：`printf`（在本課實際是 `puts`）的程式碼在 **libc（`libc.so.6`）**。接起來分兩個時間點：

### 2. `ld` 和 `ld.so`（`ld-linux-x86-64.so.2`）各在什麼時間點、做什麼事？

```
1. ld 是在連接的時候把.o 轉成可執行擋
2. ld.so 是被核心加載進來後,開始載入那些庫
```

> **批改（第 1 次，2026-09-23）**：**大致對**。上午還卡住的兩個時間點，這次都分對了：`ld` 在**連結時**，`ld.so` 在**執行時**，由核心載入。
> 各漏了一半「做什麼事」：
> - `ld` 產生執行檔時，**並沒有把函式庫的程式碼放進去**，而是寫下一張「需求單」（`NEEDED libc.so.6`、interpreter 路徑、符號版本）。
> - `ld.so` 不只是「載入那些庫」，還要**把 `puts` 等符號的位址填好**（接線），最後才跳進你的程式。

> **參考答案**：

> **批改（第 2 次，複習）**：**大致對**。連結時 `ld` 找到、執行時載入器找不到，`objdump -p` 正常、`ldd` 出錯，都對。
> 少了「**為什麼**載入器找不到」：`-L` 只是給 `ld` 的參數，載入器不知道它，只去自己的預設路徑找；執行檔裡的 `NEEDED` 只記了名字、沒記路徑。
> 也可以寫出 `ldd` 的具體輸出：`libfoo.so => not found`。參考答案同上。

### 4. 情境題：同事傳來一支 ARM 開發板用的執行檔，問你「它需要哪些函式庫」。你在自己的 x86-64 電腦上該用哪個工具？用 `ldd` 會發生什麼事，為什麼？

```
1. 用objdump or readelf
2. 會出錯,execuable format的錯誤, 你不能在x86 執行 arm編譯的程式
```

> **批改（第 1 次）**：部分錯。「不能在 x86 上執行 ARM 程式」這個原因對，但兩處不對：
> - 工具選擇：`objdump` 與 `readelf` 在這個情境**不是一樣好**，其中一個可能什麼都看不到。
> - `ldd` 的症狀：`exec format error` 是**直接執行** `./busybox` 時核心給的錯誤；`ldd` 給的是另一句話，而且那句話會誤導人。
>
> **提示**：回 [objdump能不能代替ldd](../../c/objdump能不能代替ldd找依賴庫-需求單與實際載入.md) 第三節看 `busybox` 的實測：
> `ldd ./busybox` 印了什麼？跟 `file` 的說法矛盾在哪？然後看同一節的「陷阱」：開發板／路由器上的執行檔常被剝掉什麼，那會讓哪個工具失手？

**第 2 次（重答，2026-09-24）**

```
1. 用readelf比objdump好,因爲一定有program header, section header有可能被拔掉
2. not a dynamic executable, 出現這個錯誤,因爲x86無法執行arm編譯的動態執行檔
```

> **批改（第 2 次，重答）**：**大致對**。工具選擇與理由都對，`ldd` 的輸出也找到了。兩處可以更精確：
> - 不是「x86 執行不了」，而是 `ldd` 要靠**本機的動態載入器**模擬載入，而本機載入器只處理得了 x86-64 的檔案。
> - 這句話的重點是它**會誤導人**：`file` 明明說 `dynamically linked`，`ldd` 卻說「不是動態執行檔」。
>   看到這句話不能就此認定它是靜態連結。
>
> **參考答案**：用 `readelf -d`（看 `NEEDED`）。只讀檔案，任何架構都能讀；開發板／路由器上的檔案常被剝掉區段標頭，
> 這時 `objdump -p` 找不到 `.dynamic`，但 `readelf -d` 能透過程式標頭的 `DYNAMIC` 找到。`ldd` 會印出 `not a dynamic executable`，
> 那是錯的訊息，實際原因是本機載入器處理不了 ARM 檔案。直接執行才會看到核心給的 `exec format error`。

**第 3 次（複習，2026-09-27）**
```
1. 爲了安全應該用objdump 或 readelf
2. 因爲在ubuntu找不到arm的動態載入器,所以會報錯,找不到檔案
```

> **批改（第 3 次，複習）**：**大致對**。第一問方向對（只讀檔案的工具，不能用 `ldd`）；兩個之中要選 **`readelf -d`**：開發板上的檔案常被剝掉區段標頭，`objdump -p` 這時會找不到 `.dynamic`。
> 第二問：`ldd` 實際印的是 `not a dynamic executable`，不是「找不到檔案」。重點是**這個訊息會誤導人**——檔案明明是動態連結的，真正原因是本機載入器處理不了 ARM 檔案。參考答案同上。
