## 作業批改（Claude，2026-09-22）

> 四題的實驗操作與輸出**全部正確**。第一次批改時要求解釋本課沒教過的原因，是出題錯誤（沒有標明答案來源），
> 已改成補教；完整解說寫在課程筆記[第九節〈作業解說〉](../../c/hello.c怎麼變成能跑的程式-編譯的四個階段.md#九作業解說四題背後的原因)。以下是各題的參考答案摘要。

**第 1 題**：`.c` 110 → `.i` 21K 是因為 `#include <stdio.h>` 把整份標頭檔（及它再 include 的檔案）貼進來（筆記第二節）。
`.o` 1.5K → `hello` 16K：連結器加入啟動碼與動態連結要用的區段（`.plt`、`.got`、`.dynamic`、`.interp` 等，合計約 2K），
但主因是**分頁對齊**——4 個 `LOAD` 區塊各自從 4096 bytes 的分頁邊界開始，中間補空白（新觀念，第九節）。

**第 2 題**：出錯的是**編譯階段（`cc1`）**，不是前處理；少了 `#include` 只是少貼一段文字。
沒有宣告時編譯器用 C89 舊規則「猜」函式型別，只發警告；**連結器只比對名字、不比對型別**，
所以照名字 `printf` 仍然接得上 libc，程式能跑。型別猜錯時（例如回傳 `double` 的函式）會在執行時得到錯誤結果，
沒有任何階段會擋下來（新觀念，第九節有 `half(10) = 0.000000` 的實測）。

**第 3 題**：不會換成 `puts`。`puts(s)` 只能「原封不動印字串再補換行」，不懂任何 `%` 格式；
`%d` 要把 42 轉成字元 `'4'`、`'2'`，只有 `printf` 做得到。gcc 只在效果剛好等於「印現成字串加換行」時才換（新觀念，第九節）。

**第 4 題**：靜態版把 libc 用到的程式碼複製進執行檔，所以大約 50 倍大（程式碼區 1375 → 668305 bytes）。
動態版的 `openat` 是動態載入器打開 `/etc/ld.so.cache` 與 `libc.so.6`；靜態版沒有 interpreter、libc 已在自己身上，
沒有東西要打開，系統呼叫 34 → 16。兩者都只有 1 次 `write`：連結方式只影響程式碼從哪來，不影響最後請核心做的事（筆記第五、六節）。

1. `gcc hello.c` 背後實際是哪幾個程式在接力？為什麼說 `gcc` 是「總指揮」？

```
1. 是cc1 負責前處理 擴大,引入include還是c語言
2. cc1 負責編譯稱組合語言
好像都是cc1做的?
3. as 負責變成二進制檔案
4. ld 弄成可執行擋
gcc 指揮這些程式
```

> **批改**：第一次大致對（誤以為前處理是獨立的 `cpp`）；第二次**對**。
>
> **參考答案**：本機實際接力的是 `cc1`（前處理＋編譯，C → 組合語言）→ `as`（組合語言 → 機器碼的 `.o`，但還有洞、不能執行）
> → `collect2` 呼叫 `ld`（連結成可執行檔）。`gcc` 自己不做這些轉換，只負責依序呼叫它們、在中間傳遞暫存檔，
> 所以叫總指揮（driver）；`gcc -v` 可以看到它實際執行的每個命令。

2. `hello.i` 裡有 `printf` 的宣告，卻沒有它的程式碼。那它的程式碼在哪？是在哪個時間點、由誰把「呼叫 `printf`」和「`printf` 的程式碼」接起來的？

```
- 在libc
- ld
- 是在執行的時候從libc 的 接起來與呼叫
```

> **批改**：第一次部分錯（只答 `ld`，與自己的第 4 題矛盾）；第二次**大致對**（時間點對了，但沒點名執行時負責的角色）。
>
> **參考答案**：`printf`（在本課實際是 `puts`）的程式碼在 **libc（`libc.so.6`）**。接起來分兩個時間點：
> - **連結時，`ld`**：不把程式碼接進來，只記下「需要 libc 的 `puts`」、準備好跳轉用的 `.plt`／`.got`、寫入 interpreter 路徑。
> - **執行時，動態載入器 `ld-linux-x86-64.so.2`**：`execve` 後它先跑，打開並 `mmap` `libc.so.6`，再把 `puts` 的真實位址填進去。
>
> 注意 `ld`（連結器）與 `ld-linux-x86-64.so.2`（執行時的載入器，又叫 `ld.so`）是兩個不同的程式。

3. `hello.o` 裡 `call` 指令後面的四個 byte 為什麼是 `00 00 00 00`？什麼資訊讓連結器知道要把它填成什麼？

```
- 是要填入put
- 13: R_X86_64_PLT32      puts-0x4
- 00 00 00 00 就是要填入的地址
```

> **批改**：第二問（靠重定位項目知道要填什麼）兩次都**對**；第一問（為什麼是 0）兩次都**不完整**——描述了現象，沒說原因。
>
> **參考答案**：組譯器一次只處理一個檔案，**`puts` 的程式碼不在 `hello.o` 裡**，組譯時根本不知道它的位址，
> 只能先填 0 占位，並記下一筆重定位項目 `13: R_X86_64_PLT32 puts-0x4`——「位移 0x13 的地方，將來填上 `puts` 的位址」。
> 連結器看到這筆項目，就知道要去找名叫 `puts` 的符號、把對應位址填進那四個 byte。

4. 連結完成後 `nm hello` 仍然顯示 `U puts@GLIBC_2.2.5`，這是連結失敗嗎？為什麼？

```
- 不是,但是要行程跑起來動態加載puts
```

> **批改**：**對**。
>
> **參考答案**：不是連結失敗。這是動態連結：連結器只記下需要 glibc 提供的 `puts`，真正的位址要等執行時，
> 由動態載入器 `ld-linux-x86-64.so.2` 載入 `libc.so.6` 後才填上，所以連結後的執行檔裡 `puts` 仍是 `U`（未定義）。

5. 情境題：你把一支動態連結的程式複製到另一台機器，執行時出現找不到 `libc.so.6` 某個版本符號的錯誤。從本課的哪個階段可以解釋這件事？如果改用 `-static` 編譯，這個問題還會發生嗎？

```
- 因爲 put是在glibc2.2.5的版本,所以另一臺的glibc可能不支持這個版本
- 不會,因爲static是把libc.so.6直接放到行程裏面
```

> **批改**：第一次前半錯（以為是記憶體位置不同）；第二次前半**大致對**（方向對，但實際門檻是 `GLIBC_2.34` 不是 2.2.5，且沒答哪個階段）。
> 後半兩次都**對**，但兩次都把「執行檔」寫成「行程」——行程是程式跑起來之後的東西，第 ② 站會正式區分。
>
> **參考答案**：
> - 連結時，`ld` 把「需要 libc 的哪些**符號版本**」寫進執行檔；執行時，動態載入器逐一檢查目標機器的 `libc.so.6` 有沒有提供。
>   **連結時記下要求、執行時才被檢查。**
> - 本機實測（`objdump -T hello`）這支程式需要 `GLIBC_2.2.5`（`puts`）和 `GLIBC_2.34`（啟動碼的 `__libc_start_main`）。
>   2.2.5 是 x86-64 最早的版本、到處都有；**真正的門檻是 2.34**：本機是 glibc 2.39，拿到 glibc 比 2.34 舊的機器就會失敗。
> - 位址不同**不是**問題——每次執行的位址本來就不一樣，填位址正是動態載入器的工作。
> - `-static` 不會發生：libc 的程式碼已複製進**執行檔**，執行時不再找外部的 `libc.so.6`，也沒有版本需求表。
>   代價是檔案大，而且 libc 的安全修補要重新編譯才會帶進去。實務上改在最舊的目標系統上編譯也能避開。
