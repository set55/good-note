## 1. 比 `int` 小的型別

寫 `ranges.c`，印出 `short`、`unsigned short`、`signed char`、`unsigned char` 的 `sizeof`，
以及它們的最小值、最大值（`<limits.h>` 裡的常數名稱，查 `/usr/include/limits.h`；無號型別只有最大值）。

### 1-1. 執行前先預測：`short` 是 2 byte、用二補數，範圍是多少到多少？把算的過程寫下來。【筆記第一、五節】

**第 1 次（2026-09-27）**
```
range.c 我已經寫好了 你可以看看 打印出來是
2
-32768
32767
2
65535
1
-128
127
1
255

- 最大值是 2^15-1=32767, 最小值是 (2^15 -1) - (2^16 - 1) = -32768
```

> **批改**：**對**。輸出正確，算出來的範圍也對。
>
> **參考答案**【筆記第五節】：16 bit，最高位（第 15 位）的權重是 −2¹⁵。
> 最大值是 `0111 1111 1111 1111` = 2¹⁵ − 1 = 32767；最小值是 `1000 0000 0000 0000` = −2¹⁵ = −32768。
> 你寫的 (2¹⁵−1) − (2¹⁶−1) 數字剛好相等，但它不是理由——理由是「只有符號位是 1、其他全 0」，而符號位的權重是負的。
>
> **小地方**：`sizeof` 的結果是 `size_t`，要用 `%zu` 印（筆記第一節、第九節），不是 `%ld`。x86-64 上剛好都是 8 byte 的無號整數所以印得出來，
> 但型別不同，換到 32 位元的機器就可能印錯。第 4-4 題會用到這件事。

### 1-2. 為什麼 `unsigned short` 的最大值是 `short` 最大值的兩倍再加 1？【筆記第四、五節】

**第 1 次（2026-09-27）**
```
- unsigned short 最大值計算是 2^16-1 = 2 * 2^15 - 1 = 2* (32767 + 1) - 1 = 2*SHRT_MAX + 2 -1 = 2*SHRT_MAX + 1
```

> **批改**：**對**。代數推導正確。
>
> **參考答案**【筆記第四、五節】：把代數換成**位元的理由**——`unsigned short` 的 16 個 bit **全部**是數值位，
> `short` 要拿最高位當符號位，只剩 15 個數值位。用位元看最直接：
> `SHRT_MAX` = `0x7fff` = `0111…1`，乘 2 等於整體左移一位 → `1111…10` = `0xfffe`，再加 1 → `0xffff` = `USHRT_MAX`。

> **提示**【筆記第三節】：分兩個問題想——

>    x86-64 用什麼順序把它們拼回數字？
> 2. 為什麼 `0x55667788` 印在 `0x11223344` 的**左邊**？`x` 一行裡的多個單位是照什麼排的（冒號左邊的位址是誰的位址）？

**第 2 次（重答，2026-09-27）**
```

```

> **批改（第 2 次）**：**大致對**。第一個單位是從 `&v` 開始的 4 個 byte（`88 77 66 55`），用小端序拼回來是 `0x55667788`；第二個單位從 `&v + 4` 開始（`44 33 22 11`）→ `0x11223344`，這兩點都答出來了。
> 沒有明講的是「為什麼 `0x55667788` 在左邊」。另外「順序是 55 開始」的說法不精確：不是從 55 開始讀，而是**位址最低的 `0x88` 是最低位**，寫成數字時自然排在最右邊。
>
> **參考答案**【筆記第三節】：
> 1. `x/2xw &v` 把從 `&v` 開始的 8 個 byte 切成兩個 4 byte 的單位。第一個單位是位址 `…338`～`…33b` 的 `88 77 66 55`，
>    x86-64 是小端序，位址最低的 byte 是最低位，所以拼成 `0x55667788`；第二個單位是 `…33c`～`…33f` 的 `44 33 22 11` → `0x11223344`。
> 2. `x` 一行裡的單位**照位址由低到高、從左到右**排，冒號左邊只印第一個單位（最左邊那個）的位址。`0x55667788` 位址比較低，所以在左邊。
> 3. 所以看起來像「前後兩半對調」：在小端序機器上，8 byte 數字的**低 4 byte** 放在低位址。用 `x/1xg &v`（`g` 是 8 byte）一次讀整個單位，
>    就會拼回 `0x1122334455667788`。**用幾 byte 當單位讀，就決定了拼出來的數字**——這正是第三節說「把原始位元組當成數字讀才會出事」的例子。

> 無號數 `< 0` 永遠假、`>= 0` 永遠真，所以會警告；`> 0` 等於 `!= 0`，值是 0 時為假，結果不固定，是合法且常見的寫法，gcc 無從知道你本意是比大小。

### 4-3. 把判斷改成正確的寫法。【筆記第四節】

**第 1 次（2026-09-27）**
```
if (a > b)
```

> **批改**：**對**。
>
> **參考答案**：無號數不要用「相減再跟 0 比」判斷大小，因為無號減法不會變負、只會回繞成很大的數；直接比兩個數本身。

## 5. 錯誤的溢位檢查

寫 `overflow_check.c`，裡面有一個函式想檢查「`x + y` 會不會超過 `int` 的範圍」（只考慮 `y` 是正數）：
```c
int will_overflow(int x, int y)
{
    int sum = x + y;
    return sum < x;      /* 加了正數反而變小，就代表溢位了？ */
}
```
在 `main` 裡印出 `will_overflow(INT_MAX, 1)`。

### 5-1. 用 `-O0`、`-O2`、`-O2 -fwrapv` 各編一次，貼上三個結果，解釋為什麼不一樣。【筆記第八節】

**第 1 次（2026-09-27）**
```
will_overflow(INT_MAX, 1): 1    O0 是 cpu實際執行算出來的, 有號溢位
will_overflow(INT_MAX, 1): 0    O2 是 gcc 在編譯時,檢查文法直接得出來的結果,因爲相加,文法上應該更大
will_overflow(INT_MAX, 1): 1    fwrapv 直接告訴gcc有號溢位 二補數迴繞
```

> **批改**：三個結果正確。
> - `-O0` 回傳 1 —— **對**。
> - `-O2 -fwrapv` 回傳 1 —— **對**。
> - `-O2` 回傳 0 —— **不完整**。「gcc 在編譯時直接得出結果」對，但「因為相加、文法上應該更大」沒有說出 gcc **憑什麼**可以這樣假設。
>   `INT_MAX + 1` 明明不會更大，gcc 為什麼可以當作它更大？
>
> **提示**【筆記第八節〈有號溢位在 C 標準裡是「未定義行為」〉】：有號溢位在 C 標準裡的地位是什麼？這個地位允許編譯器做什麼樣的假設？

**第 2 次（重答，2026-09-27）**
```
因爲是有號溢位,c定義有號溢位是未定義行爲,gcc會假設有號溢位不會發生,所以推論相加只會更大
```

> **批改（第 2 次）**：**對**：有號溢位是未定義行為，gcc 可以假設它不會發生，於是「加上正數一定更大」。

> **參考答案**【筆記第八節】：`-O0` 照字面算，`INT_MAX + 1` 回繞成 `INT_MIN`，`INT_MIN < INT_MAX` 成立 → 1。`-O2` 利用「有號溢位是 UB、可以假設不發生」，

> 改寫成 `y < 0` 是用 `-fdump-tree-optimized` 實測看到的，已補教進筆記第八節〈另一種寫法：`x + y < x` 被改寫成 `y < 0`〉。

### 5-2. 寫一個不會觸發有號溢位的版本 `safe_will_overflow(int x, int y)`：**在做加法之前**，用 `INT_MAX` 和 `y` 判斷 `x` 會不會太大。三種編譯方式都要得到一樣的結果。【筆記第八節】

**第 1 次（2026-09-27）**
```

```

> **批改**：**對**。三種編譯方式的結果沒有貼（題目有要求），Claude 實測三種一致：
>
> ```
> $ gcc -O0 safe_overflow_check.c -o s && ./s
> safe_will_overflow(INT_MAX, 1): 1
> $ gcc -O2 safe_overflow_check.c -o s && ./s
> safe_will_overflow(INT_MAX, 1): 1
