## 自我測驗作答：第 2 課：資料在記憶體裡長怎樣（2026-09-27）

> 題目來自 [C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.md](../../c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.md)。

### 1. 一個 `int` 變數存著 `-1`，用 `%d` 印出 `-1`，轉成 `unsigned` 再用 `%u` 印出 `4294967295`。記憶體裡的內容有沒有變？為什麼同一個東西會印出兩個不同的數？

```
1. 沒有變
2. 有號的話會有二補數,二補數有符號位,所以要把第32未,那位看成符號
0x20000000 就是 -2147483648 然後不斷+1到 -1(0xffffffff)

無號 從 0 到 0xffffffff 就是 4294967295
```

> **批改（第 1 次，2026-09-27）**：**大致對**。第一問「沒有變」**對**。第二問方向對：有號讀法有符號位、無號讀法從 0 到 `0xffffffff`。
> 兩個地方要修：
> - 筆誤：`-2147483648` 是 **`0x80000000`**（只有最高位是 1），不是 `0x20000000`。
> - 沒有直接點出「誰決定讀法」：記憶體裡一直是同一串 `0xffffffff`，是 **`printf` 的 `%d`／`%u`** 決定用有號還是無號去解讀這 32 個 bit。
>
> **參考答案**【筆記第五、六節】：沒有變，記憶體裡始終是 `ff ff ff ff`。同樣寬度的有號、無號轉換只換讀法、不動位元：
> `%d` 用二補數讀（最高位權重是 −2³¹），得到 −1；`%u` 把每一位都當正的權重，得到 2³² − 1 = 4294967295。

### 2. `int x = 0x12345678; unsigned char *b = (unsigned char *)&x;` 在本機 `*b` 是多少？換到大端序的機器上是多少？為什麼 `int *p = &x;` 的 `*p` 在兩種機器上都是 `0x12345678`？

```
1. 0x78
2. 0x12
3. 指引p指針是4byte的指針,所以小端序就是完整的0x12345678, 大端緒也是
```

> **批改（第 1 次，2026-09-27）**：第一、二問 **對**（本機 `0x78`、大端序 `0x12`）。
> 第三問**錯**：「`p` 是 4 byte 的指標」不對。第 2 課第二節才講過，本機**所有指標都是 8 byte**（第 6 題你也答了 8 byte）；
> `int *` 的「4」是它**指向的東西**（`int`）佔 4 byte。而且就算知道要讀 4 byte，也還沒解釋為什麼兩種機器讀出來都是 `0x12345678`。
>
> **提示**【筆記第三節〈什麼時候要在意位元組順序？〉】：把 `0x12345678` **寫進** `x` 的，跟用 `*p` **讀出** `x` 的，是不是同一台機器上的同一顆 CPU？
> 它寫的時候用什麼順序排 byte、讀的時候又用什麼順序拼回來？那「會出事」的情況又是誰寫、誰讀？

**第 2 次（重答，2026-09-27）**
```
1. 0x78
2. 0x12
3. 小端序他開頭是只想0x78, 大端緒是0x12,兩個都是讀4byte,但讀的方向相反,但因爲每個byte相鄰都是一樣的所以都是0x12345678
```

> **批改（第 2 次，重答）**：**不完整**。「兩種機器讀的方向相反」有抓到一半，但「每個 byte 相鄰都一樣所以都是 `0x12345678`」不是理由——兩種機器記憶體裡的 byte 排列**確實不一樣**。
>
> **參考答案**【筆記第三節〈什麼時候要在意位元組順序？〉】：寫入 `x` 和用 `*p` 讀出 `x` 的是**同一顆 CPU**，它用同一種順序寫、再用同一種順序拼回來：
> 小端機器寫成 `78 56 34 12`、讀的時候把第一個 byte 當最低位，拼回 `0x12345678`；大端機器寫成 `12 34 56 78`、讀的時候把第一個 byte 當最高位，也拼回 `0x12345678`。
> 所以**用正確的型別讀寫自己的變數**永遠看不到順序問題。會出事的是「一台機器寫、另一種順序的機器讀」（網路封包、檔案），或用 `unsigned char *` 一個個 byte 去看。
> 另外，`p` 本身是 8 byte 的指標；「讀 4 byte」是因為它指向的型別是 `int`。

### 3. `int n = -1; unsigned int len = 5;`，`n < len` 為什麼是假？只加 `-Wall` 編譯，gcc 會不會提醒你？

```
1. 換成無號的 -1 就是 4294967295, 做一就是false
2. 不會
```

> **批改（第 1 次，2026-09-27）**：**對**。`int` 跟 `unsigned int` 比較時 `-1` 被轉成 4294967295，比 5 大，所以是假；只加 `-Wall` 不會警告。
> 可以補一句：要加 `-Wextra` 才有 `-Wsign-compare` 警告。
>
> **參考答案**【筆記第七節】：一般算術轉換把 `int` 轉成 `unsigned int`，位元不變、換成無號讀法，`-1` 變成 4294967295，所以 `n < len` 為假。
> `-Wall` 不警告，`-Wall -Wextra` 才有 `-Wsign-compare`。

### 4. `int y = x + 1; return y > x;` 在 `x = INT_MAX` 時，`-O0` 回傳 0、`-O2` 回傳 1。為什麼會這樣？這算不算 gcc 的 bug？kernel 用哪個選項避免這種情況，代價是什麼？

```
1. -O0: y會變成-2147483648, 所以return 0
-O2: 因爲這是二補數迴繞是未定義的情況,所以對於gcc, 加只會越加越大,所以return 1

2. fwrapv用這個,告訴gcc有二補數迴繞,代價要在編譯階段就算出來
```

> **批改（第 1 次，2026-09-27）**：
> - `-O0` 回傳 0 **對**（`INT_MAX + 1` 回繞成 −2147483648，不比 `x` 大）。
> - `-O2` 回傳 1 **大致對**：有號溢位是未定義行為，gcc 假設它不會發生，所以認為「加 1 一定更大」。（用詞：未定義的是「有號溢位」，「二補數迴繞」是 CPU 實際發生的事。）
> - 「算不算 gcc 的 bug」**沒有回答**。
> - kernel 用的選項**不完整**：`-fwrapv` 是單一程式的做法；kernel 的 `Makefile` 用的是另一個名字的選項（它等於 `-fwrapv` 再加上指標的版本）。
> - 代價**錯**：「要在編譯階段就算出來」不是代價——在編譯時算好反而是最佳化帶來的**好處**。
>
> **提示**【筆記第八節〈有號溢位在 C 標準裡是「未定義行為」〉與〈kernel 怎麼處理〉】：
> - 標準對一支發生有號溢位的程式「要求了什麼結果」？如果標準沒要求，gcc 輸出哪一個結果才算「錯」？
> - kernel 選項的名字是 `-fno-...`，筆記引了 kernel `Makefile` 那一行。
> - 關掉「溢位不會發生」這個假設之後，編譯器**少了**什麼能力？對程式的執行速度有什麼影響？

**第 2 次（重答，2026-09-27）**
```
1. 
-O0: y會變成-2147483648, 所以return 0
-O2: 因爲這是二補數迴繞是未定義的情況,所以對於gcc, 加只會越加越大,所以return 1
gcc的標準未定義的就沒有標準答案
2. 不算,因爲這是未定義的情況
3. fwrapv用這個,告訴gcc要做二補數迴繞,關閉了最佳化,代價就是程式執行可能會變慢,因爲犧牲了最佳化
```

> **批改（第 2 次，重答）**：**大致對**。「不是 bug，標準對有號溢位沒有要求，所以沒有標準答案」**對**；代價「少了最佳化、程式可能變慢」**對**。
> kernel 的選項名稱還是不對：`-fwrapv` 是一般程式可以用的選項，kernel 的 `Makefile` 寫的是 **`-fno-strict-overflow`**（效果等於 `-fwrapv -fwrapv-pointer`，連指標運算也照回繞處理）。
>
> **參考答案**【筆記第八節】：`-O0` 照字面算，`INT_MAX + 1` 回繞成 `INT_MIN`，不比 `x` 大 → 0；`-O2` 利用「有號溢位是 UB、假設不會發生」，把 `x + 1 > x` 當成永遠成立 → 1。
> 不是 gcc 的 bug：標準對發生 UB 的程式沒有任何要求，兩種結果都合法。kernel 用 `-fno-strict-overflow` 整個專案關掉這種推理，代價是少了依賴這個假設的最佳化，程式可能稍慢。

### 5. 情境題：你從網路封包裡讀到 4 個 byte，依序是 `00 00 01 00`。協定規定數字用大端序，所以它代表 256。如果直接用 `int *` 把這 4 個 byte 讀進本機（x86-64），會得到多少？為什麼？

```
65536
本機是小端序
00 01 00 00

```

> **批改（第 1 次，2026-09-27）**：**對**。小端序把第一個 byte 當最低位，`00 00 01 00` 拼成 `0x00010000` = 65536。
>
> **參考答案**【筆記第三節】：記憶體從低到高是 `00 00 01 00`，x86-64 是小端序，位址最低的 byte 是最低位，拼回來是 `0x00010000` = 65536，
> 不是協定要的 256。所以讀網路資料要用 `ntohl` 之類的函式轉換。

**第 2 次（重答，2026-09-27）**

```
1. 因爲long最大只有 2147483648
   unsigned int 可以到4294967296
```

>
> **提示**【筆記第四節〈常數也有型別〉】：沒有後綴的常數，gcc 會「依序嘗試幾個型別，選第一個裝得下的」。**十進位**和**十六進位**嘗試的清單一樣嗎？

```
1. 
2147483648
int 最大是 2147483647 不是他
```

> **批改（第 2 次，重答）**：**大致對**。兩個常數的型別（`long`、`unsigned int`）和兩個比較結果（假、真）都**對**，轉換過程也寫對了。兩個地方要修：
> - 「`long` 最大是 4294967295」**錯**：那是 `unsigned int` 的最大值。本機 `long` 是 8 byte，最大 9223372036854775807。
> - 沒說出**為什麼十進位不試 `unsigned int`**：4294967295 明明也裝得下 2147483648，十進位卻直接跳到 `long`——因為十進位的嘗試清單裡**根本沒有無號型別**。這才是兩者型別不同的原因。
>
> **參考答案**【筆記第四節〈常數也有型別〉】：沒有後綴的常數依序嘗試、選第一個裝得下的型別，但十進位與十六進位的清單不同：
> 十進位是 `int` → `long` → `long long`（永遠不變成無號），所以 `2147483648` 是 `long`；十六進位是 `int` → `unsigned int` → `long` → …，所以 `0x80000000` 是 `unsigned int`。
> `-1 < 0x80000000`：`int` 與 `unsigned int` 比，`-1` 轉成 4294967295 → **假**；`-1 < 2147483648`：`int` 與 `long` 比，`-1` 轉成 `long` 還是 −1 → **真**。
>
> 你的追問「常數比較要怎麼比、以誰為準」已寫進筆記第四節新小節〈怎麼確定一個常數的型別？比較時以誰為準？〉：先決定每一邊的型別，再照一般算術轉換的 5 條規則決定共同型別，附 `common.c` 實測 8 種組合。並新增第 10 題。
