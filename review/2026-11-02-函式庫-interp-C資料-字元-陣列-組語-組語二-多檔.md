### 函式庫 2. 順序：`-ltxt` 寫在 `main.c` 前面

> 盒子 1｜過去的作答：[s1-07 quiz.md 第 2 題](../small-project/s1-07-libraries/quiz.md#2-順序-ltxt-寫在-mainc-前面)（10-29 第一次作答）、[11-01 複習](./2026-11-01-函式庫-組語.md#函式庫-2-順序-ltxt-寫在-mainc-前面)

一個靜態函式庫 `libtxt.a` 由下面的 `case.c`、`space.c`、`trim.c` 三個成員組成，`main.c` 只呼叫 `trim`（檔案同第 1 題）。`gcc -Wall -L. -ltxt main.c -o app` 會失敗，錯誤訊息是 `undefined reference to 'trim'`。用 `ld` 處理輸入檔的方式解釋為什麼。這個錯誤跟 `cannot find -ltxt` 差在哪（各是什麼東西找不到）？`cannot find -ltxt` 可以這樣產生：同樣的檔案，指令改成漏掉 `-L.` 的 `gcc -Wall main.c -ltxt -o app`。在 Ubuntu 上把 `libtxt.a` 換成 `libtxt.so`、命令一樣寫成 `-L. -ltxt main.c`，也會失敗，原因是什麼？

> **批改**：**對**。抓到重點：Ubuntu 的 gcc 預設傳 `--as-needed`，讀到 `-ltxt` 時清單上沒有 `libtxt.so` 能提供的符號，它就被丟掉；之後 `main.o` 的 `trim` 沒人提供 → `undefined reference`。10-29、11-01 都漏了 `--as-needed`（寫成「跟 `.a` 一樣」），這次寫出來了。小修：「符號清單沒有 `-ltxt` 擁有的」精確說是「清單上沒有 `libtxt.so` 能提供的符號」；`.so` 被丟掉的意思是不寫進 `NEEDED`、也不拿來解決之後的符號。
>
> **參考答案**【[第四節](../html/c/靜態與動態函式庫-ar與.a、-fPIC與.so、執行時怎麼找到.so.html#so-在-ubuntu-上也有順序問題)〈`.so` 在 Ubuntu 上也有順序問題〉】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. Ubuntu 的 gcc 預設傳 `--as-needed` 給 `ld`：`.so` 只有在**目前有人需要它的符號**時才寫進 `NEEDED`、才拿來解決符號。
> 2. 遇到 `-ltxt` 時 `main` 還沒讀、沒人需要 `trim`，`libtxt.so` 就被丟掉 → 之後 `main` 的 `trim` 沒人提供 → `undefined reference`。
>
> **詳細說明**：單純「由左往右」不會讓 `.so` 失敗：把 `-Wl,--no-as-needed` 放在 `-ltxt` 前面（`gcc -Wall -L. -Wl,--no-as-needed -ltxt main.c -o app4`）就成功，`readelf -d app4` 有 `NEEDED libtxt.so`。所以 `.a` 和 `.so` 失敗的機制不同（`.a` 是不拉成員、`.so` 是被 `--as-needed` 丟掉），但結論一樣：`-l` 一律寫在後面。

#### 函式庫 4-1. 這個訊息是誰印的？為什麼連結時找得到、執行時找不到？

> 1. 是動態連結器 `ld.so`（執行檔的 interpreter）在執行時印的。
> 2. `-Llib` 只告訴**連結時**的 `ld` 去哪找，不會寫進執行檔；執行檔的 `NEEDED` 只記名字 `libfoo.so`。

> **核心關鍵**（答到這幾點就算對）：
>
> 1. 延遲綁定靠跳板：呼叫函式時一定先經過 PLT 這段程式碼，第一次才有機會轉去叫 `ld.so` 查。

#### 函式庫 11-2. `nm setlevel` 會不會看到 `level`？在哪一種區段？為什麼原始碼只有 `extern` 卻會有？

```
會
```

> **批改**：**對**。三個核心關鍵都有：會看到、在執行檔的 `.bss`；主程式是 `-fPIE`，用 `%rip` 加固定距離直接讀全域變數；所以執行檔裡要有一份 `level`，距離才固定。11-01 缺的「`-fPIE` 直接讀」這次寫出來了。小修：「複製一份到執行檔」要分兩個時間點——**連結時** `ld` 只在 `.bss` 替 `level` **留一個同樣大小的位置**、並寫一個 `R_X86_64_COPY`；**載入時** `ld.so` 才把值複製進去（11-3）。你第一段「初始值為 0」講的就是這件事：檔案裡只有位置、沒有值，所以放 `.bss`。
>
> **參考答案**【[第九節第 3 章](../html/c/靜態與動態函式庫-ar與.a、-fPIC與.so、執行時怎麼找到.so.html#3-主程式只寫-extern-int-counter變數放進執行檔複製重定位)〈主程式只寫 `extern int counter;`：變數放進執行檔（複製重定位）〉】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. 會看到，類型 `B`，在執行檔的 `.bss`。
> 2. 主程式是 `-fPIE`：編譯器假設全域變數都在執行檔自己裡面，用 `%rip` 加固定距離直接讀，不經 GOT。
> 3. 但 `level` 定義在 `.so`，距離不可能固定；`ld` 只好在執行檔的 `.bss` 替它留一個同樣大小的位置，並寫一個 `R_X86_64_COPY` 重定位（複製重定位）。
>
> **詳細說明**：本機實測：`nm setlevel` → `0000000000004010 B level`；`readelf -SW setlevel` 的 `.bss` 從 `0x4010` 開始；`readelf -r setlevel` → `000000004010 … R_X86_64_COPY … level + 0`。

#### 函式庫 11-3. 第一行印出的值是怎麼放進那裡的？`get_level()` 讀的是哪一份 `level`？用重定位的類型和 `ld.so` 找符號的順序說明。

```
1. level 是用R_X86_64_COPY這個重定位類型,當執行的時候,ld.so看到執行檔的level重定位類型是R_X86_64_COPY,就會把so裏面的level = 3 複製到執行檔.bss level的地方

2. get_level() 他是在so檔, ld.so在執行的時候依據執行檔 -> so的順序,以及在libcfg.so的level重定位類型是R_X86_64_GLOB_DAT,會把優先選擇執行檔的level,把這個位址複製到.got的3fd0, 所以實際上get_level() 拿得還是執行檔的level
```

> **批改**：**對**。三個核心關鍵都有：(1) 執行檔的 `R_X86_64_COPY`，`ld.so` 載入時把 `libcfg.so` 的初值 3 複製進執行檔 `.bss` 的 `level`；(2) `libcfg.so` 的 GOT 那格是 `R_X86_64_GLOB_DAT`，`ld.so` 照「先執行檔、再 `.so`」找到執行檔那份，把它的位址填進 `.got`——`0x3fd0` 也對（本機實測 `readelf -r libcfg.so`：`000000003fd0 … R_X86_64_GLOB_DAT 0000000000004008 level + 0`）；(3) 所以 `get_level()` 讀的是執行檔那份。11-01 缺的 `GLOB_DAT` 與「先找執行檔」這次都寫出來了。用詞小修：「把這個位址複製到 `.got`」說「填進」比較準，`GLOB_DAT` 是填位址、`COPY` 才是複製值。
>
> **參考答案**【[第九節第 3 章](../html/c/靜態與動態函式庫-ar與.a、-fPIC與.so、執行時怎麼找到.so.html#3-主程式只寫-extern-int-counter變數放進執行檔複製重定位)〈主程式只寫 `extern int counter;`：變數放進執行檔（複製重定位）〉】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. 第一行的 3：載入時 `ld.so` 處理執行檔的 `R_X86_64_COPY`，去 `libcfg.so` 找到 `level`，把初值 3 複製進執行檔 `.bss` 的 `level`；`main` 直接讀它。
> 2. `get_level()` 經過 `libcfg.so` 的 GOT 讀 `level`，那格是 `R_X86_64_GLOB_DAT level`；`ld.so` 照「先找執行檔、再找 `.so`」找到**執行檔那份**，把執行檔的 `&level` 填進去。
> 3. 所以兩邊用的都是執行檔那份；`main` 改成 7，`get_level()` 讀到 7。`libcfg.so` 自己那份 `level` 只在載入時被讀一次初值。
>
> **詳細說明**：本機實測 `LD_DEBUG=bindings ./setlevel` 的兩行就是這兩件事：`binding file ./setlevel to …/libcfg.so: normal symbol 'level'`（處理 `COPY`：去 `.so` 拿初值）、`binding file …/libcfg.so to ./setlevel: normal symbol 'level'`（處理 `GLOB_DAT`：`.so` 的 GOT 接到執行檔）。

#### 函式庫 11-4. 之後把 `cfg.c` 改成 `long level = 3;` 重做 `libcfg.so`，`setlevel` 不重新連結就執行，會發生什麼事、為什麼？

```
由於ld.so會發現執行檔的level 大小是4byte,但libcfg.so的level大小是8byte
所以會提示:./setlevel: Symbol `level' has different size in shared object, consider re-linking
但不會終止,程式會繼續執行,ld.so會把8byte的level 複製到 執行檔0x4010的那格,但是因爲是8byte 上位那4byte
但我檢查過那4byte好像沒有符號在使用,所以不會有事,以當前的題目情況
```

> **批改**：**對**。兩個核心關鍵都有：`ld.so` 印 `Symbol 'level' has different size in shared object, consider re-linking`、程式照樣跑；原因是執行檔裡 `level` 是 4 byte、`.so` 裡變成 8 byte，大小對不上。11-01 缺的警告訊息這次寫出來了。**寫錯一處**（不在核心關鍵，所以不扣，但要改正）：`ld.so` **不會**把 8 byte 複製進執行檔——處理 `COPY` 時它只複製**兩邊大小較小的那個**（這裡是執行檔的 4 byte），因為執行檔只留了 4 byte，多寫就蓋到別人。本機實測：把 `.so` 改成 `long level = 0x500000003L;`，執行檔照舊當 `int`，印出執行檔 `level` 的 8 個 byte 是 `03 00 00 00 00 00 00 00`，`get_level()` 回傳 `0x3`——上面 4 byte 的 `05` 沒有被複製過來。所以「上面那 4 byte 沒人用所以沒事」的結論方向對，但原因要改成：那 4 byte 是執行檔 `.bss` 裡 `level` 後面的空間、本來就是 0，`get_level()` 經過 GOT 讀 8 byte 時把它一起讀進來；`.so` 的初值超過 4 byte 就會錯（像上面變成 `0x3`）。
>
> **參考答案**【[第九節第 3 章](../html/c/靜態與動態函式庫-ar與.a、-fPIC與.so、執行時怎麼找到.so.html#3-主程式只寫-extern-int-counter變數放進執行檔複製重定位)〈主程式只寫 `extern int counter;`：變數放進執行檔（複製重定位）〉】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. 執行時 `ld.so` 印警告 `Symbol 'level' has different size in shared object, consider re-linking`，程式照樣跑。
> 2. 原因：執行檔 `.bss` 留給 `level` 的大小（4 byte）是**連結時**照當時的 `.so` 決定的；現在 `.so` 裡的 `level` 是 8 byte，大小對不上，要重新連結。
>
> **詳細說明**：本機實測（`cfg.c` 改成 `long level = 3;` 重做 `libcfg.so`，`setlevel` 不動）：先印那行警告，接著照樣印 `一開始 level = 3`、`get_level() = 7`。印對是運氣：`COPY` 只複製較小的 4 byte；`get_level()` 經過 GOT 到執行檔那格讀 8 byte，多讀的 4 byte 是執行檔 `.bss` 裡 `level` 後面的空間，剛好是 0；初值超過 4 byte、或後面放了別的變數，就會讀錯、寫到別人。這是函式庫通常**不直接給外面用全域變數、而是提供函式**（`get_level()`）的原因之一：函式走 PLT，執行檔不必知道它的大小。

> **參考答案**【[第九節第 15 章](../html/c/靜態與動態函式庫-ar與.a、-fPIC與.so、執行時怎麼找到.so.html#15-ld-還沒讀到-maino怎麼知道誰需要什麼未定義符號清單與---as-needed)〈`ld` 還沒讀到 `main.o`，怎麼知道誰需要什麼〉】

> **核心關鍵**（答到這幾點就算對）：
>
> 1. **不是空的**：`-ltxt` 前面的啟動檔已經讀過，`Scrt1.o` 帶進 `main`、`__libc_start_main` 等未定義符號。
> 2. **沒有 `trim`**：需要 `trim` 的是 `main.c` 的 `.o`，它排在 `-ltxt` 後面、還沒讀到；`ld` 由左往右、不往後看，只用此刻的清單做決定。

#### 函式庫 13-2. 預設下 `gcc -Wall -L. -ltxt main.c -o app_bad` 失敗；把 `-Wl,--no-as-needed` 放在 `-ltxt` 前面（`gcc -Wall -L. -Wl,--no-as-needed -ltxt main.c -o app_no`）就成功。讀到 `libtxt.so` 時兩種模式各做了什麼？`main.o` 要的 `trim` 最後是怎麼被解決的——是 `libtxt.so` 把 `trim` 加進了清單嗎？

```
ubuntu 默認的模式是--as-needed, 這個模式下,當讀到-ltxt trim還沒有出現在清單裏,那libtxt就會被認爲沒用而丟棄,等到走到main發現需要trim符號的定義時,反而找不到定義

加了-Wl,--no-as-needed, 並不是所說libtxt.so把trim加入清單,而是ld不管當下libtxt有沒有用,都會把他計入需求單,然後等走到main的時候需要trim的符號直接拿來解決
```

> **批改**：**對**。三個核心關鍵都有：`--as-needed` 讀到 `libtxt.so` 時清單上沒有它能提供的符號，就丟掉；`--no-as-needed` 不管當下有沒有用都記進 `NEEDED`，讀到 `main.o` 需要 `trim` 時直接拿它的定義解決；不是 `libtxt.so` 把 `trim` 加進清單。用詞小修：清單比對的是「`libtxt.so` 能提供的定義（`trim` 等四個）」對不對得上「清單上缺的符號」——不是「`trim` 有沒有出現在清單裡」這麼窄，不過這題剛好就是 `trim`。
>
> **參考答案**【[第九節第 15 章](../html/c/靜態與動態函式庫-ar與.a、-fPIC與.so、執行時怎麼找到.so.html#15-ld-還沒讀到-maino怎麼知道誰需要什麼未定義符號清單與---as-needed)〈`ld` 還沒讀到 `main.o`，怎麼知道誰需要什麼〉】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. `--as-needed`（預設）：讀到 `libtxt.so` 時看此刻的清單，沒人需要它的符號 → 整個丟掉、不記進 `NEEDED`；後面 `main.o` 要 `trim` 時沒人提供 → `undefined reference`。
> 2. `--no-as-needed`：不看清單，一律留下、記進 `NEEDED`，並**記住它提供的定義**。
> 3. `trim` 是讀到 `main.o` 時，`ld` 用已經記住的 `libtxt.so` 定義當場解決的；不是 `libtxt.so` 把 `trim` 加進清單——清單只放「還沒找到定義的符號」，`.so` 提供的是定義。
>
> **詳細說明**：`nm -D --defined-only libtxt.so` 看得到它提供的四個定義：`is_space`、`to_lower_str`、`to_upper_str`、`trim`。`.so` 本來就有「先記住、後面再用」的能力，順序問題完全是 `--as-needed` 在那一刻「丟掉」造成的。實測：`gcc -Wall -L. -Wl,--no-as-needed -ltxt main.c -o app_no` 成功，`LD_LIBRARY_PATH=. ./app_no` 印 `[hello]`，`readelf -d app_no` 有 `libtxt.so` 與 `libc.so.6` 兩個 `NEEDED`。


> **批改**：**對**。兩個核心關鍵都有：`none_no` 的 `NEEDED` 有 `libtxt.so`、`none_as` 沒有；用不到的 `.so` 沒必要載入、浪費資源。可以補兩點：兩個執行檔都有 `NEEDED libc.so.6`（差別只有 `libtxt.so` 那一列）；多一個用不到的 `NEEDED` 不只是浪費——換到沒裝 `libtxt.so` 的機器，`ld.so` 找不到它，程式整個跑不起來。
>
> **參考答案**【[第九節第 15 章](../html/c/靜態與動態函式庫-ar與.a、-fPIC與.so、執行時怎麼找到.so.html#15-ld-還沒讀到-maino怎麼知道誰需要什麼未定義符號清單與---as-needed)〈`ld` 還沒讀到 `main.o`，怎麼知道誰需要什麼〉】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. `none_no` 有 `libtxt.so` 與 `libc.so.6` 兩個 `NEEDED`；`none_as` 只有 `libc.so.6`。
> 2. `--no-as-needed` 讓用不到的 `.so` 也記進 `NEEDED`，執行時 `ld.so` 就得多找、多載入一個；`--as-needed` 讓沒用到的自動消失。
>
> **詳細說明**：多出來的 `NEEDED` 不只是浪費：換到沒裝 `libtxt.so` 的機器，`ld.so` 找不到它，程式會整個跑不起來，即使根本沒用到。建置系統常把一長串 `-l` 套到每個程式上，`--as-needed` 讓沒用到的自動消失；代價就是 `-l` 一定要寫在用到它的檔案後面。

> 2. `--as-needed`／`--no-as-needed` 只管 `.so`；`.a` 讀到時只拉此刻清單需要的成員，此刻清單沒有 `trim` → 一個都不拉、也不記，之後不回頭。

> **詳細說明**：`.a` 的順序問題不管加什麼選項都存在，只能把 `-ltxt` 寫在 `main.c` 後面，或用 `--start-group … --end-group` 讓群組反覆掃（正文第二節）。`rm libtxt.so` 是因為 `-ltxt` 會先找 `.so`（正文第三節）。

> 1. `ld`：**連結時**（`gcc` 的最後一步，只做一次）合併各 `.o` 的區段、決定每個符號的位址、把 `call` 的洞填上。
> 2. 位址在共享函式庫裡的符號（例如 `puts`），`ld` 填不了真實位址，只寫需求單：`NEEDED libc.so.6`、`INTERP` 路徑。連結完 `ld` 就結束，執行時不會出現。
> 3. `ld.so`：**執行時**（每次執行都做）由核心先啟動，依 `NEEDED` 找到函式庫（含間接依賴）映射進記憶體。
> 4. `ld.so` 把 `puts` 等符號的真實位址填進 `.got`（接線），最後跳到程式的進入點 `_start`（不是 `main`）。
>

```c
    unsigned int len = 5;

```

```sh
$ ./signcmp
```

> 題目：`int n = -1; unsigned int len = 5;`，`n < len` 為什麼是假？只加 `-Wall` 編譯，gcc 會不會提醒你？


>
> **參考答案**【[第四節](../html/c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.html#四無號整數二進位與回繞)〈怎麼確定一個常數的型別？比較時以誰為準？〉、[第六節](../html/c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.html#六有號與無號之間的轉換位元不變換個讀法)、[第七節](../html/c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.html#七陷阱有號和無號混在一起比較)】

> **核心關鍵**（答到這幾點就算對）：
>
> 1. 比較之前做一般算術轉換：`int` 和 `unsigned int` 等級相同，無號贏，`n` 被轉成 `unsigned int`。
> 2. 轉換時位元不變、換成無號讀法：`-1`（`0xffffffff`）變成 4294967295 > 5，所以 `n < len` 為假。

>

> **參考答案**【[第六節](../html/c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.html#六有號與無號之間的轉換位元不變換個讀法)】

>
> **詳細說明**：順序是「先依來源型別擴展到 32 bit，再換成目標型別的讀法」。目標型別 `unsigned int` 是無號的，並不會讓擴展改成補 0——同樣是 `-1`，來源 `signed char` 就補 1。n 個 bit 全是 1 ＝ 2ⁿ − 1，所以 32 bit 全 1 是 2³² − 1；2³¹ − 1（`0x7fffffff`）是有號 `int` 的最大值，最高位是 0，不是這題的答案。

### 組語 1. `mov` 與 `lea`

> `movl (%rdi,%rsi,4), %eax` 和 `leaq (%rdi,%rsi,4), %rax` 括號裡寫的一模一樣。
>
> 盒子 3｜過去的作答：[s1-04 quiz.md 第 1 題](../small-project/s1-04-asm-basics/quiz.md#1-mov-與-lea)、[10-12 複習](./2026-10-12-objdump-hello-ELF-陣列-組語.md)、[10-21 複習](./2026-10-21-字元-objdump-陣列-組語-interp-ELF-GNU.md)、[10-23 複習](./2026-10-23-大複習-hello-gcc-GNU-interp-ELF-objdump-C資料-字元-陣列-組語-組語二-多檔.md)、[10-26 複習](./2026-10-26-hello-GNU-interp-objdump-C資料-字元-陣列-組語-組語二-多檔.md#組語-1-mov-與-lea)

（`%rdi` 是第 1 個參數、`%rsi` 是第 2 個參數。）

#### 組語 1-1. 兩個指令做的事差在哪？

```
mov 是把 這個(%rdi,%rsi,4)記憶體位址那格的值 ,寫入eax
leaq (%rdi,%rsi,4), %rax 這個是把記憶體位址 寫入rax
```

> **批改**：**對**。兩個核心關鍵都有：`movl` 用括號算出的位址**去記憶體讀**那格的 4 byte 放進 `%eax`；`leaq` 只把**算出來的位址數字本身**放進 `%rax`，不讀記憶體。
>
> **參考答案**【[第四節](../html/c/x86-64組合語言入門-暫存器、mov與lea、cmp與條件跳躍.html#四mov-與-lea搬資料-vs-算位址)〈`lea`：只算位址，不碰記憶體〉】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. `movl` 先算出位址 `a + i×4`，再**去記憶體讀**那個位址的 4 byte，放進 `%eax`。
> 2. `leaq` 只把算出來的**位址數字本身**放進 `%rax`，**不讀記憶體**。
>
> **詳細說明**：括號寫法一樣，代表兩個指令算出同一個數字 D ＋ B ＋ I × S；差別只在要不要拿這個數字去存取記憶體。因為 `lea` 根本不存取，位址不合法也不會 segfault。

#### 組語 1-2. 各對應 C 的什麼寫法？

> 題目：`movl (%rdi,%rsi,4), %eax` 和 `leaq (%rdi,%rsi,4), %rax` 各對應 C 的什麼寫法？

```
a是int指標

*(a + b)

(a + b)
```

> **批改**：**對**。`a` 是 `int *`、`b` 是索引時，`movl` 是 `*(a + b)`（也就是 `a[b]`），`leaq` 是 `a + b`（也就是 `&a[b]`）。`mov` 比 `lea` 多做的就是那個 `*`。
>
> **參考答案**【[第四節](../html/c/x86-64組合語言入門-暫存器、mov與lea、cmp與條件跳躍.html#四mov-與-lea搬資料-vs-算位址)〈`lea`：只算位址，不碰記憶體〉】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. `movl (%rdi,%rsi,4), %eax` ↔ `a[i]`（就是 `*(a + i)`，`a` 是 `int *`）。
> 2. `leaq (%rdi,%rsi,4), %rax` ↔ `&a[i]`（就是 `a + i`，結果是指標）。
>
> **詳細說明**：第 3 課：`a[i]` ＝ `*(a + i)`、`&a[i]` ＝ `a + i`；括號裡的 `a + i×4` 是 `a + i` 換算成 byte 的算法。`mov` 比 `lea` 多做的就是那個 `*`。
>
> 純算數的寫法也會編出同一行（本機 `gcc -O2 -S` 實測），所以單看一行 `lea` 分不出是指標還是算數：
>
> ```c
> long  f(long a, long b) { return a + 4*b; }   /* → leaq (%rdi,%rsi,4), %rax */
> int  *h(int *a, long i) { return &a[i]; }     /* → leaq (%rdi,%rsi,4), %rax */
> ```
>
> 跟 `movl` 並排時，參數 `a` 被拿去讀記憶體，表示它是指標，這時 `lea` 讀成 `&a[i]` 才是對的對照。

#### 組語 1-3. 為什麼 gcc 會拿 `lea` 來算 `x * 3` 這種跟位址無關的東西？

`long times3(long x) { return x * 3; }` 用 `gcc -S -O2` 編出來是：

```asm
times3:
	endbr64                       # 給 CPU 的控制流程保護標記，跟計算無關
	leaq	(%rdi,%rdi,2), %rax       # 這一行就是本題要解釋的
	ret                           # 回傳 %rax
```

> 題目：為什麼 gcc 會拿 `lea` 來算 `x * 3` 這種跟位址無關的東西？

```
從上一小題leaq (%rdi,%rsi,4), %rax 這個計算看的出來他把位址算出來的結果直接寫到rax,也就是說他是純數值的加減

而且x*3 = x+ 2x 剛好算法也符合leaq
```

> **批改**：**對**。兩個核心關鍵都有：`lea` 只是把 D ＋ B ＋ I × S 算出來、直接放進暫存器，算的東西不必是位址；`x * 3 ＝ x + x×2` 正好寫成 `(%rdi,%rdi,2)`，一個指令做完。小修：可以明講「`lea` **不碰記憶體**」——這是它能拿來做算術的關鍵（不會去讀一個亂七八糟的位址而 segfault）；另外它算的不只加減，還有 ×1、2、4、8 的乘。
>
> **參考答案**【[第四節](../html/c/x86-64組合語言入門-暫存器、mov與lea、cmp與條件跳躍.html#四mov-與-lea搬資料-vs-算位址)〈`lea` 被拿來做算術〉】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. `lea` 只算 D ＋ B ＋ I × S 這個數字、不碰記憶體，所以算的東西不必是位址。
> 2. `x * 3` ＝ `x + x×2`，正好寫成 `leaq (%rdi,%rdi,2), %rax`，一個指令做完。
>
> **詳細說明**：另外兩個好處：`lea` **不改旗標**（`add` 會），而且結果可以放到另一個暫存器（`add` 只能寫回其中一個運算元）。能一次做到的倍數是 x × S 或 x ＋ x × S：1、2、3、4、5、8、9 倍（作業第 1 題）。

### 組語 10. 暫存器 vs 記憶體運算元

> `mov %rdi,%rax` 和 `mov (%rdi),%rax` 只差一對括號。
>
> 盒子 3｜過去的作答：[s1-04 quiz.md 第 10 題](../small-project/s1-04-asm-basics/quiz.md#10-暫存器-vs-記憶體運算元2026-10-06-課後提問新增)、[10-13 複習](./2026-10-13-組語-字元.md)、[10-23 複習](./2026-10-23-大複習-hello-gcc-GNU-interp-ELF-objdump-C資料-字元-陣列-組語-組語二-多檔.md)、[10-26 複習](./2026-10-26-hello-GNU-interp-objdump-C資料-字元-陣列-組語-組語二-多檔.md#組語-10-暫存器-vs-記憶體運算元)

用到的程式（檔案：[`paren.c`](../small-project/s1-04-asm-basics/paren.c)）：

```c
#include <stdio.h>

__attribute__((noinline)) long copy_val(long x)  { return x; }    /* 回傳 x 本身 */
__attribute__((noinline)) long deref(long *p)    { return *p; }   /* 回傳 p 指向的值 */

int main(void)
{
    long v = 1234;
    printf("%ld %ld\n", copy_val(v), deref(&v));
    return 0;
}
```

```sh
gcc -O2 -g paren.c -o paren
objdump -d --no-show-raw-insn paren
```

```asm
copy_val:
	endbr64
	mov	%rdi,%rax       # 沒有括號（第 1 個參數在 %rdi）
	ret                 # 回傳 %rax
deref:
	endbr64
	mov	(%rdi),%rax     # 有括號
	ret
```

#### 組語 10-1. 兩個指令各拿 `%rdi` 裡的數字做什麼？

```
mov	%rdi,%rax  直接把存在rdi的值寫到rax

mov	(%rdi),%rax 先找出rdi這個記憶體位址那格的值,在寫到rax
```

> **批改**：**對**。沒有括號是把 `%rdi` 裡的**數字本身**複製到 `%rax`、不碰記憶體；有括號是把那個數字**當成位址**，去記憶體讀那裡的 8 byte。
>
> **參考答案**【[第三節](../html/c/x86-64組合語言入門-暫存器、mov與lea、cmp與條件跳躍.html#三指令的文法助憶符大小後綴運算元)〈上表第一列 `(B)` 的 `(%rdi)`：`%rdi` 和 `(%rdi)` 差在哪？〉】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. `mov %rdi,%rax`：把 `%rdi` 裡的**數字本身**複製到 `%rax`，不碰記憶體。
> 2. `mov (%rdi),%rax`：把那個數字**當成位址**，去記憶體讀那裡的 8 byte，放進 `%rax`。
>
> **詳細說明**：暫存器裡永遠只是一個 64 位元的數字；括號的意思是「它是位址，請去記憶體的那裡」。

#### 組語 10-2. 各對應 C 的什麼寫法？

> 題目：`mov %rdi,%rax` 和 `mov (%rdi),%rax` 各對應 C 的什麼寫法？

```
a

*a
```

> **批改**：**對**。沒括號 ↔ 直接用變數的值（`paren.c` 的 `return x;`），有括號 ↔ 取指標指向的值（`return *p;`）。括號就是 C 的 `*`。
>
> **參考答案**【[第三節](../html/c/x86-64組合語言入門-暫存器、mov與lea、cmp與條件跳躍.html#三指令的文法助憶符大小後綴運算元)〈上表第一列 `(B)` 的 `(%rdi)`：`%rdi` 和 `(%rdi)` 差在哪？〉】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. `%rdi` ↔ 用變數的值 `x`（`return x;`）。
> 2. `(%rdi)` ↔ 用指標指向的值 `*p`（`return *p;`）。
>
> **詳細說明**：括號就是 C 的 `*`。筆記的 `paren.c`：`copy_val` 回傳 `x`，`deref` 回傳 `*p`。

#### 組語 10-3. 如果 `%rdi` 裡是 1234，哪一個會 segfault，為什麼？

```
mov	(%rdi),%rax
因爲記憶體位址是1234, 在記憶體區段找不到對映區段或位址,那就會segfault
```

> **批改**：**對**。`mov (%rdi),%rax` 會 segfault：1234（`0x4d2`）被當成位址去讀，行程在那個位址沒有對映任何分頁；第一個只是複製數字，不會出事。用詞小修：「記憶體區段找不到」說成「那個位址**沒有對映任何分頁**」比較準——`maps` 列出的每一段都是對映，`0x4d2` 不落在任何一段裡（最低的一段也在 `0x5555…` 附近）。
>
> **參考答案**【[第三節](../html/c/x86-64組合語言入門-暫存器、mov與lea、cmp與條件跳躍.html#三指令的文法助憶符大小後綴運算元)〈上表第一列 `(B)` 的 `(%rdi)`：`%rdi` 和 `(%rdi)` 差在哪？〉】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. `mov (%rdi),%rax` 會 segfault；第一個只是複製數字，不會。
> 2. 它把 1234（`0x4d2`）當成位址去讀，行程在那個位址**沒有對映任何分頁**，所以收到 SIGSEGV。
>
> **詳細說明**：筆記實測：`set $rdi = 1234` 後 `stepi`，得到 `Program received signal SIGSEGV, Segmentation fault.`。跟第 3 課用壞掉的指標 `*p` 是同一件事。

#### 多檔 1-1. 為什麼編譯器會產生錯的程式？

```
因爲雖然在square算出了10^10=0x2540BE400
但返回到 main 確實讀eax(32位),因爲main不知道square宣告爲long,所以走預設int

```

> **批改**：**對**。兩個核心關鍵都有：編 `main.c` 時看不到 `square` 回傳 `long`，只好照預設（隱式宣告）當成回傳 `int`，所以只讀 `%eax`；`square` 自己算對了（`0x2540be400`），`main` 只拿到低 32 位元 `0x540be400` ＝ 1410065408。可以把根因講得更直接：編譯器**一次只看一個 `.c`**，編 `main.c` 時根本看不到 `mathx.c`。
>
> **參考答案**【[第二節](../html/c/多檔案的C程式-標頭檔、static與extern、連結錯誤與make.html#實驗忘了宣告square100000-印出-1410065408)〈實驗：忘了宣告〉】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. 編譯器一次只看一個 `.c`，編 `main.c` 時看不到 `square` 的宣告和定義。
> 2. 只好照舊規則**隱式宣告**成回傳 `int`，照 `int` 產生程式碼：回傳值只取 `%eax`（低 32 位元）。
>
> **詳細說明**：`square` 本身照 `long` 算，`%rax` ＝ `0x2_540be400`（10000000000）；`main` 只拿 `%eax` ＝ `0x540be400` ＝ 1410065408。**被呼叫的那邊是對的，呼叫的那邊用錯的型別解讀結果**。編譯器是忠實照自己的猜測產生程式，錯在猜測本身。
> gcc 13 對隱式宣告只給 `-Wimplicit-function-declaration` 警告，所以編譯要開 `-Wall`、不能忽略警告（據 gcc 14 的變更說明新版預設改成錯誤，本機未實測）。

#### 多檔 1-2. 為什麼連結器沒有發現兩邊型別不一樣？

```
ld他不會知道c的型別,他只是根據符號的名稱做連結,以及檢查符號是否位global,能不能連
```

> **批改**：**對**。`ld` 只照符號的名字把 `UND square` 接到 `mathx.o` 的 `GLOBAL square`，`.o` 的符號表裡沒有 C 的型別，所以發現不了。
>
> **參考答案**【[第四節](../html/c/多檔案的C程式-標頭檔、static與extern、連結錯誤與make.html#四符號表o-之間靠名字接起來)】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. 連結器只比對符號的**名字**：`main.o` 的 `UND square` 配上 `mathx.o` 的 `GLOBAL square`。
> 2. `.o` 的符號表裡沒有 C 的型別（`Type` 只有 `FUNC`／`OBJECT`／`NOTYPE` 這種），所以兩邊型別不一樣，連結器無從發現。
>
> **詳細說明**：整理成一句：編譯 `main.c` 時看不到 `mathx.c`、編譯 `mathx.c` 時看不到 `main.c`、連結時看不到型別——**沒有任何一個階段同時看得到兩邊的型別**。標頭檔的作用就是在編譯階段把同一份型別資訊帶到兩邊（第三節）。

#### 多檔 1-3. `main.o` 裡的 `cltq` 在這個錯誤裡扮演什麼角色？

```
因爲c代碼寫long r = square(100000); 他負責把返回的int(main認爲的) 轉成long
他與本題造成錯誤的原因沒有什麼關係,應該說就是因爲main預設了square的返回值是int,所以才用了cltq去轉換,前面的原因導致出用
cltq的結果
```

> **批改**：**大致對**。對的部分：`cltq` 是把 `main` 以為的 `int` 回傳值轉成 `long` 存進 `r`；它是「猜成 `int`」造成的**結果**，不是根因。**不對的一句**：「它與本題造成錯誤的原因沒有什麼關係」——它正是**截斷發生的那一條指令**。`call` 回來時 `%rax` 裡其實是正確的 `0x2_540be400`；`cltq` 只看 `%eax`（`0x540be400`），用它的符號擴展**重寫整個 `%rax`**，高 32 位元的 `0x2` 就在這一刻被蓋掉。沒有這一條，正確答案還在 `%rax` 裡。所以它的角色是：根因（猜成 `int`）讓編譯器插了這一條，而這一條把錯誤真正做出來。你在 1-1 寫的「用 `cltq` 轉 `long`…獲得 1410065408」其實就是這件事，只是 1-3 沒有接上。
>
> **參考答案**【[第二節](../html/c/多檔案的C程式-標頭檔、static與extern、連結錯誤與make.html#實驗忘了宣告square100000-印出-1410065408)〈實驗：忘了宣告〉】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. `cltq` 把回傳的 `%eax` 擴展成 `%rax` 存進 `long r`：只保留低 32 位元。（2026-10-24 改判：「符號擴展」移到詳細說明，題目的 100000 補 0 補 1 結果一樣）
> 2. 所以 `square` 留在 `%rax` 高 32 位元的正確結果（`0x2`）被蓋掉，截斷就發生在這一條；它是「猜成 `int`」的結果，不是根因。
>
> **詳細說明**：`cltq` 是**符號擴展**（＝ `movslq %eax,%rax`），高 32 位元照第 31 位元補。為什麼會有這一條：`main` 以為拿到的是 `int`，要存進 `long r`，`int` 轉 `long` 要保留數值（含正負號），所以編譯器插一條符號擴展。如果 `main` 有正確的宣告（回傳 `long`），就不會有 `cltq`，直接 `mov %rax,-0x8(%rbp)`。
>
> 本機實測：把題目 `main.c` 的 `square(100000)` 改成 `square(50000)`，其餘不變、照題目的指令編譯執行，印出 `-1794967296`。50000² ＝ 2500000000 ＝ `0x9502f900`，還沒超過 32 位元，但最高位元是 1（`0x9` ＝ `1001`），`cltq` 補成全 1 → 2500000000 − 2³² ＝ −1794967296。
>
> （2026-10-24 使用者追問「印出來是負數好像不對」，重新實測確認）負數只出現在這一題的寫法（沒有宣告、有 `cltq`）。同樣是 `square(50000)`，換成多檔 2-2 的寫法（`main.c` 引入 `long square(long)` 的標頭檔、`mathx.c` 定義成 `int square(int)`）印的是 **2500000000**：`imul %eax,%eax` 留下 `0x9502f900`，寫 `%eax` 時高 32 位元被清成 0，`main` 照 `long` 讀整個 `%rax`，沒有 `cltq` 去補 1。兩個寫法的 `100000` 都印 1410065408，因為 `0x540be400` 的第 31 位是 0（`0x5` ＝ `0101`），補 0 補 1 結果一樣。差別只有第 31 位是 1 時才看得出來。
