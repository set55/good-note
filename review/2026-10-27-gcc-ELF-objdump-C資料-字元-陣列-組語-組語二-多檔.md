### gcc 2. 為什麼 `-O0` 的組合語言每一圈都在讀寫記憶體（`-4(%rbp)`），而 `-O2` 不會？這個差別對 `gdb` 有什麼影響？

> 盒子 2｜過去的作答：[s1-01 quiz.md gcc 第 2 題](../small-project/s1-01-hello-compile/quiz.md#2-為什麼--o0-的組合語言每一圈都在讀寫記憶體-4rbp而--o2-不會這個差別對-gdb-有什麼影響)、[10-09 複習](./2026-10-09-陣列-gcc-GNU-C資料-interp-ELF.md)、[10-16 複習](./2026-10-16-interp-ELF-gcc-GNU-陣列-C資料.md)、[10-23 複習](./2026-10-23-大複習-hello-gcc-GNU-interp-ELF-objdump-C資料-字元-陣列-組語-組語二-多檔.md)、[10-24 複習](./2026-10-24-gcc-GNU-ELF-objdump-C資料-字元-陣列-組語-組語二-多檔.md)

**題目用到的程式**：`sumto.c`（檔案：[`sumto.c`](../small-project/s1-01-hello-compile/sumto.c)），
用 `gcc -O0 -S sumto.c` 與 `gcc -O2 -S sumto.c` 產生組合語言（`-S`：只編譯到組合語言 `.s` 就停）。

```c
#include <stdio.h>

int sum_to(int n)
{
    int total = 0;
    for (int i = 1; i <= n; i++)
        total += i;
    return total;
}

int answer(void)
{
    return sum_to(100);
}

int main(void)
{
	printf("answer:%d\n", answer());
	return 0;
}
```

`-O0` 的 `sum_to`（本機 gcc 13.3 實際輸出，刪掉 `.cfi`、`.type` 這類組譯指示，右邊是逐行說明）：

```asm
sum_to:
	endbr64                    # 間接跳躍的保護標記（CET），跟這題無關
	pushq	%rbp               # 存起呼叫者的 %rbp
	movq	%rsp, %rbp         # %rbp = 這個函式的堆疊框底
	movl	%edi, -20(%rbp)    # 參數 n（放在 %edi 傳進來）寫到記憶體 -20(%rbp)
	movl	$0, -8(%rbp)       # total = 0，寫到記憶體 -8(%rbp)
	movl	$1, -4(%rbp)       # i = 1，寫到記憶體 -4(%rbp)
	jmp	.L2                # 先跳去檢查條件
.L3:                               # 迴圈本體
	movl	-4(%rbp), %eax     # 從記憶體讀 i 到 %eax
	addl	%eax, -8(%rbp)     # 記憶體裡的 total += %eax
	addl	$1, -4(%rbp)       # 記憶體裡的 i += 1
.L2:                               # 迴圈條件
	movl	-4(%rbp), %eax     # 從記憶體讀 i
	cmpl	-20(%rbp), %eax    # 比較 i 與記憶體裡的 n（算 i − n、設旗標）
	jle	.L3                # i <= n（有號）就回去跑本體
	movl	-8(%rbp), %eax     # 從記憶體讀 total 當回傳值
	popq	%rbp               # 還原 %rbp
	ret
```

`-O2` 的 `sum_to`（同上，實際輸出）：

```asm
sum_to:
	endbr64
	testl	%edi, %edi         # n & n，只為了設旗標
	jle	.L4                # n <= 0 就跳去回傳 0
	leal	1(%rdi), %ecx      # %ecx = n + 1（迴圈的終點）
	xorl	%edx, %edx         # %edx = 0（total）
	andl	$1, %edi           # %edi = n & 1（n 是奇數還是偶數）
	movl	$1, %eax           # %eax = 1（i）
	je	.L3                # n 是偶數就直接進迴圈
	movl	$2, %eax           # n 是奇數：先處理掉 i = 1，i 從 2 開始
	movl	$1, %edx           #           total = 1
	cmpl	%ecx, %eax         #           i 已經到 n + 1 了嗎（n = 1 時）
	je	.L1
.L3:                               # 迴圈本體：一圈加兩個數
	leal	1(%rdx,%rax,2), %edx  # total = total + 2×i + 1（＝ total + i + (i+1)）
	addl	$2, %eax           # i += 2
	cmpl	%ecx, %eax         # i 到 n + 1 了嗎
	jne	.L3
.L1:
	movl	%edx, %eax         # 回傳 total
	ret
.L4:
	xorl	%edx, %edx
	movl	%edx, %eax         # 回傳 0
	ret
```

> 題目：為什麼 `-O0` 的組合語言每一圈都在讀寫記憶體（`-4(%rbp)`），而 `-O2` 不會？這個差別對 `gdb` 有什麼影響？

```
-O0就是沒有做任何最佳化,所以會把區域變數存在堆疊裏(記憶體),每個迴圈都在更新-4(%rbp)
但-O2 就是針對速度做了最佳化,把迴圈擴展,並把區域變數存在了寄存器

-O0 因爲變數存在記憶體內,所以gdb可以打印出變數,而且每一行程式碼可以找到對應一段的組合語言
-O2 因爲使用寄存器的關係,打印變數遇到optimized out是常態,因爲寄存器存的東西常常變化
而且行數會亂跳
```

> **批改**：**對**。抓到：`-O0` 區域變數放在堆疊、每圈都讀寫 `-4(%rbp)`；`-O2` 放在暫存器；gdb 上 `-O0` 每一行對得到一段指令、變數印得出來，`-O2` 行號亂跳、`<optimized out>` 是常態。小修（不扣分）：`<optimized out>` 不是因為「暫存器的內容常變」本身，而是變數**沒有固定的家**——值只在某一段指令裡待在某個暫存器，之後那個暫存器拿去放別的、或整個被算掉，除錯資訊在那個位置就說不出它在哪。
>
> **參考答案**【[第二節](../html/c/gcc最佳化等級-O0到O3差在哪.html#二實驗同一段程式不同等級編出什麼)、[第三節](../html/c/gcc最佳化等級-O0到O3差在哪.html#三為什麼除錯要用--o0)】
>
> **核心關鍵**：
>
> 1. `-O0` 不最佳化、照字面翻譯：每個變數都有**固定的記憶體位置**（`i` 是 `-4(%rbp)`、`total` 是 `-8(%rbp)`），每條語句都從記憶體讀、再寫回記憶體。
> 2. `-O2` 把變數留在**暫存器**（`i` 在 `%eax`、`total` 在 `%edx`），迴圈裡完全不碰記憶體。
> 3. 對 gdb 的影響：`-O0` 原始碼的每一行都對得到一段指令，變數隨時印得出來；`-O2` 行號會跳、指令被重排，變數可能顯示 `<optimized out>`。
>
> **詳細說明**：`-O2` 版裡的 `andl $1, %edi` 不是計數，是在進迴圈前判斷 `n` 的奇偶，好讓迴圈一圈加兩個數。第三節的實測：`-O2` 停下來時跳過了第 3 行；只走兩行，`total` 就已經是 3；被內嵌進 `main` 的那一份變數全是 `<optimized out>`。所以學習、單步除錯用 `-O0 -g`，日常開發用 `-Og -g`。

### gcc 5. 情境題：你在自己的程式裡用 `-O2` 編譯，`gdb` 印某個變數時顯示 `<optimized out>`。你會怎麼處理？如果是在 kernel 裡遇到同樣的狀況，處理方式又有什麼不同？

> 盒子 2｜過去的作答：[s1-01 quiz.md 第 5 題](../small-project/s1-01-hello-compile/quiz.md#5-情境題你在自己的程式裡用--o2-編譯gdb-印某個變數時顯示-optimized-out你會怎麼處理如果是在-kernel-裡遇到同樣的狀況處理方式又有什麼不同)、[10-06 複習](./2026-10-06-字元-interp-ELF-gcc-GNU.md)、[10-16 複習](./2026-10-16-interp-ELF-gcc-GNU-陣列-C資料.md)、[10-23 複習](./2026-10-23-大複習-hello-gcc-GNU-interp-ELF-objdump-C資料-字元-陣列-組語-組語二-多檔.md)、[10-24 複習](./2026-10-24-gcc-GNU-ELF-objdump-C資料-字元-陣列-組語-組語二-多檔.md)

```
改成用-O0編譯,因爲這樣變數就會存在記憶體了,能夠打印出來

kernel不能用-O0編譯,他裏面有太多的死碼與迴圈擴展,所以只能用printk的方法直接把想看的變數print出來
```

> **批改**：**對**。抓到：自己的程式改用 `-O0` 重編；kernel 不能 `-O0`，改用 `printk`。小修（不扣分）：kernel 不能 `-O0` 的理由寫成「太多死碼與迴圈擴展」不準——是 kernel **依賴**編譯器做內嵌（inline）與刪除死碼才編得過，跟迴圈展開無關（10-24 也是這句寫歪）。
>
> **參考答案**【[第三節](../html/c/gcc最佳化等級-O0到O3差在哪.html#三為什麼除錯要用--o0)、[第四節](../html/c/gcc最佳化等級-O0到O3差在哪.html#四跟-kernel-的關係)】
>
> **核心關鍵**：
>
> 1. 自己的程式：用 `-O0 -g`（或 `-Og -g`）重編，變數有固定位置，gdb 就印得出來；不能重編時，加 `printf` 把值印出來。
> 2. kernel：**不能用 `-O0` 編**（kernel 依賴編譯器一定會做的內嵌與刪除死碼才編得過），`<optimized out>` 是常態；只能改用 `printk`、tracing 這類方法觀察，並學會讀最佳化後的組合語言。
>
> **詳細說明**：kernel 不連結 libc，沒有 `printf`，也沒有 stdout；`printk` 的訊息寫進 kernel 的紀錄緩衝區，用 `dmesg` 看。一句話：自己的程式可以「改編譯方式」，kernel 只能「改觀察方式」。

> **參考答案**【[第四節](../html/c/ELF是什麼-可執行與可連結格式的兩種視角.html#四名字的關鍵兩種視角)】
>
> **核心關鍵**：
>

> 題目：`int y = x + 1; return y > x;` 在 `x = INT_MAX` 時，`-O0` 回傳 0、`-O2` 回傳 1。為什麼會這樣？這算不算 gcc 的 bug？kernel 用哪個選項避免這種情況，代價是什麼？

```

-O2: 因爲溢位是未定義的,O2 認爲溢位不會發生,所以 y>x -> x+1 > x 溢位不會發生,此爲真.

不算是,因爲對gcc來說溢位是未定義的

-fno-strict-overflow 這可以在所有可能發生溢位的地方打一個標籤,算到這個地方會實際計算,
代價就是計算量會增加,可能會拖延到一點時間
```

> **批改**：**大致對**。抓到：`-O0` 照算、回繞成 `INT_MIN` → 0；`-O2` 因為溢位未定義、假設不會發生 → 1；不是 bug；選項是 `-fno-strict-overflow`。核心關鍵 4 的「這個選項做了什麼」寫錯：它不是「在可能溢位的地方打標籤、算到那裡實際計算」，而是**改掉語言規則**——讓有號溢位一律照二補數回繞、變成有定義的行為，編譯器就不能再用「不會溢位」去推論；代價也不是「計算量增加」，是少了依賴這個假設的最佳化。另一個小修（同 10-24）：未定義是 **C 標準**規定的，不是「對 gcc 來說」。
>
> **參考答案**【[第八節](../html/c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.html#八溢位無號回繞有號是未定義行為)】
>
> **核心關鍵**：
>
> 1. 有號溢位是未定義行為（UB），C 標準允許編譯器**假設它不會發生**。
> 2. `-O0` 照字面算，`INT_MAX + 1` 回繞成 `INT_MIN`，`y > x` 為假 → 0；`-O2` 依這個假設推論 `x + 1` 一定大於 `x`，直接回傳 1。
> 3. 不是 gcc 的 bug：標準對發生 UB 的程式沒有任何要求，兩種結果都合法。
> 4. kernel 用 `-fno-strict-overflow`（等於 `-fwrapv -fwrapv-pointer`），讓溢位照二補數回繞、變成有定義的行為；代價是少了依賴「不會溢位」的最佳化，程式可能稍慢。
>
> **詳細說明**：連 `-O0` 也不保證照字面算：把同一件事寫成一行 `return x + 1 > x;`，`-O0` 也回傳 1，因為 gcc 在最佳化之前的化簡階段就把它改掉了。所以本題的 `bigger` 才故意拆成兩行。

> 題目：（8 位元算 4 − 9）如果 CPU 是用加法器算（D + S 反轉 + 1），加法器有沒有往外進位，跟 CF 是什麼關係？

```
0x4 + 反轉(0x9) + 1 = 0x4 + 反轉(00001001) + 1 = 0x4 + 11110110 + 1 = 0x4 + 0xf6 + 1 = 0xfb
沒有往外進位, 故可得知 有借位 , 沒往外進位 CF 1

CF是否爲1的判斷就看是否有借位 或 是否有往外進位
```

> **批改**：**對**。抓到：4 ＋ `0xf6` ＋ 1 ＝ `0xfb`，沒有往外進位 → 有借位 → CF ＝ 1。小修（不扣分）：最後一句「看是否有借位或是否有往外進位」容易讀成「有進位也是 CF 1」——**減法**時兩者相反：沒進位 ＝ 有借位 ＝ CF 1，有進位 ＝ 沒借位 ＝ CF 0；「有進位 ＝ CF 1」只在加法成立。
>
> **參考答案**【[第五節](../html/c/x86-64組合語言入門-暫存器、mov與lea、cmp與條件跳躍.html#五旗標與條件跳躍cmp-只負責比跳不跳由下一個指令決定)〈上面③：3 − 5 在 CPU 裡實際上是怎麼算的？〉的「電路上其實是用加法做的」】

> **核心關鍵**：
>
> 1. 4 ＋ (9 反轉 ＝ 246) ＋ 1 ＝ 251，沒超過 255 → 加法器**沒有**往外進位。
> 2. 減法時進位跟借位**相反**：x86 把加法器的進位反過來存進 CF，所以「沒進位」→ CF ＝ 1（借位了）。
>
> **詳細說明**：對照 5 − 3：5 ＋ 252 ＋ 1 ＝ 258，有進位 → CF ＝ 0（不用借）。ARM 等架構減法時直接存加法器的進位，CF 的意思剛好相反。

> **批改**：**對**。抓到：進位一路傳進第 7 位；第 7 位沒有再往外進。
>
> **參考答案**【[第五節](../html/c/x86-64組合語言入門-暫存器、mov與lea、cmp與條件跳躍.html#五旗標與條件跳躍cmp-只負責比跳不跳由下一個指令決定)〈上面⑦：127 + 1 明明有「進位」，為什麼 CF 還是 0？〉】
>
> **核心關鍵**：
>
> 1. 有：`0x01 + 0x7f` 從第 0 位起每一位都「留 0、進 1」，進位一路傳進第 7 位。
> 2. 沒有：第 7 位是 0 + 0 + 1 ＝ 1，留下 1、不再往外進。

#### 組語 18-2. CF、OF 各是多少，為什麼「有進位」不等於 CF = 1？

> 題目：（承 18-1，8 位元的 `0x01 + 0x7f`）CF、OF 各是多少，為什麼「有進位」不等於 CF = 1？

```
CF = 0, 因爲他沒有借位 也沒有往外進位,有進位是有,但沒有往更高第8委員進位
OF = 1, 因爲有溢位
```

> **批改**：**對**（2026-10-27 改判：原判大致對，扣在「OF ＝ 1 只寫有溢位、沒寫 127 ＋ 1 超出範圍」；使用者指出題目的「為什麼」只問 CF，OF 只問值，改判為對，OF 的理由移到詳細說明）。抓到：CF ＝ 0，因為 CF 只看從第 7 位往外的那一次進位，中間的進位不算；OF ＝ 1。小修（不扣分）：加法沒有「借位」，CF 這裡寫「沒有從第 7 位往外進位」就夠了。
>
> **參考答案**【[第五節](../html/c/x86-64組合語言入門-暫存器、mov與lea、cmp與條件跳躍.html#五旗標與條件跳躍cmp-只負責比跳不跳由下一個指令決定)〈上面⑦：127 + 1 明明有「進位」，為什麼 CF 還是 0？〉】
>
> **核心關鍵**：
>
> 1. CF ＝ 0：CF 只記**從第 7 位往外**的那一次進位，中間各位的進位不算；無號 127 + 1 ＝ 128 ≤ 255，裝得下。
> 2. OF ＝ 1。
>
> **詳細說明**：題目的「為什麼」只問 CF，OF 只問值（2026-10-27 改判後把 OF 的理由移出核心關鍵）。OF ＝ 1 的理由：當**有號數**算，127 + 1 ＝ +128 超出 −128～127，留下的 `0x80` 讀成 −128。

#### 組語 18-3. 再比較 `0x05 + 0x03`：它也有進位，為什麼兩個旗標都是 0？

```
CF要往外進位纔會是1, 所以05 + 03 沒有 故 0
OF要有溢位,一樣沒有 所以0
```

> **批改**：**對**。抓到：沒有從第 7 位往外進位 → CF ＝ 0；當有號數也沒溢位 → OF ＝ 0。小修（不扣分，同 10-26）：可以點出 `0x05 + 0x03` 的進位只在低位，**根本沒傳到第 7 位**，這是它跟 18-1 不同的地方。
>
> **參考答案**【[第五節](../html/c/x86-64組合語言入門-暫存器、mov與lea、cmp與條件跳躍.html#五旗標與條件跳躍cmp-只負責比跳不跳由下一個指令決定)〈上面⑦：127 + 1 明明有「進位」，為什麼 CF 還是 0？〉】
>
> **核心關鍵**：
>
> 1. `0x05 + 0x03` 的進位只發生在第 1～3 位，**沒有傳到第 7 位**：進第 7 位 0、出第 7 位 0 → CF ＝ 0、OF ＝ 0。
> 2. 無號 8、有號 8 都裝得下；「中間有進位」本身不影響任何旗標。

#### 組語 18-4. 最後用「進到第 7 位的進位」和「第 7 位往外的進位」說明 `0xff + 0x01` 的 OF 為什麼是 0。

```
OF爲0 就是有號沒有產生溢位
現在看 進到第7位的進位是1, 第7爲往外進位也是 1
1xor1 = 0算出來of也是0, 而且他也沒有溢位
```

> **批改**：**對**（10-26 不完整的這次對了）。抓到：進到第 7 位的進位 1、第 7 位往外的進位 1，1 XOR 1 ＝ 0 → OF ＝ 0；對照有號的說法也沒溢位。小修（不扣分）：有號那邊寫出算式 −1 ＋ 1 ＝ 0 更清楚。
>
> **參考答案**【[第五節](../html/c/x86-64組合語言入門-暫存器、mov與lea、cmp與條件跳躍.html#五旗標與條件跳躍cmp-只負責比跳不跳由下一個指令決定)〈上面那條規則：OF 不是看溢位嗎？為什麼又變成看進位？〉】
>
> **核心關鍵**：
>
> 1. `0xff + 0x01`：進到第 7 位的進位是 1，第 7 位 1 + 0 + 1 ＝ 10，往外的進位也是 1；兩個一樣 → OF ＝ 0。
> 2. 對照有號的說法：−1 + 1 ＝ 0，裝得下，沒溢位；CF ＝ 1 只代表無號的 255 + 1 裝不下。
>
> **詳細說明**：OF 的定義一直是「當有號數裝不下」；「進 XOR 出」是 CPU 算出它的方法。為什麼會一致：同號相加時「進 ≠ 出」剛好就是正負號被改壞（兩個正數 `0+0` 卻收到進位，第 7 位變 1 ＝ 結果變負；兩個負數 `1+1` 卻沒收到進位，第 7 位留 0 ＝ 結果變正）；一正一負相加時第 7 位是 `1+0`，收到進位就往外進、沒收到就不進，「進」和「出」一定相同，也一定不溢位。拿 18 題的三組對一次：`0x01+0x7f` 進 1 出 0 → OF 1；`0x05+0x03` 進 0 出 0 → OF 0；`0xff+0x01` 進 1 出 1 → OF 0。

### 組語二 1. `call` 與 `ret`

> 盒子 2｜過去的作答：[s1-05 quiz.md 第 1 題](../small-project/s1-05-asm-calls/quiz.md#1-call-與-ret)、[10-23 複習](./2026-10-23-大複習-hello-gcc-GNU-interp-ELF-objdump-C資料-字元-陣列-組語-組語二-多檔.md)、[10-24 複習](./2026-10-24-gcc-GNU-ELF-objdump-C資料-字元-陣列-組語-組語二-多檔.md)

`frame.c` 的 `main` 裡有 `call 1149 <add3>`（位址 `0x1194`），下一條指令在 `0x1199`；`add3` 最後一條是 `ret`。

完整原始碼（檔案：[`frame.c`](../small-project/s1-05-asm-calls/frame.c)）與編譯指令：

```c
#include <stdio.h>

long add3(long a, long b, long c)
{
    long s = a + b;
    return s + c;
}

int main(void)
{
    long r = add3(1, 2, 3);
    printf("%ld\n", r);
    return 0;
}
```

```sh
gcc -O0 -g -fno-asynchronous-unwind-tables frame.c -o frame
objdump -d --no-show-raw-insn frame
```

```asm
# main
1194:	call   1149 <add3>
1199:	mov    %rax,-0x8(%rbp)
# add3 的最後
1177:	pop    %rbp
1178:	ret
```

#### 組語二 1-1. `call` 做了哪兩件事？

```
%rsp 減了8byte,存上add3的返回位址
然後跳到add3
```

> **批改**：**對**。抓到：`%rsp` 減 8、寫進返回位址，再跳到 `add3`。
>
> **參考答案**【[第三節](../html/c/x86-64組合語言入門二-call與ret、堆疊框、參數與呼叫慣例.html#三call-與-ret用-gdb-一條一條走)】
>
> **核心關鍵**：
>
> 1. 把**返回位址**（`call` 下一條指令的位址 `0x1199`）推進堆疊：`%rsp` 減 8，寫進新的頂端。
> 2. 跳到 `add3`（`%rip` 變成 `add3` 的位址）。
>
> **詳細說明**：`frame.c` 實測：`call` 之後 `%rsp` 從 `d410` 變成 `d408`，`d408` 裡是 `0x555555555199`（PIE 載入後的 `0x1199`）。

#### 組語二 1-2. `ret` 做了什麼？

```
ret 讀了 %rsp那格的返回位址,然後rsp清除返回位址(+8byte)
然後跳到返回位址
```

> **批改**：**對**。抓到：取 `%rsp` 指的那格當位址跳過去、`%rsp` 加 8。小修（同 10-24）：返回位址沒有被「清除」，那格內容還在，只是 `%rsp` 移過去、之後會被覆蓋。
>
> **參考答案**【[第三節](../html/c/x86-64組合語言入門二-call與ret、堆疊框、參數與呼叫慣例.html#三call-與-ret用-gdb-一條一條走)】
>
> **核心關鍵**：
>
> 1. 把堆疊頂端那 8 byte 當成位址，放進 `%rip`（跳過去）。
> 2. `%rsp` 加 8（返回位址被拿走）。
>
> **詳細說明**：`ret` ＝ `pop` 到 `%rip`。實測 `ret` 之後 `%rsp` 回到 `d410`，跟 `call` 之前一模一樣。

#### 組語二 1-3. `ret` 怎麼知道要回到 `0x1199`？

```
ret不知道,ret只負責從%rsp那格拿值,不管值是什麼他都會當作返回位址跳過去
```

> **批改**：**對**。抓到：`ret` 不知道，只拿 `%rsp` 指的那格。
>
> **參考答案**【[第三節](../html/c/x86-64組合語言入門二-call與ret、堆疊框、參數與呼叫慣例.html#三call-與-ret用-gdb-一條一條走)】
>
> **核心關鍵**：
>
> 1. `call` 把 `0x1199` 推進堆疊，存在 `%rsp` 指的那格記憶體裡。
> 2. `ret` 不知道呼叫者是誰，只是取堆疊頂端那 8 byte 當位址。
>
> **詳細說明**：所以 `add3` 在 `ret` 之前必須把 `%rsp` 還原到放返回位址的那一格：`pop %rbp` 把序言推的舊 `%rbp` 拿走，頂端就又是 `0x1199`。函式裡 `push` 和 `pop` 沒配好，`ret` 就會跳錯。

#### 組語二 1-4. 如果 `add3` 裡有個陣列越界寫入，剛好蓋掉了堆疊上的返回位址，`ret` 會發生什麼事？

```
有可能會跳到沒有權限 的記憶體區,甚至根本沒有對應的區段,報segfault
```

> **批改**：**對**。抓到：`ret` 照樣把被蓋掉的值當位址跳過去，通常 segfault。
>
> **參考答案**【[第三節](../html/c/x86-64組合語言入門二-call與ret、堆疊框、參數與呼叫慣例.html#三call-與-ret用-gdb-一條一條走)】
>
> **核心關鍵**：
>
> 1. `ret` 不檢查，照樣把被蓋掉的值當成位址跳過去。
>
> **詳細說明**：跳到亂的地方，通常是 segfault 當掉（那個位址沒有對映，或不能執行）。有堆疊保護時，函式返回**之前**檢查金絲雀，印 `stack smashing detected` 中止；關掉保護就真的走到 `ret`，返回時 segfault。如果蓋上去的值是攻擊者刻意挑的位址，`ret` 就會跳去執行攻擊者要的程式碼——這是緩衝區溢位攻擊的原理。

### 組語二 4. callee-saved 與對齊

> 盒子 2｜過去的作答：[s1-05 quiz.md 第 4 題](../small-project/s1-05-asm-calls/quiz.md#4-callee-saved-與對齊)、[10-23 複習](./2026-10-23-大複習-hello-gcc-GNU-interp-ELF-objdump-C資料-字元-陣列-組語-組語二-多檔.md)、[10-24 複習](./2026-10-24-gcc-GNU-ELF-objdump-C資料-字元-陣列-組語-組語二-多檔.md)

下面兩個函式用 `-O2` 編譯（`g` 只有宣告）。

```c
/* saved.c */                          /* noret.c */
long g(long x);                         long g(long x);

long f(long x)                          long f(long x)
{                                       {
    long y = g(x);                          long y = g(x);
    return x + y;                           return y * 2;
}                                       }
```

完整原始碼（檔案：[`saved.c`](../small-project/s1-05-asm-calls/saved.c)、[`noret.c`](../small-project/s1-05-asm-calls/noret.c)；`g` 只有宣告，只編成 `.o`）與編譯指令：

```sh
gcc -O2 -c -fno-asynchronous-unwind-tables saved.c -o saved.o
gcc -O2 -c -fno-asynchronous-unwind-tables noret.c -o noret.o
objdump -d --no-show-raw-insn saved.o noret.o
```

```asm
# saved.c 的 f                          # noret.c 的 f
push   %rbx                             sub    $0x8,%rsp
mov    %rdi,%rbx                        call   g
call   g                                add    $0x8,%rsp
add    %rbx,%rax                        add    %rax,%rax
pop    %rbx                             ret
ret
```

#### 組語二 4-1. 為什麼 `saved.c` 的 `f` 要 `push %rbx`，而不是讓 `x` 留在 `%rdi`？

```
1. rdi是caller-saved,因爲進g以後有可能被改,所以f找rbx存他
2. 但rbx本身是callee-saved,而f本身也是callee,所以他也要存rbx,因此存到堆疊上
3. x(rdi)在f返回還要用,因爲存好了,這個時候就可以直接從rbx拿,而不用擔心rdi被改掉
```

> **批改**：**對**。抓到：`%rdi` 是 caller-saved、`g` 可能改掉；`x` 搬到 callee-saved 的 `%rbx`；`f` 借用 `%rbx` 也要先備份。
>
> **參考答案**【[第六節](../html/c/x86-64組合語言入門二-call與ret、堆疊框、參數與呼叫慣例.html#六誰負責保存暫存器以及-16-byte-對齊)〈實驗：要跨過 `call` 保存的值放哪裡〉】
>
> **核心關鍵**：
>
> 1. `x` 在 `g` 回來後還要用，但 `%rdi` 是 caller-saved，`g` 可能改掉它。
> 2. 所以把 `x` 搬到 callee-saved 的 `%rbx`：ABI 保證 `g` 回來時 `%rbx` 不變。
> 3. `f` 借用 `%rbx` 也要對自己的呼叫者負責：開頭 `push %rbx`、返回前 `pop %rbx` 還原。
>
> **詳細說明**：對照 `noret.c`：`call` 之後不再用 `x`，就不需要 `%rbx`。`saved.c` 的 `push %rbx` 還順便把 `%rsp` 挪了 8 byte，同時滿足 16 byte 對齊（4-2）。

#### 組語二 4-2. `noret.c` 的 `f` 不需要保存任何值，為什麼還要 `sub $0x8,%rsp`？

```
1. 首先call本身會空出rsp的空間存返回位址,要是rsp一開始沒有push或sub預留空間 區域變數有可能被返回位址改掉
2. save.c有push,而noret有sub
3. 另外之所以-8byte,是因爲 g是未知定義的,根據ABI, 在進入call之前rsp的位址需要是16的倍數,f本身是被人call的,所以他已經
-8byte了,還需要-8byte纔會是16byte的倍數
```

> **批改**：**對**。抓到：ABI 規定 `call` 時 `%rsp` 要是 16 的倍數；`call f` 推了 8 byte，再補 8 才對齊。兩處要修（不扣分）：(1) 第 1 點這裡用不上：`f` 沒有區域變數，沒有東西會被 `call g` 推的返回位址蓋掉（那是組語二 2-3 紅區的情況）；(2)「因為 `g` 是未知定義的」跟對齊無關，**每一次** `call` 都要對齊（10-24 同一個小修）。
>
> **參考答案**【[第六節](../html/c/x86-64組合語言入門二-call與ret、堆疊框、參數與呼叫慣例.html#六誰負責保存暫存器以及-16-byte-對齊)〈上面的 `sub $0x8,%rsp`：16 byte 對齊〉】
>
> **核心關鍵**：
>
> 1. ABI 規定：執行 `call` 的那一刻，`%rsp` 必須是 16 的倍數。
> 2. 呼叫 `f` 的人照規定對齊，但 `call f` 推了 8 byte 返回位址，進到 `f` 時 `%rsp` 是「16 的倍數 − 8」。
> 3. `f` 要 `call g`，必須再挪 8 byte：沒東西要存，就用 `sub $0x8,%rsp` 單純挪。
>
> **詳細說明**：要 16 的原因：有些指令（例如 SSE 的 `movaps`）要求記憶體位址是 16 的倍數，否則會當掉。

### 多檔 3. `static` 的兩種意思

> 盒子 2｜過去的作答：[s1-06 quiz.md 第 3 題](../small-project/s1-06-multi-file/quiz.md#3-static-的兩種意思)、[10-23 複習](./2026-10-23-大複習-hello-gcc-GNU-interp-ELF-objdump-C資料-字元-陣列-組語-組語二-多檔.md)、[10-24 複習](./2026-10-24-gcc-GNU-ELF-objdump-C資料-字元-陣列-組語-組語二-多檔.md)

`static` 寫在函式外面和寫在函式裡面，各改變了什麼？用下面兩個例子說明：(a) `a.c`、`b.c` 各有一個 `static int helper(void)`，為什麼能一起連結，拿掉 `static` 為什麼就 `multiple definition`？(b) `next_id()` 呼叫三次回傳 1、2、3，`plain_id()` 每次都是 1，兩個 `n` 各放在記憶體的哪裡？

```c
/* a.c（b.c 一樣，只是 helper 回傳 2、函式叫 b_value） */
static int helper(void)
{
    return 1;
}

int a_value(void)
{
    return helper();
}
```
```c
/* nextid.c 的兩個函式 */
int next_id(void)
{
    static int n = 0;
    n = n + 1;
    return n;
}

int plain_id(void)
{
    int n = 0;
    n = n + 1;
    return n;
}
```

#### 多檔 3-1. `static` 寫在函式外面和寫在函式裡面，各改變了什麼？

```
static 在函式外面: 這個函式變成只有當前這個檔案能調用,用readelf -s 看bind會是local,不可以外面的符號鏈接
static 在函式內部: 這個變數不能像是區域變數一樣可以直接在函式的堆疊處理,而是要用.bss或.data儲存,並且不會在函式結束後被清除
```

> **批改**：**對**。抓到：外面 → `LOCAL`、只在這個檔案；裡面 → 放 `.bss`／`.data`、函式結束後不消失。小修（不扣分）：函式裡的 `static`，名字仍然只有那個函式看得到。
>
> **參考答案**【[第五節](../html/c/多檔案的C程式-標頭檔、static與extern、連結錯誤與make.html#五static兩種完全不同的意思)】
>
> **核心關鍵**：
>
> 1. 函式外面：改的是名字的**可見範圍**——只在這個 `.c` 有效，符號變成 `LOCAL`，連結器不拿它跟別的檔案配對。
> 2. 函式裡面：改的是**儲存期間**——不放堆疊，放在固定記憶體（`.bss`／`.data`），整個程式執行期間只有一份，值留到下一次呼叫；名字仍然只在那個函式裡看得到。

#### 多檔 3-2. (a) `a.c`、`b.c` 各有一個 `static int helper(void)`，為什麼能一起連結，拿掉 `static` 為什麼就 `multiple definition`？

```
因爲這兩個的bind都是local,也就是他們不會跟彼此連接,應該說他們根本不會連接,只有本檔範圍可以使用.

因爲兩個的bind會變global,也就是ld真的會把他們連接,結果發現兩個都有定義了就報了multiple definition的問題
```

> **批改**：**對**。抓到：`LOCAL` 不拿去配對；拿掉後兩個 `GLOBAL` 定義 → `multiple definition`。
>
> **參考答案**【[第五節](../html/c/多檔案的C程式-標頭檔、static與extern、連結錯誤與make.html#檔案層級的-static讓名字變成-local)〈檔案層級的 `static`〉】
>
> **核心關鍵**：
>
> 1. 有 `static`：兩個 `helper` 都是 `LOCAL`，連結器做符號解析時只用 `GLOBAL` 配對，所以同名也不衝突。
> 2. 拿掉 `static`：兩個 `.o` 各有一個 `GLOBAL` 的 `helper` 定義 → 同名的 `GLOBAL` 定義有兩個 → `multiple definition`。
>
> **詳細說明**：兩份內容不一樣（回傳 1 和 2）不是重點；就算一模一樣，有兩個同名的 `GLOBAL` 定義也是錯。

#### 多檔 3-3. (b) `next_id()` 呼叫三次回傳 1、2、3，`plain_id()` 每次都是 1，兩個 `n` 各放在記憶體的哪裡？

```
next_id的n放在.bss裏面 因爲他的初值是0, 如果是非0會放在.data
plain_id的n是放在函式堆疊裏,也就是stack,所以每次函式重call, n都會被刷新
```

> **批改**：**對**。抓到：`.bss`（初值 0；非 0 放 `.data`）vs 堆疊。
>
> **參考答案**【[第五節](../html/c/多檔案的C程式-標頭檔、static與extern、連結錯誤與make.html#函式裡的-static不放堆疊值留到下一次)〈函式裡的 `static`〉】
>
> **核心關鍵**：
>
> 1. `next_id` 的 `n`：固定記憶體 `.bss`（初值 0），只初始化一次、值留著，所以 1、2、3。
> 2. `plain_id` 的 `n`：堆疊框裡（`-0x4(%rbp)`），每次呼叫都重新設成 0，所以每次都是 1。

### 多檔 4. 標頭檔裡的 `long hits;`

> 盒子 2｜過去的作答：[s1-06 quiz.md 第 4 題](../small-project/s1-06-multi-file/quiz.md#4-標頭檔裡的-long-hits)、[10-23 複習](./2026-10-23-大複習-hello-gcc-GNU-interp-ELF-objdump-C資料-字元-陣列-組語-組語二-多檔.md)、[10-24 複習](./2026-10-24-gcc-GNU-ELF-objdump-C資料-字元-陣列-組語-組語二-多檔.md)

下面的 `hits.h` 被 `hits.c` 和 `hits_main.c` 都 `#include`，兩個 `.c` 都沒有再寫 `hits` 的定義。本機 gcc 13 連結時出現 `multiple definition of 'hits'`。為什麼？已經有 include guard 了，為什麼沒擋住？該怎麼改（標頭檔寫什麼、哪裡寫什麼）？為什麼同樣的程式碼在舊版 gcc 上可以連結？

```c
/* hits.h */
#ifndef HITS_H
#define HITS_H

long hits;
void hit(void);

#endif
```
```c
/* hits.c */
#include "hits.h"

void hit(void)
{
    hits = hits + 1;
}
```
```c
/* hits_main.c */
#include <stdio.h>
#include "hits.h"

int main(void)
{
    hit();
    hit();
    hit();
    printf("hits = %ld\n", hits);
    return 0;
}
```
編譯與連結：`gcc -c hits.c hits_main.c && gcc -o hits hits_main.o hits.o`

#### 多檔 4-1. 為什麼？

```
因爲他們都是各自編譯成object file, 所以兩個都include hits.h 裏面的hits也被定義了.所以當ld在連接兩個.o檔的時候自然就發現hits被重複定義了.
```

> **批改**：**對**。抓到：兩個 `.c` 都貼進 `long hits;`，各有一份定義，連結時重複。
>
> **參考答案**【[第六節](../html/c/多檔案的C程式-標頭檔、static與extern、連結錯誤與make.html#忘了-extern每個-c-都有一份定義)〈忘了 `extern`：每個 `.c` 都有一份定義〉】
>
> **核心關鍵**：
>
> 1. `long hits;`（沒有 `extern`、沒有初值）是暫定定義，實際上就是**定義**。
> 2. 標頭檔被貼進兩個 `.c`，兩個 `.o` 各有一個 `GLOBAL` 的 `hits` → 連結器看到兩個同名定義 → `multiple definition`。

#### 多檔 4-2. 已經有 include guard 了，為什麼沒擋住？

```
include只能防止單一檔案編譯成object 重複引用.h, 所以include 自然沒擋住.話說重複定義是發生在ld連結時,本來就與include無關
```

> **批改**：**對**。抓到：guard 只管同一個編譯單元；重複定義發生在連結時。
>
> **參考答案**【[第六節](../html/c/多檔案的C程式-標頭檔、static與extern、連結錯誤與make.html#忘了-extern每個-c-都有一份定義)〈忘了 `extern`：每個 `.c` 都有一份定義〉最後一段】
>
> **核心關鍵**：
>
> 1. include guard 只防止**同一個編譯單元**裡被貼兩次（`HITS_H` 這個巨集只在編譯這一個 `.c` 的期間有效）。
> 2. `hits.c` 和 `hits_main.c` 是分開編譯的兩個編譯單元，各貼一次是正常的；錯誤發生在連結時兩個 `.o` 之間，guard 管不到。

#### 多檔 4-3. 該怎麼改（標頭檔寫什麼、哪裡寫什麼）？

```
hits.h 改成用extern ,代表全域宣告
extern long hits;

hits.c 增加 hits的定義
long hits = 0;
```

> **批改**：**對**。
>
> **參考答案**【[第六節](../html/c/多檔案的C程式-標頭檔、static與extern、連結錯誤與make.html#六extern全域變數的宣告與定義)〈整理：全域變數放哪裡〉】
>
> **核心關鍵**：
>
> 1. 標頭檔寫 `extern long hits;`：宣告，不配置空間，幾個 `.c` 引入都沒關係。
> 2. **恰好一個 `.c`**（`hits.c`）寫定義 `long hits = 0;`，而且這個 `.c` 也引入 `hits.h`，讓編譯器檢查宣告與定義的型別一致。

#### 多檔 4-4. 為什麼同樣的程式碼在舊版 gcc 上可以連結？

```
這是因爲舊版本的gcc默認打開-fcommon, 可以讓helper符號變成com, 這樣所有相同符號的定義就可以統一 
```

> **批改**：**對**。抓到：舊版 gcc（10 以前）預設 `-fcommon`，變成 common 符號（`COM`）、合併成一份。筆誤：「helper 符號」應是 `hits`。
>
> **參考答案**【[第六節](../html/c/多檔案的C程式-標頭檔、static與extern、連結錯誤與make.html#忘了-extern每個-c-都有一份定義)〈`-fcommon`：舊程式為什麼這樣寫也能動〉】
>
> **核心關鍵**：
>
> 1. gcc 10 以前預設 `-fcommon`：沒有初值的全域變數被標成 **common 符號**（`Ndx` 是 `COM`，`nm` 印 `C`），不是一般的定義。
> 2. 連結器遇到好幾個同名的 common 符號會**合併成一份**，不報錯，兩個檔案共用同一個 `hits`。
>
> **詳細說明**：gcc 10 起預設改成 `-fno-common`。正確修法是補 `extern`（4-3），不是加 `-fcommon`。
