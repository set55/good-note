## 字元：[字元是什麼-char就是1byte的整數與ASCII和UTF-8](../html/c/字元是什麼-char就是1byte的整數與ASCII和UTF-8.html)

### 字元 1. `char c = 'A';` 和 `char c = 65;` 存進記憶體的東西一樣嗎？為什麼 `printf` 用 `%c` 印出 `A`、用 `%d` 印出 65？

> 盒子 3｜過去的作答：[s1-02 quiz.md 字元第 1 題](../small-project/s1-02-data-repr/quiz.md#1-char-c--a-和-char-c--65-存進記憶體的東西一樣嗎為什麼-printf-用-c-印出-a用-d-印出-65)、[10-05 複習](./2026-10-05-gcc-陣列-GNU-C資料-字元.md)

```
一樣
printf %c 是把他用ascii轉出來
%d就是直接把整數打出來
```

> **批改**：**對**（盒子 3 → 4）。抓到：存進去的東西一樣；`%c`、`%d` 只是 `printf` 對同一個數字的兩種印法。小補：說「一樣」時直接講出**一樣是什麼**——兩種寫法存進去的都是數字 65（`0x41`），`'A'` 只是寫 65 的另一種方式。
>
> **參考答案**【[第一節](../html/c/字元是什麼-char就是1byte的整數與ASCII和UTF-8.html#一字元就是一個數字)】
>
> 核心關鍵：
> 1. 一樣：記憶體裡都是同一個數字 65（`0x41`），`'A'` 只是寫 65 的另一種方式。
> 2. 印成什麼由 `printf` 的格式決定：`%c` 把這個數字當編碼查表、印出對應的字；`%d` 把它印成十進位數字。
>
> 詳細說明：`char` 就是 1 byte 的整數，記憶體裡沒有「這是字元」的標記。同一個 byte 拿去做加減法也可以，`'A' + 1` 就是 66，用 `%c` 印是 `B`。

## objdump：[objdump能不能代替ldd找依賴庫-需求單與實際載入](../html/c/objdump能不能代替ldd找依賴庫-需求單與實際載入.html)

### objdump 4. 情境題：同事傳來一支 ARM 開發板用的執行檔，問你「它需要哪些函式庫」。你在自己的 x86-64 電腦上該用哪個工具？用 `ldd` 會發生什麼事，為什麼？

> 盒子 1｜過去的作答：[s1-01 quiz.md 第 4 題](../small-project/s1-01-hello-compile/quiz.md#4-情境題同事傳來一支-arm-開發板用的執行檔問你它需要哪些函式庫你在自己的-x86-64-電腦上該用哪個工具用-ldd-會發生什麼事為什麼)、[10-04 複習](./2026-10-04-字元-C資料-objdump-hello-ELF.md)、[10-08 複習](./2026-10-08-字元-C資料-objdump-hello-ELF-陣列.md)、[10-12 複習](./2026-10-12-objdump-hello-ELF-陣列-組語.md)

```
用objdump -p 直接看dynamic section 動態載入哪些函式庫
ldd 會直接拉起interpreter,並且載入直接與間接的函式庫,以及linux虛擬的函式庫, 因爲ldd確實啓動了interpreter讓他執行載入的工作
```

> **批改**：**不完整**（盒子 1 → 1）。工具方向對：只讀檔案、不執行（`objdump -p` 平常可以；開發板上的檔案常被剝掉區段標頭，`readelf -d` 比較保險，這點不扣分）。
> 第二問又沒答到題目問的「**ARM 的檔案**會怎樣」：你寫的是 `ldd` 處理**本機 x86-64 程式**時的正常流程（載入直接、間接依賴、vdso）。但載入器是**本機的 x86-64 載入器**，它載入不了 ARM 的檔案，第一步就失敗，`ldd` 印出誤導人的 **`not a dynamic executable`**，什麼依賴都列不出來（跟 10-08、10-12 錯在同一處，第四次）。
> 記法：**`ldd` ＝ 請本機載入器跑一次 → 本機載入器跑不了的檔案（別的架構），`ldd` 就沒用。**
>
> **參考答案**【[第三節](../html/c/objdump能不能代替ldd找依賴庫-需求單與實際載入.html#三ldd-會執行東西這是它的代價)、[第五節](../html/c/objdump能不能代替ldd找依賴庫-需求單與實際載入.html#五怎麼選)】
>
> 核心關鍵：
>
> 1. 用 **`readelf -d`** 看 `NEEDED`：只讀檔案、不執行，任何架構的 ELF 都讀得了。
> 2. `ldd` 要靠**本機的 x86-64 載入器**實際載入，處理不了 ARM 的檔案，於是印出誤導人的 **`not a dynamic executable`**。
>
> 詳細說明：`ldd` 平常列出 vdso、間接依賴的那整套機制，都建立在「本機載入器能載入它」上面；架構不同，第一步就失敗。`objdump -p` 平常也行，但開發板上的檔案常被剝掉區段標頭，`readelf -d` 能透過程式標頭的 `DYNAMIC` 找到同一份資料，比較保險。直接執行則會看到核心的 `exec format error`。

**自我練習**（不批改）

```
用readelf -d
本機的ldd需要啓動x86的動態載入器,處理不了arm的檔案,會出錯,會映出誤導人的not a dynamic executable
```

### 陣列 4. 越界的三種下場

#### 陣列 4-1. 越界存取有三種下場：安靜出錯、`stack smashing detected`、segfault。分別是什麼決定會落到哪一種？

> 盒子 1｜過去的作答：[s1-03 quiz.md 4-1](../small-project/s1-03-arrays-pointers/quiz.md#4-1-越界存取有三種下場安靜出錯stack-smashing-detectedsegfault分別是什麼決定會落到哪一種)、[10-08 複習](./2026-10-08-字元-C資料-objdump-hello-ELF-陣列.md)、[10-12 複習](./2026-10-12-objdump-hello-ELF-陣列-組語.md)

```
安靜出錯: 當越界並沒有越過且修改金絲雀位址,或者存取到不同權限的記憶體區段,他還是在同樣的區段,但是有可能寫到堆棧上其他程式負責的地方,就有可能安靜出錯

stack smashing detected: 當我們分配給某個東西記憶體的時候,會分配金絲雀位址,如果有誤修改金絲雀位址,就會出現錯誤

segfault: 當你存取到不同權限區段的記憶體位址就會噴這個錯誤
```

> **批改**：**大致對**。三種的分界都對：還在能存取的記憶體 → 安靜出錯；寫到金絲雀 → `stack smashing detected`；權限不允許 → segfault。兩處要修：
> - segfault 又只寫「權限不同」，漏了**分頁根本沒有對映**（例如位址 0、或遠遠超出堆疊的位址）也會 segfault（跟 10-12 缺同一點）。
> - 金絲雀不是「分配給某個東西記憶體」時都有：它是 gcc 放在**函式堆疊框**裡、區域陣列後面的檢查值，**函式返回前**才檢查。`malloc` 來的堆積記憶體沒有金絲雀。
>
> **參考答案**【[第五節](../html/c/陣列、字串與指標運算-C不檢查邊界與用gdb找segfault.html#五c-不檢查邊界越界的三種下場)開頭的表格、〈下場一：安靜地出錯〉、〈下場二：被堆疊保護抓到〉】
>
> 核心關鍵：
>
> 1. 位址還在可存取的記憶體 → **安靜出錯**。
> 2. 越界**寫入**改掉金絲雀、函式返回前檢查 → **`stack smashing detected`**。
> 3. 分頁**沒有對映或權限不允許** → **segfault**。
>
> 詳細說明：金絲雀是 gcc 放在區域陣列後面的檢查值，返回前才檢查，所以發現得比犯錯晚；只讀不寫不會改到它。檢查失敗時由 `__stack_chk_fail` 中止程式，不會執行 `ret`。segfault 是核心送出的 `SIGSEGV`。

**自我練習**（不批改）

```
1.位址還在可存取的地方 -> 安靜出錯
2. 修改到金絲雀位址,並在函式返回時檢查到
3. 沒有對應的記憶體分頁,或權限 
```

#### 陣列 4-2. 為什麼「程式沒當掉」不能證明沒有越界？

```
因爲你可能已經修改到某個區域變數了,事實上你不應該修改它,但是記憶體管理沒管好就會越界,修改到他
```

> **批改**：**大致對**。抓到：越界可能只是寫壞了別的變數，程式照樣跑完。缺的是「為什麼不會報錯」：**C 不檢查邊界**（越界是未定義行為），只要位址落在還能存取的記憶體，沒有任何機制會發現。「記憶體管理沒管好」太模糊——不是哪個管理機制失職，而是根本沒有檢查。
> **陣列 4 記為大致對**（盒子 1 → 1）。
>
> **參考答案**【[第五節](../html/c/陣列、字串與指標運算-C不檢查邊界與用gdb找segfault.html#五c-不檢查邊界越界的三種下場)〈下場一：安靜地出錯〉】
>
> 核心關鍵：
>
> 1. C 不檢查邊界（越界是未定義行為），落在還能存取的記憶體時沒有任何機制會報錯，所以「沒當掉」證明不了什麼。
>
> 詳細說明：「沒當掉」的時候可能讀到垃圾、寫壞別人的資料，程式照常結束（`oob.c` 結束狀態 0），錯誤很久以後才在別處出現。要在越界當下抓到，用 `-fsanitize=address`。

**自我練習**（不批改）

```
c不檢查邊界,落到還能存取的記憶體 沒有任何機制可以報錯,對於c來說越界是未定義行爲,程式跑得完不代表沒有問題
```

## 組語：[x86-64組合語言入門-暫存器、mov與lea、cmp與條件跳躍](../html/c/x86-64組合語言入門-暫存器、mov與lea、cmp與條件跳躍.html)

### 組語 1. `mov` 與 `lea`

> `movl (%rdi,%rsi,4), %eax` 和 `leaq (%rdi,%rsi,4), %rax` 括號裡寫的一模一樣。
>
> 盒子 1｜過去的作答：[s1-04 quiz.md 第 1 題](../small-project/s1-04-asm-basics/quiz.md#1-mov-與-lea)、[10-12 複習](./2026-10-12-objdump-hello-ELF-陣列-組語.md)

（`%rdi` 是第 1 個參數、`%rsi` 是第 2 個參數。）

#### 組語 1-1. 兩個指令做的事差在哪？

```
movl 是把前項算出的記憶體位址那格存的值 複寫到eax寄存器
leaq 是把前項算出的記憶體位址的值,複寫到rax寄存器
```

> **批改**：**對**。`movl` 去那個位址讀值、`leaq` 只放位址數字本身，你用「那格存的值」和「位址的值」分開了。建議 `leaq` 那句直接寫「**位址本身，不讀記憶體**」，「位址的值」容易被讀成「位址裡的值」。
>
> **參考答案**【[第四節](../html/c/x86-64組合語言入門-暫存器、mov與lea、cmp與條件跳躍.html#四mov-與-lea搬資料-vs-算位址)〈`lea`：只算位址，不碰記憶體〉】
>
> 核心關鍵：
>
> 1. `movl` 先算出位址 `a + i×4`，再**去記憶體讀**那個位址的 4 byte，放進 `%eax`。
> 2. `leaq` 只把算出來的**位址數字本身**放進 `%rax`，**不讀記憶體**。
>
> 詳細說明：括號寫法一樣，代表兩個指令算出同一個數字 D ＋ B ＋ I × S；差別只在要不要拿這個數字去存取記憶體。因為 `lea` 根本不存取，位址不合法也不會 segfault。

#### 組語 1-2. 各對應 C 的什麼寫法？

> 題目：`movl (%rdi,%rsi,4), %eax` 和 `leaq (%rdi,%rsi,4), %rax` 各對應 C 的什麼寫法？

```
假如是參數分別是 int* a intb
*(a + 4b)
a + 4b
```

> **批改**：**錯**。你把 `a` 宣告成 `int *`，這時 C 的 `a + 4*b` 是往後 **4b 個 `int`**（16b byte），乘了兩次 4。C 的指標加法**自動乘 `sizeof(int)`**，括號裡的 `,4` 就是這個自動乘的 4，所以 C 裡不用（也不能）再寫 4：
> - `movl (%rdi,%rsi,4), %eax` ↔ `*(a + b)`，也就是 `a[b]`
> - `leaq (%rdi,%rsi,4), %rax` ↔ `a + b`，也就是 `&a[b]`
>
> 10-12 這一小題答對過（`a[i]`、`&a[i]`），這次是把「組合語言的 byte 算法」直接搬進 C 的指標運算（第 3 課）。
>
> **參考答案**【[第四節](../html/c/x86-64組合語言入門-暫存器、mov與lea、cmp與條件跳躍.html#四mov-與-lea搬資料-vs-算位址)〈`lea`：只算位址，不碰記憶體〉】
>
> 核心關鍵：
>
> 1. `movl (%rdi,%rsi,4), %eax` ↔ `a[i]`（就是 `*(a + i)`，`a` 是 `int *`）。
> 2. `leaq (%rdi,%rsi,4), %rax` ↔ `&a[i]`（就是 `a + i`，結果是指標）。
>
> 詳細說明：第 3 課：`a[i]` ＝ `*(a + i)`、`&a[i]` ＝ `a + i`；括號裡的 `a + i×4` 是 `a + i` 換算成 byte 的算法，C 的指標加法會自動乘上元素大小，所以 C 寫 `a + i`、組合語言寫 `(%rdi,%rsi,4)`。`mov` 比 `lea` 多做的就是那個 `*`。純算數的 `long f(long a, long b) { return a + 4*b; }` 也會編出同一行 `leaq`，那時 `a`、`b` 都是整數，才寫成 `a + 4*b`。

**自我練習**（不批改）

```
應該用 *(a + b) 與 a+b
```

#### 組語 1-3. 為什麼 gcc 會拿 `lea` 來算 `x * 3` 這種跟位址無關的東西？

```asm

	ret                           # 回傳 %rax
```

> 題目：為什麼 gcc 會拿 `lea` 來算 `x * 3` 這種跟位址無關的東西？

```
leaq 可以用來做純數值計算,計算出來直接放在回傳值
```

> **批改**：**大致對**。第 1 點對：`lea` 只算數字、不碰記憶體，所以可以拿來做純算術。又缺第 2 點：**`x * 3` ＝ `x + x×2`**，正好是 `(%rdi,%rdi,2)` 的 B ＋ I × S，一個指令做完（跟 10-12 缺同一點）。「直接放在回傳值」是因為目的地剛好寫 `%rax`，不是 `lea` 的特性。
> **組語 1 記為錯**（盒子 1 → 1，因 1-2）。
>
> **參考答案**【[第四節](../html/c/x86-64組合語言入門-暫存器、mov與lea、cmp與條件跳躍.html#四mov-與-lea搬資料-vs-算位址)〈`lea` 被拿來做算術〉】
>
> 核心關鍵：
>
> 1. `lea` 只算 D ＋ B ＋ I × S 這個數字、不碰記憶體，所以算的東西不必是位址。
> 2. `x * 3` ＝ `x + x×2`，正好寫成 `leaq (%rdi,%rdi,2), %rax`，一個指令做完。

用到的程式（檔案：[`dil.c`](../small-project/s1-04-asm-basics/dil.c)）：

`widen_char` 編出來的組合語言（`objdump` 節錄）：

gdb -batch -ex 'break *widen_char+4' -ex run -ex 'p/x $rdi' \

```

> 3. 因為程式一開始就要呼叫函式庫裡的函式，那些位址連結時填不了；載入器要先把函式庫映射進來、把位址填好，程式的第一條指令之前就得接好。
>
> 詳細說明：`INTERP` 指向 `.interp` 區段，`readelf -l` 顯示成 `Requesting program interpreter`。核心把程式和載入器都映射進記憶體，載入器依 `NEEDED` 找到並映射 `libc.so.6`、檢查版本、填好 `puts` 等符號的位址，最後跳到程式的進入點 `_start`。

```

> **批改**：**對**（盒子 4 → 5）。原因、兩個確認步驟、`-static` 都答到。小補：找不到的原因是 Ubuntu 用 glibc，interpreter 是 `/lib64/ld-linux-x86-64.so.2`；Alpine 用 musl，載入器叫 `ld-musl-*`，沒有 glibc 那個檔。
>
> **參考答案**【[第五節](../html/c/ELF的interpreter是什麼-動態載入器與井字號驚嘆號.html#五直譯器不存在時明明有檔案卻說找不到)】（2026-10-21 改寫成核心關鍵格式）

> 1. 原因：程式要求的 interpreter `/lib64/ld-linux-x86-64.so.2` 在 Alpine 上**不存在**，核心回報「檔案不存在」，shell 說成你的程式 `not found`。
> 2. 確認：① `readelf -l 程式 | grep interpreter` 看它要求哪個 interpreter；② 在 Alpine 上 `ls -l` 那個路徑，確認不存在。

## ELF：[ELF是什麼-可執行與可連結格式的兩種視角](../html/c/ELF是什麼-可執行與可連結格式的兩種視角.html)

### ELF 1. ELF 三個字母各代表什麼？為什麼說「Executable」和「Linkable」對應兩種不同的讀者？

> 盒子 3｜過去的作答：[s1-01 quiz.md 第 1 題](../small-project/s1-01-hello-compile/quiz.md#1-elf-三個字母各代表什麼為什麼說executable和linkable對應兩種不同的讀者)、[10-06 複習](./2026-10-06-字元-interp-ELF-gcc-GNU.md)

```
excutable linkable format
executable 對應是給kernel看的,kernel會看program header 啓動動態載入器,載入後,就可以執行了
linkable是給連接器看的,連接器要負責組合.o,建好記憶體區段,如果是別的庫無法知道記憶體位址的,需要寫需求單,並在program header放上interpreter路徑
```

> **批改**：**大致對**（盒子 3 → 3）。名字對（全名是 Executable **and** Linkable Format）；執行視角對：核心看**程式標頭表**。連結那一半描述的是連結器**做了什麼**（合併 `.o`、寫需求單），沒答到它**讀的是哪一張目錄**：連結器讀的是**區段標頭表**（單位是區段 section，記錄每個區段叫什麼、在哪、多大）。題目問「兩種讀者」，答案是 ELF 有兩張目錄、各給一種讀者看，兩張都要講到。另外「寫需求單、放 interpreter 路徑」是連結器**產生**執行檔時寫進程式標頭的東西，不是它讀的東西。
>
> **參考答案**【[第一節](../html/c/ELF是什麼-可執行與可連結格式的兩種視角.html#一名字的意思)、[第四節](../html/c/ELF是什麼-可執行與可連結格式的兩種視角.html#四名字的關鍵兩種視角)】（2026-10-21 改寫成核心關鍵格式）
>
> 核心關鍵：
> 1. Executable and Linkable Format（可執行與可連結格式）。
> 2. ELF 有兩張目錄：**程式標頭表**（執行視角，單位是載入段 segment）給核心與動態載入器看——載入時把哪幾塊放進記憶體、權限是什麼。
> 3. **區段標頭表**（連結視角，單位是區段 section）給連結器 `ld` 看——每個區段叫什麼、在哪、多大。
>
> 詳細說明：`nm`、`objdump` 也讀區段標頭表。`.o` 只有區段標頭表、沒有程式標頭表（`readelf -l hello.o` 說 `There are no program headers in this file`），所以只能給連結器用、不能執行；連結器把區段合併、打包成載入段，寫出程式標頭表，「可連結的」才變成「可執行的」。

### GNU 3. 情境題：一支 shell 腳本在你的 Ubuntu 上用 `bash` 測試完全正常，放到 OpenWrt 上卻出錯。從本篇的角度，最可能的原因是什麼？寫腳本時該怎麼預防？

```
最可能是bash 腳本語法 與 openwrt的shell適用的語法衝突
1,試着用openwrt的shell ash 在 ubuntu 用ash跑這個腳本
2. 儘量用posix的語法,因爲每個shell通用
```

> **批改**：**對**（盒子 3 → 4）。原因與兩個預防都答到。兩個小補：
> - 原因說精確一點：OpenWrt **不是 GNU 使用者空間，根本沒有 bash**，`/bin/sh` 是 BusyBox 的 `ash`。
> - 本機沒有 `ash` 這個命令（`which ash` 找不到），要寫成 `busybox sh 腳本` 或 `dash 腳本`；而且本機 `/bin/sh -> bash`，用 `#!/bin/sh` 直接 `./腳本` 跑的仍是 bash，測不出問題。
>
> **參考答案**【[第四節](../html/linux/GNU是什麼-Linux核心與GNU工具的分工.html#四不是-gnu-的-linux你已經遇過了)】（2026-10-21 改寫成核心關鍵格式）
>
> 核心關鍵：
> 1. 原因：OpenWrt 不是 GNU 使用者空間，沒有 bash，`/bin/sh` 是 BusyBox 的 `ash`；腳本用了 bash 才有的擴充語法（陣列、`[[ ]]` 等）就會出錯。
> 2. 預防：只用 POSIX 規定的語法與選項，並在本機用 POSIX 的 shell（`busybox sh 腳本` 或 `dash 腳本`）測試。
>
> 詳細說明：本機 `/bin/sh -> bash`：第一行寫 `#!/bin/sh` 直接 `./腳本`，跑的仍是 bash，測不出問題。改第一行解決不了：`#!/bin/busybox` 會報 `applet not found`。
