### hello 5. 情境題：你把一支動態連結的程式複製到另一台機器，執行時出現找不到 `libc.so.6` 某個版本符號的錯誤。從本課的哪個階段可以解釋這件事？如果改用 `-static` 編譯，這個問題還會發生嗎？

> 盒子 2｜過去的作答：[s1-01 quiz.md 第 5 題](../small-project/s1-01-hello-compile/quiz.md#5-情境題你把一支動態連結的程式複製到另一台機器執行時出現找不到-libcso6-某個版本符號的錯誤從本課的哪個階段可以解釋這件事如果改用--static-編譯這個問題還會發生嗎)、[10-04 複習](./2026-10-04-字元-C資料-objdump-hello-ELF.md)、[10-08 複習](./2026-10-08-字元-C資料-objdump-hello-ELF-陣列.md#hello-5-情境題你把一支動態連結的程式複製到另一台機器執行時出現找不到-libcso6-某個版本符號的錯誤從本課的哪個階段可以解釋這件事如果改用--static-編譯這個問題還會發生嗎)、[10-12 複習](./2026-10-12-objdump-hello-ELF-陣列-組語.md)、[10-23 複習](./2026-10-23-大複習-hello-gcc-GNU-interp-ELF-objdump-C資料-字元-陣列-組語-組語二-多檔.md)、[10-26 複習](./2026-10-26-hello-GNU-interp-objdump-C資料-字元-陣列-組語-組語二-多檔.md)

```
這隻程式在另外一臺機器連結的時候,在重定位符號的時候,抓到某符號是在libc.so.6 某個版本裏,所以連結器會在dynamic section寫下需求單,並也把版本寫入到執行檔.

執行時,本機的interpreter在重定位這個符號時,會試着去找對應的庫與版本,但是本機沒有這個版本的庫,纔會有這個問題

不會 -static,已經把整個程式碼打包到執行檔了
```

> **批改**：**對**（盒子 2 → 3）。三個核心關鍵都有：連結時 `ld` 把版本寫進執行檔（10-23、10-26 都缺這點，這次主動寫出來了）、執行時載入器在這台機器找不到那個版本就報錯、`-static` 不會發生。小修（不扣分）：(1)「本機沒有這個版本的庫」說得不精確，`libc.so.6` 是**找得到**的，缺的是它沒提供執行檔要的**版本符號**（例如 `GLIBC_2.34`），跟 10-26 的小修同一處；(2) 連結時 `ld` 對 `libc` 的符號不是「重定位」，而是記下「這個符號要從 `libc.so.6` 的哪個版本拿」，真正的填位址是執行時載入器做的；(3) `-static` 打包進去的是用到的 `libc.a` 裡的那些 `.o`，不是「整個程式碼」。
>
> **參考答案**【[第九節](../html/c/hello.c怎麼變成能跑的程式-編譯的四個階段.html#九作業解說四題背後的原因)〈自我測驗第 5 題延伸：「找不到版本符號」是怎麼回事〉】
>
> **核心關鍵**：
>
> 1. **連結時**：`ld` 把需要的符號版本（例如 `GLIBC_2.34`）寫進執行檔。
> 2. **執行時**：動態載入器檢查目標機器的 `libc.so.6` 有沒有提供這個版本，沒有就報 `` version `GLIBC_2.34' not found ``。
> 3. `-static` 不會發生：libc 的程式碼已經整份複製進執行檔，不再找外部的 `libc.so.6`。
>
> **詳細說明**：`readelf -V hello` 看得到版本需求；真正的門檻是 2.34（`__libc_start_main`），不是 `puts` 的 2.2.5。`-static` 的代價是檔案大，而且 libc 的安全修補要重新編譯才會帶進去。

### GNU 4. GPL 的 copyleft 要求什麼？glibc 用 LGPL 而不是 GPL，對「商業軟體能不能連結 libc」有什麼差別？

> 盒子 2｜過去的作答：[s1-01 quiz.md 第 4 題](../small-project/s1-01-hello-compile/quiz.md#4-gpl-的-copyleft-要求什麼glibc-用-lgpl-而不是-gpl對商業軟體能不能連結-libc有什麼差別)、[10-06 複習](./2026-10-06-字元-interp-ELF-gcc-GNU.md#gnu-4-gpl-的-copyleft-要求什麼glibc-用-lgpl-而不是-gpl對商業軟體能不能連結-libc有什麼差別)、[10-10 複習](./2026-10-10-C資料-GNU-interp-hello-gcc.md#gnu-4-gpl-的-copyleft-要求什麼glibc-用-lgpl-而不是-gpl對商業軟體能不能連結-libc有什麼差別)、[10-19 複習](./2026-10-19-interp-GNU-C資料-ELF-objdump-組語.md)、[10-23 複習](./2026-10-23-大複習-hello-gcc-GNU-interp-ELF-objdump-C資料-字元-陣列-組語-組語二-多檔.md)、[10-26 複習](./2026-10-26-hello-GNU-interp-objdump-C資料-字元-陣列-組語-組語二-多檔.md)

```
1. 當我們對GPL的軟體修改後 若要發佈我們必須以同樣GPL授權發佈,並且公開程式碼

2. LGPL是即使我們開發的軟體連結了glibc,發佈後我們可以不用公開程式碼
但GPL的話如果連結並發佈了我們就需要公開程式碼
```

> **批改**：**對**（盒子 2 → 3）。抓到：修改後**要散布**才有義務（「若要發佈」也隱含了只自己用沒有義務）、散布時要用**同樣的 GPL** 並公開原始碼（10-26 缺的「同樣授權」這次寫了）；連結 LGPL 的 glibc 散布時不必公開，GPL 的庫就要。
>
> **參考答案**【[第五節](../html/linux/GNU是什麼-Linux核心與GNU工具的分工.html#五gplgnu-最深遠的影響)】
>
> **核心關鍵**：
>
> 1. copyleft：可以自由使用、修改、散布，但**散布**修改後（或以它為基礎）的版本時，必須用**同樣的授權（GPL）**並提供原始碼。
> 2. 只是使用、或改了自己用、不給別人，沒有義務。
> 3. glibc 用 LGPL：允許非自由的程式**連結**它而不必開放自己的原始碼，所以商業軟體都能連結 `libc.so.6`；如果 glibc 是 GPL，連結它的程式在散布時就得整個用 GPL 開放。
>
> **詳細說明**：copyleft 的目的是讓「自由不能在傳遞途中被拿走」。例子：公司內部改了 GPL 的工具自己用，不必公開；把改過的版本賣給客戶，就要給客戶原始碼，並讓客戶同樣能以 GPL 再散布。

## objdump：[objdump能不能代替ldd找依賴庫-需求單與實際載入](../html/c/objdump能不能代替ldd找依賴庫-需求單與實際載入.html)

### objdump 2. `ldd` 是怎麼得到依賴清單的？從這個機制解釋：為什麼對來路不明的執行檔用 `ldd` 有風險，`objdump -p` 卻沒有？

> 盒子 3｜過去的作答：[s1-01 quiz.md 第 2 題](../small-project/s1-01-hello-compile/quiz.md#2-ldd-是怎麼得到依賴清單的從這個機制解釋為什麼對來路不明的執行檔用-ldd-有風險objdump--p-卻沒有)、[10-07 複習](./2026-10-07-GNU-C資料-hello-objdump-字元.md)、[10-11 複習](./2026-10-11-字元-C資料-objdump-GNU-陣列.md)、[10-22 複習](./2026-10-22-組語-C資料-objdump-字元-陣列.md)

```
新版本的ldd會啓動預設的interpreter然後依據執行檔的dynamict section 先找到so,然後也會去看這些so他們自己在
dynamic section也會有相關的so,另外還有linux預設的虛擬so,他就是這樣找到依賴清單,(他也會找到interpreter路徑)

有風險的是舊版本的ldd, 他會直接啓動執行檔寫的interpreter,如果這個被改爲攻擊病毒就有風險.

objdump -p 會直接看dynamic section部分 看有哪些needed的庫
```

> **批改**：**對**（盒子 3 → 4）。三個核心關鍵都有：`ldd` 讓載入器實際處理這支程式、照 `NEEDED` 一路找到間接依賴；攻擊點是舊版 `ldd` 照檔案寫的 `INTERP` 啟動載入器；`objdump -p` 只讀需求單。而且你把 10-24 追問的結論（本機 glibc 2.39 的 `ldd` 用自己清單裡的本機載入器）用上了，比 10-22 的答案精確。補一點（不扣分）：既然新版不照 `INTERP`，為什麼仍不建議對來路不明的檔案用 `ldd`？因為**你不一定知道眼前那台機器的 `ldd` 是哪一種**，而且就算是新版，載入器仍然真的去打開、映射這個檔案和它要的函式庫；`objdump -p` 不管哪個版本都只讀檔案。小修：「linux 預設的虛擬 so」正式名稱是 vDSO（`linux-vdso.so.1`）。
>
> **參考答案**【[第三節](../html/c/objdump能不能代替ldd找依賴庫-需求單與實際載入.html#三ldd-會執行東西這是它的代價)】
>
> **核心關鍵**：
>
> 1. `ldd` 讓動態載入器實際處理這支程式：載入器照常找、載入全部依賴（含間接依賴），在進 `main` 前停下來印清單。
> 2. 風險：`ldd` 要讓載入器真的去處理這個檔案。有些版本的 `ldd`（上游 glibc 2.27 以前）直接執行程式，這時載入器由檔案的 `INTERP` 決定，攻擊者可以寫成自己的程式，跑 `ldd` 就執行了它；你不一定知道眼前的 `ldd` 是哪一種。
> 3. `objdump -p` 只讀檔案裡的 `NEEDED`，不啟動任何東西。
>
> **詳細說明**：`grep -n LD_TRACE /usr/bin/ldd` 可以看到腳本裡的 `LD_TRACE_LOADED_OBJECTS=1`；本機的 `ldd` 等於執行 `LD_TRACE_LOADED_OBJECTS=1 /lib64/ld-linux-x86-64.so.2 ./程式`，所以 `INTERP` 指向不存在的檔案時 `ldd` 照樣列得出來（第三節的 `hello_badinterp` 實驗）。對來路不明的檔案要看依賴，用 `objdump -p` 或 `readelf -d`。

### objdump 3. 一支程式連結時用了 `-L./lib -lfoo`，編譯成功；執行時卻出現 `error while loading shared libraries: libfoo.so`。用「連結時」與「執行時」分別是誰在找檔案，解釋為什麼連結找得到、執行卻找不到。這時 `objdump -p` 與 `ldd` 各會顯示什麼？

> 盒子 2｜過去的作答：[s1-01 quiz.md 第 3 題](../small-project/s1-01-hello-compile/quiz.md#3-一支程式連結時用了--llib--lfoo編譯成功執行時卻出現-error-while-loading-shared-libraries-libfooso用連結時與執行時分別是誰在找檔案解釋為什麼連結找得到執行卻找不到這時-objdump--p-與-ldd-各會顯示什麼)、[10-04 複習](./2026-10-04-字元-C資料-objdump-hello-ELF.md)、[10-08 複習](./2026-10-08-字元-C資料-objdump-hello-ELF-陣列.md)、[10-11 複習](./2026-10-11-字元-C資料-objdump-GNU-陣列.md)、[10-20 複習](./2026-10-20-C資料-objdump-字元-陣列-gcc.md)、[10-23 複習](./2026-10-23-大複習-hello-gcc-GNU-interp-ELF-objdump-C資料-字元-陣列-組語-組語二-多檔.md)、[10-26 複習](./2026-10-26-hello-GNU-interp-objdump-C資料-字元-陣列-組語-組語二-多檔.md)

```
連結,ld會根據命令列的 -L, -lfoo,去找libfoo.so
但執行時,interpreter 從 dynamic section 只能拿到 libfoo.so這個庫名,他是從自己預設的庫資料夾找的,所以找不到

objdump 會顯示 (NEEDED)libfoo.so
ldd 在這個庫會顯示not found
```

> **批改**：**對**（盒子 2 → 3）。三個核心關鍵都有：連結時 `ld` 照 `-L` 找到；執行時載入器從 dynamic section 只拿到**名字**、只找自己的預設路徑所以找不到；`objdump -p` 列出 `NEEDED libfoo.so`、`ldd` 顯示 `not found`（10-26 缺的這一點這次寫了）。小修（不扣分）：「預設的庫資料夾」完整說是 `RUNPATH`、`LD_LIBRARY_PATH`、`/etc/ld.so.cache`、`/lib`／`/usr/lib`。
>
> **參考答案**【[第四節](../html/c/objdump能不能代替ldd找依賴庫-需求單與實際載入.html#四找不到函式庫時兩者各看到什麼)、[第二節](../html/c/objdump能不能代替ldd找依賴庫-需求單與實際載入.html#二為什麼會差這麼多兩者看的是不同時間點)】
>
> **核心關鍵**：
>
> 1. 連結時是 **`ld`** 在找：照 `-L./lib` 找到 `libfoo.so`，在執行檔寫下 `NEEDED libfoo.so`，**只有名字、沒有路徑**。
> 2. 執行時是**動態載入器**在找：它不知道當初的 `-L`，只找自己的預設路徑（加上 `LD_LIBRARY_PATH` 等），所以找不到。
> 3. `objdump -p` 照樣列出 `NEEDED libfoo.so`（看不出問題）；`ldd` 顯示 `libfoo.so => not found`。
>
> **詳細說明**：執行時的搜尋順序是：執行檔裡的 `RUNPATH`、`LD_LIBRARY_PATH`、`/etc/ld.so.cache`、預設目錄（`/lib`、`/usr/lib`）。修法是連結時加 `-Wl,-rpath,…` 把路徑寫進執行檔，或執行時設 `LD_LIBRARY_PATH`。

### 組語 12. 檔案裡的位址 vs 執行時的位址

> 用 `objdump -d paren` 查到 `deref+4` 在 `0x11f4`，`break *0x11f4` 之後 `run` 卻得到 `Cannot access memory at address 0x11f4`，`break *deref+4` 就沒問題。
>
> 盒子 2｜過去的作答：[s1-04 quiz.md 第 12 題](../small-project/s1-04-asm-basics/quiz.md#12-檔案裡的位址-vs-執行時的位址2026-10-06-課後實作新增)、[10-13 複習](./2026-10-13-組語-字元.md)、[10-22 複習](./2026-10-22-組語-C資料-objdump-字元-陣列.md)、[10-23 複習](./2026-10-23-大複習-hello-gcc-GNU-interp-ELF-objdump-C資料-字元-陣列-組語-組語二-多檔.md)、[10-26 複習](./2026-10-26-hello-GNU-interp-objdump-C資料-字元-陣列-組語-組語二-多檔.md)

用到的程式（檔案：[`paren.c`](../small-project/s1-04-asm-basics/paren.c)）：

```c
#include <stdio.h>

__attribute__((noinline)) long copy_val(long x)  { return x; }    /* 回傳 x 本身 */
__attribute__((noinline)) long deref(long *p)    { return *p; }   /* 回傳 p 指向的值 */

int main(void)
{
    long v = 1234;
    printf("%ld %ld\n", copy_val(v), deref(&v));
    return 0;
}
```

`-O2` 編出的 `deref`：

```asm
deref:
	endbr64                 # 控制流程保護標記（佔 4 byte，所以下一條是 deref+4）
	mov	(%rdi),%rax         # 把 %rdi 當位址，讀 8 byte 放進 %rax
	ret                     # 回傳 %rax
```

實驗步驟：

```sh
gcc -O2 -g paren.c -o paren
objdump -d --no-show-raw-insn paren        # deref 的 mov (%rdi),%rax 那一行印成 11f4
gdb -batch -ex 'break *0x11f4' -ex 'break *deref+4' -ex 'info breakpoints' -ex run -ex 'info breakpoints' ./paren
```

#### 組語 12-1. 為什麼？

> 題目：`break *0x11f4` 之後 `run` 得到 `Cannot access memory at address 0x11f4`，`break *deref+4` 卻沒問題，為什麼？

```
因爲 對於gdb, *後面是要運算式,也就是符號deref的位址 + 4byte,而執行後符號會被interpreter重定位,根據ASLR deref+4的位址也不再是0x11f4 而是0x11f4 + base位址,所以直接使用break *0x11f4會失敗, 要用符號去找當時的位址纔會成功
```

> **批改**：**對**。兩個核心關鍵都有：執行時位址 ＝ 基底 ＋ `0x11f4`，所以寫死的 `0x11f4` 失敗；`*deref+4` 有符號，gdb 會用 `deref` 當時的位址去算（10-13、10-22、10-26 缺的這點這次寫了）。小修兩處（不扣分）：(1) 搬家的原因是 **PIE**，不是 ASLR——gdb 預設**關掉** ASLR，基底固定是 `0x555555554000`，照樣失敗；ASLR 只是讓每次的基底不同。(2) 不是「interpreter 把符號重定位」：gdb 自己讀執行檔的符號表（`deref` 在檔案裡是 `0x11f0`），程式載入後知道基底，就把符號位址加上基底；載入器（`ld.so`）重定位的是程式裡的 `.got` 這些洞，不是 gdb 用的符號。
>
> **參考答案**【[第三節](../html/c/x86-64組合語言入門-暫存器、mov與lea、cmp與條件跳躍.html#三指令的文法助憶符大小後綴運算元)〈上面中斷點 4 的 `break *0x11f4`：為什麼 `run` 之後失敗？〉】
>
> **核心關鍵**：
>
> 1. `objdump -d` 印的是**檔案裡的位址**；PIE 執行時整支被搬到基底（gdb 裡是 `0x555555554000`），執行時位址 ＝ 基底 ＋ 檔案位址，`0x11f4` 在執行時沒有對映。
> 2. `*deref+4` 裡有符號名稱，程式載入後 gdb 用新的位址重算成 `0x5555555551f4`；寫死的 `0x11f4` 只是數字，不會重算。

> **批改**：**對**（組語 12 整題 盒子 2 → 3）。抓到：非 PIE 的位址連結完就定了，載入時不搬，`objdump -d` 的位址就是執行時的位址。
>
> **參考答案**【[第三節](../html/c/x86-64組合語言入門-暫存器、mov與lea、cmp與條件跳躍.html#三指令的文法助憶符大小後綴運算元)〈上面中斷點 4 的 `break *0x11f4`：為什麼 `run` 之後失敗？〉】
