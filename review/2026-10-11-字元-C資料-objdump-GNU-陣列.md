### 字元 3. `sizeof('A')`、`sizeof("A")`、`sizeof("字")` 在本機各是多少？分別解釋為什麼。

> 盒子 1｜過去的作答：[s1-02 quiz.md 第 3 題](../small-project/s1-02-data-repr/quiz.md#3-sizeofasizeofasizeof字-在本機各是多少分別解釋為什麼)、[10-04 複習](./2026-10-04-字元-C資料-objdump-hello-ELF.md)、[10-07 複習](./2026-10-07-GNU-C資料-hello-objdump-字元.md)

```
4byte
2byte
4byte

'A' 是int
"A" 是一個A char + \0
"字" 是3個char + \0
```

> **批改**：**對**（盒子 1 → 2）。三個數字和理由都對。`sizeof('A')` 這次答成 4、理由是 `int`，10-04、10-07 兩次錯的地方這次對了。「3 個 char」就是「字」的 UTF-8 佔 3 個 byte，意思一樣。
>
> **參考答案**【[第三節](../c/字元是什麼-char就是1byte的整數與ASCII和UTF-8.md#三c-的字元常數單引號而且型別是-int)、[第四節](../c/字元是什麼-char就是1byte的整數與ASCII和UTF-8.md#四中文字一個-byte-裝不下utf-8-用-3-個-byte)】
>
> 核心關鍵：
> 1. `sizeof('A')` = 4：在 C 裡，字元常數 `'A'` 的型別是 `int`（C++ 才是 `char`）。
> 2. `sizeof("A")` = 2：`'A'` 加上結尾的 `'\0'`。
> 3. `sizeof("字")` = 4：UTF-8 用 3 byte 表示「字」，再加上 `'\0'`。
>
> 詳細說明：`'A'` 只是寫數字 65 的另一種方式，C 裡沒有後綴的整數常數都是 `int`，所以佔 4 byte。字串常數是 `char` 陣列，`sizeof` 量的是整個陣列，含 `'\0'`；`strlen` 才不算 `'\0'`（`strlen("字")` 是 3）。「字」的 UTF-8 是 `e5 ad 97`。

### 字元 2. 使用者輸入的字元是 `'7'`，你想得到數值 7。直接把它當數字用會得到多少？該怎麼轉，這個方法為什麼成立？

> 盒子 2｜過去的作答：[s1-02 quiz.md 字元第 2 題](../small-project/s1-02-data-repr/quiz.md#2-使用者輸入的字元是-7你想得到數值-7直接把它當數字用會得到多少該怎麼轉這個方法為什麼成立)、[10-05 複習](./2026-10-05-gcc-陣列-GNU-C資料-字元.md)

```
55

'7' - 48
因爲根據ascii, 0~9 是48~57
然後'7'其實是int 直接-48差值就是7,其他數字也可以這麼做
```

> **批改**：**對**（盒子 2 → 3）。55、減掉 48、`'0'`～`'9'` 排在 48～57，三個重點都有。「其他數字也可以這麼做」就是連號的意思；10-05 缺的「為什麼成立」這次補上了。建議寫成 `c - '0'`，不要寫死 48，理由見詳細說明。
>
> **參考答案**【[第一節](../c/字元是什麼-char就是1byte的整數與ASCII和UTF-8.md#一字元就是一個數字)、[第二節](../c/字元是什麼-char就是1byte的整數與ASCII和UTF-8.md#二編碼表ascii)】
>
> 核心關鍵：
> 1. 直接當數字用，`'7'` 是 55（它的 ASCII 碼），不是 7。
> 2. 要寫成 `c - '0'`（`'0'` 是 48）。
> 3. 這個方法成立是因為 `'0'`～`'9'` 在編碼表裡是**連號的**（48～57），數字字元減掉 `'0'` 就是它跟 `'0'` 差幾號，也就是它代表的數值。
>
> 詳細說明：`'7' - '0'` = 55 − 48 = 7。寫 `'0'` 比寫 48 好：讀的人一看就懂意思；而且 C 標準只保證 `'0'`～`'9'` 一定連號，沒有保證 `'0'` 是 48，寫 `'0'` 就不用依賴 ASCII 的具體數字。

### 字元 5. 有人說「『字』是 3 個字元」，另一個人說「是 1 個字元」，誰對？`strlen("字")` 和 `mbstowcs(NULL, "字", 0)` 各會得到多少？如果程式忘了呼叫 `setlocale`，後者會得到什麼，那個數字是怎麼來的？

> 盒子 1｜過去的作答：[s1-02 quiz.md 第 5 題](../small-project/s1-02-data-repr/quiz.md#5-有人說字是-3-個字元另一個人說是-1-個字元誰對strlen字-和-mbstowcsnull-字-0-各會得到多少如果程式忘了呼叫-setlocale後者會得到什麼那個數字是怎麼來的)、[10-04 複習](./2026-10-04-字元-C資料-objdump-hello-ELF.md)、[10-08 複習](./2026-10-08-字元-C資料-objdump-hello-ELF-陣列.md)

```
如果字元是指unicode字元,那一個字元沒錯
如果是指char,那就是3個字元

strlen: 3
mbstowcs: 1

那C就不知道該用什麼編碼了,那預設就會返回size_t -1 = 18446744073709551615 - 1= 18446744073709551614
```

> **批改**：**大致對**（盒子 1 → 1）。前兩問對：兩個人都對（`char` 算 3 個、Unicode 字元算 1 個），`strlen` = 3、`mbstowcs` = 1。第三問機制對了（沒呼叫 `setlocale`、看不懂編碼 → 回傳 `(size_t)-1`），10-08 寫的「得到 3」這次修正了；但**數字算錯**：`(size_t)-1` 就是 **18446744073709551615**，不用再減 1。−1 轉成無號是「64 個位元全部是 1」，64 個 1 ＝ 2⁶⁴ − 1 ＝ 18446744073709551615，也就是 `size_t` 能表示的最大值。這個數已經是 2⁶⁴ − 1，不是 2⁶⁴。另外「不知道用什麼編碼」可以說得精確一點：程式用的是預設的 `"C"` locale，它只認 ASCII。
>
> **參考答案**【[第五節](../c/字元是什麼-char就是1byte的整數與ASCII和UTF-8.md#五那字是-3-個字元嗎看你說的是哪一種字元)】
>
> 核心關鍵：
> 1. 兩個人都對：以 `char`（byte）算是 **3** 個，以 Unicode 字元算是 **1** 個。
> 2. `strlen("字")` = 3；呼叫 `setlocale` 之後 `mbstowcs` = 1。
> 3. 忘了 `setlocale` → 用 `"C"` locale，看不懂 UTF-8 → 回傳 `(size_t)-1`，也就是 **18446744073709551615**（2⁶⁴ − 1）。
>
> 詳細說明：「字」在 UTF-8 是 3 個 byte（`e5 ad 97`），碼位是 U+5B57。`strlen` 數的是 byte；`mbstowcs` 數的是字元，但它要先知道編碼，必須呼叫 `setlocale(LC_ALL, "")` 讀進環境變數 `LANG`（例如 `zh_TW.UTF-8`）。沒呼叫時，不管 `LANG` 設什麼，程式都用預設的 `"C"` locale，只認 ASCII（0～127），看到 `0xe5` 就判定是無效的多位元組序列，回傳 `(size_t)-1`。`size_t` 在本機是 8 byte 無號，`-1` 轉成無號就是全部位元為 1（跟 `int` 的 −1 轉 `unsigned` 得到 4294967295 ＝ 2³² − 1 是同一個道理）。

### C資料 4. `int y = x + 1; return y > x;` 在 `x = INT_MAX` 時，`-O0` 回傳 0、`-O2` 回傳 1。為什麼會這樣？這算不算 gcc 的 bug？kernel 用哪個選項避免這種情況，代價是什麼？

> 盒子 1｜過去的作答：[s1-02 quiz.md 第 4 題](../small-project/s1-02-data-repr/quiz.md#4-int-y--x--1-return-y--x-在-x--int_max-時-o0-回傳-0-o2-回傳-1為什麼會這樣這算不算-gcc-的-bugkernel-用哪個選項避免這種情況代價是什麼)、[10-07 複習](./2026-10-07-GNU-C資料-hello-objdump-字元.md)

題目用到的程式是筆記[第八節](../c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.md#八溢位無號回繞有號是未定義行為)的 `ub.c`，完整原始碼：

```c
#include <stdio.h>
#include <limits.h>

int bigger(int x)
{
    int y = x + 1;
    return y > x;
}

int main(void)
{
    printf("bigger(INT_MAX) = %d\n", bigger(INT_MAX));
    return 0;
}
```

編譯與執行：`gcc -O0 ub.c -o ub && ./ub`、`gcc -O2 ub.c -o ub && ./ub`（結果如題目所述，分別印 0 與 1）。

```
-O0, gcc實際去算 ,因爲x超過int最大值溢位,所以變成負最小因此返回0
-O2, gcc沒有實際算,因爲溢位在c沒有定義,所以c會認爲兩個int相加的值必大於兩者,因此返回1

不算因爲c沒有去定義溢位這件事

-fno-strict-overflow
這可以讓溢位變成有定義的
代價是每一個可能發生溢位的地方都會被標記實際算一次,犧牲cpu的計算增加
```

> **批改**：**對**（盒子 1 → 2）。四點都答到：`-O0` 回繞成最小值所以回傳 0；`-O2` 因為溢位是 UB、直接當成恆真回傳 1；不算 bug；`-fno-strict-overflow` 讓溢位有定義、代價是比較慢。10-07 說反的 `-O2` 推理與沒寫出的選項名稱，這次都對了。三個用詞小修，不扣分：(1) 做假設的是**編譯器（gcc）**，C 標準只是允許它這樣假設；(2)「兩個 `int` 相加必大於兩者」只在加的是正數時成立，這題是 `x + 1 > x`；(3) 代價不是「每個地方實際多算一次」——加法 `-O2` 一樣會算，差別是 gcc 不能再靠「不會溢位」這個假設來化簡比較、改寫程式。
>
> **參考答案**【[第八節](../c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.md#八溢位無號回繞有號是未定義行為)】
>
> 核心關鍵：
> 1. 有號溢位是未定義行為（UB），C 標準允許編譯器**假設它不會發生**。
> 2. `-O0` 照字面算，`INT_MAX + 1` 回繞成 `INT_MIN`，`y > x` 為假 → 0；`-O2` 依這個假設推論 `x + 1` 一定大於 `x`，直接回傳 1。
> 3. 不是 gcc 的 bug：標準對發生 UB 的程式沒有任何要求，兩種結果都合法。
> 4. kernel 用 `-fno-strict-overflow`（等於 `-fwrapv -fwrapv-pointer`），讓溢位照二補數回繞、變成有定義的行為；代價是少了依賴「不會溢位」的最佳化，程式可能稍慢。
>
> 詳細說明：連 `-O0` 也不保證照字面算：第四節的 `overflow.c` 把同一件事寫成一行 `return x + 1 > x;`，`-O0` 也回傳 1，因為 gcc 在最佳化之前的化簡階段就把它改掉了（筆記第八節用 `-fdump-tree-original` 看到）。所以本題的 `bigger` 才故意拆成兩行。

### C資料 6. `printf("%p")` 印出 `0x7ffe50b23624`，只有 12 位十六進位。指標到底佔幾個 byte？印出來為什麼比較短？如果在 kernel 的錯誤訊息裡看到 `0xffff888102a4c000`，從位址的長相你能判斷什麼？

> 盒子 1｜過去的作答：[s1-02 quiz.md 第 6 題](../small-project/s1-02-data-repr/quiz.md#6-printfp-印出-0x7ffe50b23624只有-12-位十六進位指標到底佔幾個-byte印出來為什麼比較短如果在-kernel-的錯誤訊息裡看到-0xffff888102a4c000從位址的長相你能判斷什麼)、[10-07 複習](./2026-10-07-GNU-C資料-hello-objdump-字元.md)

```
8byte
因爲前面0的部分省略了

kenerl的位址空間是 0xffff
使用者的是0x888102a4c000
最高符號位是1,所以前面的空間都變成ffff 高位補1
應該可以判斷他是sigend long, 無號的話應該是補0
```

> **批改**：**不完整**（盒子 1 → 1）。8 byte 對；「前面的 0 省略了」對（`%p` 不補前導零），但沒講為什麼上面 2 byte 一定是 0：x86-64 的虛擬位址只用 48 bit。第三問**跟 10-07 錯在同一處**：又把位址拆成「`0xffff` 是 kernel 的、`0x888102a4c000` 是使用者的」。這是**一個**完整的 kernel 位址，不是兩段拼起來，上面 16 bit 也不是一塊「給 kernel 用」的欄位。你寫「最高位是 1，所以前面補 1」，其實抓到了 canonical address 的規則：上面 16 bit 必須跟第 47 bit 相同。這個觀察是對的，結論卻錯了：上面補 1 不代表它是 `signed long`。指標沒有有號無號之分，上面 16 bit 全是 1，代表這個位址落在位址空間的**核心那一半**，所以判斷它是 kernel 的位址。
>
> **參考答案**【[第二節](../c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.md#二指標就是位址)〈位址看起來只有 6 byte？——`%p` 不補零，而且最上面 2 byte 一定是 0〉】
>
> 核心關鍵：
> 1. 指標佔 8 byte。
> 2. x86-64 虛擬位址只用 48 bit，使用者空間的位址上面 2 byte 一定是 `00 00`，`%p` 不補前導零，所以只印出 12 位。
> 3. `0xffff888102a4c000` 整個是一個位址；上面 16 bit 全是 1，表示它在位址空間的核心那一半，所以是 kernel 的位址。
>
> 詳細說明：canonical address 規定上面 16 bit 必須跟第 47 bit 相同，所以合法的位址只有兩段：`0x0000000000000000`～`0x00007fffffffffff`（使用者空間，第 47 bit 是 0，上面全 0）與 `0xffff800000000000`～`0xffffffffffffffff`（核心，第 47 bit 是 1，上面全 1），中間那一大段不合法。「看起來像符號擴展」沒錯，形式上就是把第 47 bit 往上複製；但這是 CPU 對位址格式的規定，跟 C 的有號、無號型別無關。

### C資料 9. 情境題：有人寫了 `if (len - used > 0)` 判斷「緩衝區還有沒有剩餘空間」，`len`、`used` 都是 `size_t`，用 `-Wall -Wextra` 編譯沒有任何警告。這個判斷在什麼情況下會出錯？為什麼 gcc 對 `len - used < 0` 會警告、對 `> 0` 卻不會？另外，為什麼 `int sum = x + y; if (sum < x)` 這種溢位檢查在 `-O2` 下可能完全失效？

```
len < used會出錯

因爲size_t都是unsigned long, 兩個同型別運算應該還是要unsigned long, 所以>0 gcc語法沒問題, < 0 語法反而不合理

-O2 沒有直接運算,C也沒有定義溢位,從語法看sum是兩者相加,必定大於兩者,所以他永遠爲false
```

> **批改**：**不完整**（盒子 1 → 1）。第一問對（`len < used`）。補一句：這時 `len - used` 回繞成很大的正數，程式誤以為還有空間。第二問大致對：「`< 0` 不合理」說精確一點，是無號數 `< 0` **永遠為假**，`-Wtype-limits` 專抓這種永遠成立或永遠不成立的比較；`> 0` 等於 `!= 0`，結果會變，所以不警告。第三問**錯，跟 10-04、10-08 錯在同一處（第三次）**：gcc 不是把檢查變成「永遠為 false」，而是在「不會溢位」的假設下，把 `x + y < x` 兩邊同減 `x`，化簡成 **`y < 0`**。你的前提「相加必定大於兩者」也不對：`y` 是負數時，`x + y` 本來就比 `x` 小，所以 gcc 不能把檢查刪掉，只能留下 `y < 0`。結果是這個檢查不再檢查溢位：真的溢位時（`y` 是正數、`sum` 回繞成負數），`y < 0` 為假，抓不到。
>
> **參考答案**【[第七節](../c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.md#七陷阱有號和無號混在一起比較)〈`-Wtype-limits` 只抓「永遠成立／永遠不成立」的比較〉、[第八節](../c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.md#八溢位無號回繞有號是未定義行為)〈另一種寫法：`x + y < x` 被改寫成 `y < 0`〉】
>
> 核心關鍵：
> 1. `len < used` 時，`len - used` 回繞成很大的正數，判斷誤以為「還有空間」。
> 2. 無號數 `< 0` 永遠為假，所以 gcc 警告；`> 0` 等於 `!= 0`，結果不固定，是合法寫法，所以不警告。
> 3. 有號溢位是 UB，gcc 假設它不會發生，把 `x + y < x` 改寫成 **`y < 0`**；真的溢位時（`y` 是正的），這個檢查抓不到。
>
> 詳細說明：`len == used` 時結果是 0，`> 0` 為假，所以不是「永遠為真」，只有 `len < used` 會出錯。警告來自 `-Wtype-limits`（`-Wextra` 會開啟）。溢位那一問的記法：「`x + y < x`」在數學上（沒有溢位）跟「`y < 0`」完全等價，gcc 只是做了這個代數化簡，而這個化簡只在「不會溢位」時才成立。正確的溢位檢查要在運算**之前**，用不會溢位的式子判斷，例如 `y > 0 && x > INT_MAX - y`。

> 1. `ldd` 讓動態載入器實際處理這支程式：載入器照常找、載入全部依賴（含間接依賴），在進 `main` 前停下來印清單。
> 2. 風險：載入器是誰由檔案的 `INTERP` 決定，攻擊者可以寫成自己的程式，跑 `ldd` 就執行了它。

>
> 詳細說明：`grep -n LD_TRACE /usr/bin/ldd` 可以看到腳本裡的 `LD_TRACE_LOADED_OBJECTS=1`；直接設這個變數跑程式（`LD_TRACE_LOADED_OBJECTS=1 /usr/bin/curl`）會得到跟 `ldd` 一樣的清單。所以對來路不明的檔案要看依賴，用 `objdump -p` 或 `readelf -d`。

>
> **參考答案**【[第四節](../c/objdump能不能代替ldd找依賴庫-需求單與實際載入.md#四找不到函式庫時兩者各看到什麼)、[第二節](../c/objdump能不能代替ldd找依賴庫-需求單與實際載入.md#二為什麼會差這麼多兩者看的是不同時間點)】
>
> 核心關鍵：
> 1. 連結時是 **`ld`** 在找：照 `-L./lib` 找到 `libfoo.so`，在執行檔寫下 `NEEDED libfoo.so`，**只有名字、沒有路徑**。
> 2. 執行時是**動態載入器**在找：它不知道當初的 `-L`，只找自己的預設路徑（加上 `LD_LIBRARY_PATH` 等），所以找不到。
> 3. `objdump -p` 照樣列出 `NEEDED libfoo.so`（看不出問題）；`ldd` 顯示 `libfoo.so => not found`。
>

>
