## 字元：[字元是什麼-char就是1byte的整數與ASCII和UTF-8](../c/字元是什麼-char就是1byte的整數與ASCII和UTF-8.md)

### 字元 4. 情境題：你寫了一個函式，用 `char c` 一個一個 byte 讀一段 UTF-8 文字，並用 `if (c > 127)` 判斷「這是不是非 ASCII 的 byte」。在本機這個判斷會成立嗎？為什麼？該怎麼改？

> 盒子 2｜過去的作答：[s1-02 quiz.md 第 4 題](../small-project/s1-02-data-repr/quiz.md#4-情境題你寫了一個函式用-char-c-一個一個-byte-讀一段-utf-8-文字並用-if-c--127-判斷這是不是非-ascii-的-byte在本機這個判斷會成立嗎為什麼該怎麼改)

```
不會

ascii 是0~127, 但char有可能是負數所以 不只>127 不是 ascii, < 0 也不是

if (c > 127 || c < 0)
```

> **批改**：**大致對**（盒子 2 → 2）。「不會成立」對，改法也能用。缺兩點：(1) 沒講出**為什麼 `> 127` 永遠是假**：本機 `char` 是有號的，範圍 −128～127，任何 `char` 都不可能大於 127，所以你改法裡的 `c > 127 ||` 那半是死的（`-Wextra` 會警告 `comparison is always false`），真正在做事的只有 `c < 0`；(2) `c < 0` 依賴「`char` 有號」，換到 ARM（`char` 通常無號）就變成永遠假。正解是改**讀法**，不是補條件。
>
> **參考答案**【[字元第四節](./../c/字元是什麼-char就是1byte的整數與ASCII和UTF-8.md#跟第-2-課的連結char-有號讀到中文會變負數)〈跟第 2 課的連結〉、〈[判斷「是不是非 ASCII 的 byte」](./../c/字元是什麼-char就是1byte的整數與ASCII和UTF-8.md#判斷是不是非-ascii-的-byte用哪個型別為什麼是-127)〉】：不會成立。本機 `char` 有號（−128～127），UTF-8 的非 ASCII byte 是 `0x80`～`0xff`，用 `char` 讀變成負數（例如 `0xe5` → −27），`c > 127` 永遠為假。改成 `unsigned char c`（或比較時寫 `(unsigned char)c > 127`），byte 就照 0～255 讀，`> 127` 的意思才正確。不要改成 `unsigned int`：會先符號擴展成 `0xffffffe5`，判斷碰巧對、值卻是錯的。

## interp：[ELF的interpreter是什麼-動態載入器與井字號驚嘆號](../c/ELF的interpreter是什麼-動態載入器與井字號驚嘆號.md)

### interp 1. 動態連結的執行檔裡，interpreter 的路徑寫在哪裡？`execve` 之後，核心先執行的是你的程式還是它？為什麼要這樣安排？

> 盒子 2｜過去的作答：[s1-01 quiz.md 第 1 題](../small-project/s1-01-hello-compile/quiz.md#1-動態連結的執行檔裡interpreter-的路徑寫在哪裡execve-之後核心先執行的是你的程式還是它為什麼要這樣安排)

```
在program header

先執行interpreter

因爲需要interpreter 把其他函式庫加載進來
```

> **批改**：**對**（盒子 2 → 3）。三問都答出：寫在程式標頭（`INTERP`）、核心先跑 interpreter、因為要先把函式庫載入。補一個細節：`INTERP` 指向 `.interp` 區段那串路徑；載入器除了「載入」，還要把符號的真實位址填好（見下一題）。
>
> **參考答案**【[interp 第一節](./../c/ELF的interpreter是什麼-動態載入器與井字號驚嘆號.md#一它寫在執行檔的哪裡)、[第二節](./../c/ELF的interpreter是什麼-動態載入器與井字號驚嘆號.md#二執行時發生什麼事)】：路徑寫在程式標頭表的 `INTERP` 項（指向 `.interp` 區段，內容是 `/lib64/ld-linux-x86-64.so.2`）。核心 `execve` 時把程式和載入器都映射進記憶體，**先執行載入器**；載入器依 `NEEDED` 找到並映射 `libc.so.6`、檢查版本、填好 `puts` 等符號的位址，最後跳到程式的進入點。這樣安排是因為程式一開始就要呼叫函式庫，函式庫必須在程式的第一條指令之前就接好。

### interp 2. `ld` 和 `ld.so`（`ld-linux-x86-64.so.2`）各在什麼時間點、做什麼事？

> 盒子 2｜過去的作答：[s1-01 quiz.md 第 2 題](../small-project/s1-01-hello-compile/quiz.md#2-ld-和-ldsold-linux-x86-64so2各在什麼時間點做什麼事)

```
ld: 連接時,負責將.o的需求(section header), 寫出來並整理kernel看得懂的格式 與 NEED,在program header, 例如動態載入器,所有section元素的內存分頁

ld.so: 執行時,kernel把他加載進來,他在根據需求單NEED把需要的函式庫載入,在跳入main的entrypoint
```

> **批改**：**不完整**（盒子 2 → 1）。時間點兩個都對，`ld` 寫 `NEEDED`、`INTERP`、建程式標頭這部分也對。問題有三：
> (1) `ld` **最主要的工作沒寫**：把多個 `.o` 的同類區段合併、決定位址，然後**把 `call` 後面的 `00 00 00 00` 洞填上**（重定位）。你寫的「將 `.o` 的需求（section header）寫出來」不對——區段標頭表不是需求單，`.o` 本來就有區段標頭表；「需求單」指的是 `NEEDED`。
> (2) `ld.so` 漏了**接線**：載入函式庫之後，要把 `puts` 這些符號的真實位址填進 `.got`，程式才呼叫得到。這是上次就指出的卡點，這次又漏了。
> (3) `ld.so` 跳去的是**進入點 `_start`**，不是 `main`。`_start` 再呼叫 libc 的 `__libc_start_main`，由它呼叫 `main`。這也是 9/27 指出過的。
>
> **參考答案**【[interp 第二節](./../c/ELF的interpreter是什麼-動態載入器與井字號驚嘆號.md#二執行時發生什麼事)〈「跳進程式」是什麼意思：進入點（entry point）〉、[第 1 課第五節](./../c/hello.c怎麼變成能跑的程式-編譯的四個階段.md#五連結把洞接上但-puts-還是沒接完)】：
> - **`ld`（連結時，`gcc` 的最後一步，只做一次）**：合併各 `.o` 的區段、決定每個符號的位址、把 `call` 的洞填上；遇到在 `libc.so.6` 裡的符號（例如 `puts`）填不了真實位址，只寫一張**需求單**：`NEEDED libc.so.6`、`INTERP` 路徑，並產生程式標頭表。
> - **`ld.so`（執行時，每次執行都做）**：依 `NEEDED` 找到函式庫並映射進記憶體、檢查版本、把 `puts` 等符號的真實位址填進 `.got`（接線），最後跳到程式的進入點 `_start`。

>

```
他是根據需求單section header來建立需求單每個元素的內存分頁,根據權限.然後根據是否有--static決定要不要提供interpreter,最後再把這些信息用來建立program header
```

> **批改**：**大致對**（盒子 2 → 2）。連結器做的事答得好：依權限打包、看是否 `-static` 決定要不要 `INTERP`、產生程式標頭。缺兩點：
> - 前半「代表什麼」：比「`ld` 還沒連結」更直接的說法是 **`.o` 只給連結器用，還沒準備好被核心載入執行**，所以沒有執行視角。
> - 漏了第一步「**把多個 `.o` 的同類區段合併**」（例如各檔的 `.text` 併成一個 `.text`），之後才打包成載入段。另外「需求單 section header」用詞錯（同 ELF 1）；打包的單位是**載入段**，「內存分頁」是載入段的對齊單位，不是它本身。
>
> **參考答案**【[ELF 第四節](./../c/ELF是什麼-可執行與可連結格式的兩種視角.md#四名字的關鍵兩種視角)〈最有力的證據：`.o` 沒有執行視角〉】：`.o` 沒有程式標頭表，代表它只有連結視角——只給連結器用，還不能被核心載入執行。連結器把一堆 `.o` 的區段**合併**，再把權限相同的區段打包成載入段（`LOAD`，依分頁對齊），動態連結時加上 `INTERP`、`DYNAMIC` 等項，最後寫出程式標頭表，「可連結的」才變成「可執行的」。

### gcc 5. 情境題：你在自己的程式裡用 `-O2` 編譯，`gdb` 印某個變數時顯示 `<optimized out>`。你會怎麼處理？如果是在 kernel 裡遇到同樣的狀況，處理方式又有什麼不同？

```
我會在程式碼,直接把這個變數打印出來,或者直接重新用-O0編譯

如果是kernel,那就只能用程式碼來打印了
```

> **批改**：**大致對**（盒子 2 → 2）。自己的程式的兩種處理（印出來、用 `-O0` 重編）都對。kernel 那半跟 9/30 一樣：「只能用程式碼打印」方向對，但沒講出**為什麼只能這樣**——kernel **不能用 `-O0` 編**。另外 kernel 裡印東西用的是 `printk`，不是 `printf`（kernel 不連結 libc）。
>
> **參考答案**【[gcc 第三節](./../c/gcc最佳化等級-O0到O3差在哪.md#三為什麼除錯要用--o0)、[第四節](./../c/gcc最佳化等級-O0到O3差在哪.md#四跟-kernel-的關係)】：自己的程式：改用 `-O0 -g`（或 `-Og -g`）重新編譯，變數就有固定位置；不能重編時加 `printf` 印出來。kernel：**不能用 `-O0` 重編**（kernel 依賴編譯器一定會做的內嵌與刪除死碼才編得過），`<optimized out>` 是常態，只能改用 `printk`、tracing 等方法觀察，並學會讀最佳化後的組合語言。一句話：自己的程式可以「改編譯方式」，kernel 只能「改觀察方式」。

## GNU：[GNU是什麼-Linux核心與GNU工具的分工](../linux/GNU是什麼-Linux核心與GNU工具的分工.md)

### GNU 3. 情境題：一支 shell 腳本在你的 Ubuntu 上用 `bash` 測試完全正常，放到 OpenWrt 上卻出錯。從本篇的角度，最可能的原因是什麼？寫腳本時該怎麼預防？

> 盒子 2｜過去的作答：[s1-01 quiz.md 第 3 題](../small-project/s1-01-hello-compile/quiz.md#3-情境題一支-shell-腳本在你的-ubuntu-上用-bash-測試完全正常放到-openwrt-上卻出錯從本篇的角度最可能的原因是什麼寫腳本時該怎麼預防)

```
最有可能就是兩個os的shell是不同的

儘量用所有腳本都可以讀的腳本語法(posix規範),並且在openwrt測試之前,現在ubuntu(bash)用openwrt(ash)的shell測試
```

> **批改**：**對**（盒子 2 → 3）。原因（shell 不同）、預防（只用 POSIX 語法、在本機用 OpenWrt 那種 shell 測）都答出，這次也說出了 `ash`，比 9/30 完整。可以再精確一點：OpenWrt 的 `/bin/sh` 是 BusyBox 的 `ash`，本機要用 `busybox sh` 或 `dash` 來跑；而且本機 `/bin/sh -> bash`，直接 `./腳本` 測不出問題。
>
> **參考答案**【[GNU 第四節](./../linux/GNU是什麼-Linux核心與GNU工具的分工.md#四不是-gnu-的-linux你已經遇過了)】：OpenWrt 不是 GNU 使用者空間，沒有 bash，`/bin/sh` 是 BusyBox 的 `ash`；腳本裡用了 bash 的擴充語法（陣列、`[^...]` 等）就會出錯。預防：只用 POSIX 規定的語法與選項，並在本機用 `busybox sh 腳本`（或 `dash`）測試——本機 `/bin/sh` 指向 bash，直接執行測不出問題。

### GNU 4. GPL 的 copyleft 要求什麼？glibc 用 LGPL 而不是 GPL，對「商業軟體能不能連結 libc」有什麼差別？

> 盒子 2｜過去的作答：[s1-01 quiz.md 第 4 題](../small-project/s1-01-hello-compile/quiz.md#4-gpl-的-copyleft-要求什麼glibc-用-lgpl-而不是-gpl對商業軟體能不能連結-libc有什麼差別)

```
要求 開發者開發的程式如果連接了GPL的軟體, 或者修改軟體後 必須對外發布

用LGPL 連接 glibc後不用對外發佈
```

> **批改**：**不完整**（盒子 2 → 1）。LGPL 那半對（商業軟體連結 glibc 不必開放自己的原始碼）。GPL 那半講錯了條件與內容：
> - GPL **不要求你「對外發布」**。修改了 GPL 軟體自己用、不給別人，沒有任何義務。義務是在**散布（distribute）**的時候才發生：**你把修改版（或連結了它的程式）給別人時**，必須用同樣的授權、並提供原始碼。
> - 你寫的「必須對外發布」把「散布時要附原始碼」說成了「有義務發布」，方向反了；也沒寫出 copyleft 最核心的「**同樣的授權**」——自由不能在傳遞途中被拿走。
>
> **參考答案**【[GNU 第五節](./../linux/GNU是什麼-Linux核心與GNU工具的分工.md#五gplgnu-最深遠的影響)】：copyleft：可以自由使用、修改、散布，但**散布修改後的版本時，必須用同樣的授權（GPL）、並提供原始碼**。glibc 用 LGPL（較寬鬆）：允許非自由的程式**連結**它而不必開放自己的原始碼（只有改了 glibc 本身、再散布時，才要公開對 glibc 的修改）。所以任何商業軟體都能動態連結 `libc.so.6`；如果 glibc 是 GPL，連結它的程式在散布時就得整個用 GPL 開放。
