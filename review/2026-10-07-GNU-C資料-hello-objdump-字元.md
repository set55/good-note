### GNU 5. 你將來送 kernel patch 時要加的 `Signed-off-by:` 跟 GPL 有什麼關係？

> 盒子 2｜過去的作答：[s1-01 quiz.md 第 5 題](../small-project/s1-01-hello-compile/quiz.md#5-你將來送-kernel-patch-時要加的-signed-off-by-跟-gpl-有什麼關係)

```
這個叫做DOR,GPL讓我們有自由研讀,修改,與發佈的權力,當我們發佈的時候必須著名,這樣以後我們修改的部分出問題的時候可以找到責任歸屬
```

> **批改**：**不完整**（盒子 2 → 1）。「出問題時找得到責任歸屬」方向對，但有三處錯或缺：(1) 名字是 **DCO**（Developer Certificate of Origin，開發者原創聲明），不是 DOR；(2) 它負責的不是「程式出 bug 找誰」，而是**著作權與授權**：聲明「這段是我寫的，或我有權用 GPL-2.0 貢獻它」，kernel 才能合法地整包以 GPL-2.0 散布；(3)「GPL 規定發布時必須署名」不對——`Signed-off-by:` 是 **kernel 社群的規定**，GPL 條文本身沒有這個要求。
>
> **參考答案**【[第五節](../linux/GNU是什麼-Linux核心與GNU工具的分工.md#五gplgnu-最深遠的影響)】`Signed-off-by:` 是 DCO：加上這一行，就是聲明這段程式碼是你自己寫的，或你有權以這個專案的授權（kernel 是 GPL-2.0）貢獻它。Linux 核心以 GPL-2.0 散布，每段合併進去的程式碼都必須能合法地以 GPL-2.0 散布；DCO 讓每個 patch 都有人為此負責，出了著作權爭議時查得到是誰聲明的。它是 kernel 社群的規定，不是 GPL 條文本身的要求。

### C資料 2. `int x = 0x12345678; unsigned char *b = (unsigned char *)&x;` 在本機 `*b` 是多少？換到大端序的機器上是多少？為什麼 `int *p = &x;` 的 `*p` 在兩種機器上都是 `0x12345678`？

> 盒子 2｜過去的作答：[s1-02 quiz.md 第 2 題](../small-project/s1-02-data-repr/quiz.md#2-int-x--0x12345678-unsigned-char-b--unsigned-char-x-在本機-b-是多少換到大端序的機器上是多少為什麼-int-p--x-的-p-在兩種機器上都是-0x12345678)

```
0x78

0x12

因爲指標類型int在兩種機械大小都是4byte(不是指標的大小,是從起點byte開始數4個byte),大端序從0x12開始往0x34 數4個byte
小端從0x78 往 0x56 數4個byte
```

> **批改**：**大致對**（盒子 2 → 2）。`0x78`、`0x12` 都對；「`int *` 從起點讀 4 個 byte」也對。缺的是**為什麼兩邊讀回來都一樣**：關鍵是每台機器用**自己那一套順序寫進去、再用同一套順序讀出來**，一來一回抵消——小端機器把第一個 byte（`0x78`）當最低位，大端機器把第一個 byte（`0x12`）當最高位。你寫了「從哪個 byte 開始數」，沒寫出「第一個 byte 被當成最低位還是最高位」。
>
> **參考答案**【[第三節](../c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.md#三位元組順序endianness)〈什麼時候要在意位元組順序？〉】本機（小端序）`*b` 是 `0x78`，大端序機器是 `0x12`。`*p` 兩邊都是 `0x12345678`：小端機器寫成 `78 56 34 12`、讀的時候把第一個 byte 當最低位；大端機器寫成 `12 34 56 78`、讀的時候把第一個 byte 當最高位——每台機器都用自己那一套順序寫、再用同一套順序讀，剛好抵消。看得出順序的只有兩種情況：用 `unsigned char *` 一個 byte 一個 byte 看，或一台機器寫、另一種順序的機器讀（網路封包、檔案）。

### C資料 3. `int n = -1; unsigned int len = 5;`，`n < len` 為什麼是假？只加 `-Wall` 編譯，gcc 會不會提醒你？

> 盒子 2｜過去的作答：[s1-02 quiz.md 第 3 題](../small-project/s1-02-data-repr/quiz.md#3-int-n---1-unsigned-int-len--5n--len-為什麼是假只加--wall-編譯gcc-會不會提醒你)

```
unsigned int的等級比int大,所以-1轉成unsigned看就是 unsinged int的最大值,因此是假

不會,因爲類型compare的警告要下-Wextra (Wsigned-compare)
```

> **批改**：**大致對**（盒子 2 → 2）。「`-1` 轉成無號變成最大值，所以為假」「`-Wall` 不會提醒、要 `-Wextra`」都對（選項名是 `-Wsign-compare`，不是 `Wsigned-compare`）。**有一處觀念錯**：`unsigned int` 和 `int` 的等級（rank）**一樣**，不是比較大。規則是「無號那邊的等級 **≥** 有號那邊 → 轉成無號」，等級相同時無號贏。這一點跟 C資料 10（`long` 對 `unsigned int`，10-05 答過）是同一條規則，值得再看一次。
>
> **參考答案**【[第四節](../c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.md#四無號整數二進位與回繞)〈怎麼確定一個常數的型別？比較時以誰為準？〉、[第七節](../c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.md#七陷阱有號和無號混在一起比較)】比較之前，一般算術轉換把 `int` 轉成 `unsigned int`（兩者等級相同，無號贏）：位元不變、換成無號讀法，`-1`（`0xffffffff`）變成 4294967295 > 5，所以 `n < len` 為假。只加 `-Wall` 不會提醒（C 的 `-Wall` 不含 `-Wsign-compare`），要加 `-Wextra`。

### C資料 4. `int y = x + 1; return y > x;` 在 `x = INT_MAX` 時，`-O0` 回傳 0、`-O2` 回傳 1。為什麼會這樣？這算不算 gcc 的 bug？kernel 用哪個選項避免這種情況，代價是什麼？

> 盒子 2｜過去的作答：[s1-02 quiz.md 第 4 題](../small-project/s1-02-data-repr/quiz.md#4-int-y--x--1-return-y--x-在-x--int_max-時-o0-回傳-0-o2-回傳-1為什麼會這樣這算不算-gcc-的-bugkernel-用哪個選項避免這種情況代價是什麼)

```
-O0 實際計算y,x是int最大值,再加1,會變成INT_MIN,所以回傳0
-O2 因爲溢位是UB的行爲,gcc不能確定是否發生溢位,他只能看到y-x = 1 -> y-x>0 所以爲真

UB行爲是未定義的,不算bug

有一個option,可以讓gcc在UB的行爲進行實際計算,代價是計算的增加,會比原本沒有下這個命令還要慢一點
```

> **批改**：**不完整**（盒子 2 → 1）。`-O0` 對、「不算 bug」對。兩處問題：(1) `-O2` 的推理**說反了**：不是「gcc 不能確定會不會溢位」，而是正因為有號溢位是 UB，C 標準允許 gcc **假設它一定不會發生**；在這個假設下 `x + 1 > x` 永遠成立，直接回傳 1。(2) 選項沒說出名字：kernel 用 **`-fno-strict-overflow`**（等於 `-fwrapv -fwrapv-pointer`），讓溢位照二補數回繞、變成有定義的行為。代價「少了一些最佳化、可能稍慢」你答到了。
>
> **參考答案**【[第八節](../c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.md#八溢位無號回繞有號是未定義行為)】有號溢位是未定義行為（UB），C 標準允許編譯器**假設它不會發生**。`-O0` 照字面算，`INT_MAX + 1` 回繞成 `INT_MIN`，`y > x` 為假 → 0；`-O2` 推論「`x + 1` 一定大於 `x`」，直接回傳 1。不是 gcc 的 bug：標準對發生 UB 的程式沒有任何要求，兩種結果都合法。kernel 用 `-fno-strict-overflow`（等於 `-fwrapv -fwrapv-pointer`），讓溢位照二補數回繞、變成有定義的行為；代價是編譯器少了依賴「不會溢位」這個假設的最佳化，程式可能稍慢。

### C資料 6. `printf("%p")` 印出 `0x7ffe50b23624`，只有 12 位十六進位。指標到底佔幾個 byte？印出來為什麼比較短？如果在 kernel 的錯誤訊息裡看到 `0xffff888102a4c000`，從位址的長相你能判斷什麼？

> 盒子 2｜過去的作答：[s1-02 quiz.md 第 6 題](../small-project/s1-02-data-repr/quiz.md#6-printfp-印出-0x7ffe50b23624只有-12-位十六進位指標到底佔幾個-byte印出來為什麼比較短如果在-kernel-的錯誤訊息裡看到-0xffff888102a4c000從位址的長相你能判斷什麼)

```
8個byte
剩下2個byte是kernel在用
0xffff是kernel用的指標
0x888102a4c000才是使用者空間可以看的記憶體位址
```

> **批改**：**不完整**（盒子 2 → 1）。「8 byte」對。另外兩問錯：(1) 印出來比較短，**不是**「剩下 2 byte 給 kernel 用」：使用者空間的位址上面 2 byte 一定是 `00 00`，而 `%p` 不補前導零，所以只印 12 位。x86-64 的虛擬位址只用 48 bit，上面 16 bit 必須跟第 47 bit 相同（canonical address）。(2) `0xffff888102a4c000` 不能拆成「`0xffff` 是 kernel 的、後面是使用者空間的位址」——**整個**是一個位址；上面 16 bit 全是 1，代表它落在位址空間的**核心那一半**，所以整個是 kernel 位址。
>
> **參考答案**【[第二節](../c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.md#二指標就是位址)〈位址看起來只有 6 byte？〉】指標佔 8 byte。x86-64 虛擬位址只用 48 bit，上面 16 bit 必須跟第 47 bit 相同（canonical address）。使用者空間是 `0x0000…`～`0x00007fff…`，上面 2 byte 一定是 `00 00`，`%p` 不補零，就只印出 12 位。`0xffff888102a4c000` 上面 16 bit 全是 1，屬於位址空間的核心那一半，所以這是 kernel 的位址。

## hello：[hello.c怎麼變成能跑的程式-編譯的四個階段](../c/hello.c怎麼變成能跑的程式-編譯的四個階段.md)

### hello 1. `gcc hello.c` 背後實際是哪幾個程式在接力？為什麼說 `gcc` 是「總指揮」？

```
cc1 前處理,轉成組合語言
ac 組譯
ld 連接
```

> **批改**：**大致對**（盒子 3 → 3）。`cc1`（前處理＋轉成組合語言）、組譯器、`ld` 三棒對。小地方：組譯器是 **`as`**（不是 `ac`）；`ld` 是由 `collect2` 呼叫的。「總指揮」的理由缺了關鍵的一半：**`gcc` 自己不做任何轉換**，只負責依序呼叫它們、在中間傳遞暫存檔；`gcc -v` 可以看到它實際執行的每個命令。

> **參考答案**【[第一節](../c/hello.c怎麼變成能跑的程式-編譯的四個階段.md#一四個階段總覽)】本機實際接力的是 `cc1`（前處理＋編譯，C → 組合語言）→ `as`（組合語言 → 機器碼的 `.o`，還有洞、不能執行）→ `collect2` 呼叫 `ld`（連結成執行檔）。`gcc` 自己不做任何轉換，只負責依序呼叫它們、在中間傳遞暫存檔，所以叫總指揮（driver）；`gcc -v` 看得到它實際執行的每個命令。

> 盒子 3｜過去的作答：[s1-01 quiz.md 第 2 題](../small-project/s1-01-hello-compile/quiz.md#2-helloi-裡有-printf-的宣告卻沒有它的程式碼那它的程式碼在哪是在哪個時間點由誰把呼叫-printf和printf-的程式碼接起來的)

```
在c標準函式庫

在執行的時候,由interpreter
```

### objdump 2. `ldd` 是怎麼得到依賴清單的？從這個機制解釋：為什麼對來路不明的執行檔用 `ldd` 有風險，`objdump -p` 卻沒有？

> 盒子 3｜過去的作答：[s1-01 quiz.md 第 2 題](../small-project/s1-01-hello-compile/quiz.md#2-ldd-是怎麼得到依賴清單的從這個機制解釋為什麼對來路不明的執行檔用-ldd-有風險objdump--p-卻沒有)

```
ldd 載入interpreter, 由interpreter載入所有直接,簡介函式庫
因爲他會實際去讀函式庫的內容,如果這個有問題的函式庫有攻擊行爲,就有可能執行
objdump -p 只是顯示header的記錄
```

> **批改**：**不完整**（盒子 3 → 1）。機制對：`ldd` 讓動態載入器去處理程式，載入器照常載入直接與間接的函式庫。`objdump -p` 只讀檔案裡的紀錄，也對。**風險的來源說錯了**：重點不是「讀到有問題的函式庫」，而是**載入器是誰由這個檔案自己決定**——它寫在檔案的 `INTERP` 裡。攻擊者可以把 `INTERP` 寫成自己的程式，你一跑 `ldd`，執行的就是他的程式。（`ldd` 本身是 shell 腳本，靠設 `LD_TRACE_LOADED_OBJECTS=1` 讓載入器在進 `main` 前停下來印清單。）
>
> **參考答案**【[第三節](../c/objdump能不能代替ldd找依賴庫-需求單與實際載入.md#三ldd-會執行東西這是它的代價)】`ldd` 是 shell 腳本，設 `LD_TRACE_LOADED_OBJECTS=1` 後讓動態載入器處理這支程式；載入器照常找、載入全部依賴，但在進 `main` 前停下來改成印清單。風險：載入器是誰由檔案的 `INTERP` 決定，攻擊者可以寫成自己的程式，跑 `ldd` 就執行了它。`objdump -p` 只讀檔案裡的 `NEEDED`，不啟動任何東西。

## 字元：[字元是什麼-char就是1byte的整數與ASCII和UTF-8](../c/字元是什麼-char就是1byte的整數與ASCII和UTF-8.md)

### 字元 3. `sizeof('A')`、`sizeof("A")`、`sizeof("字")` 在本機各是多少？分別解釋為什麼。

> 盒子 1｜過去的作答：[s1-02 quiz.md 第 3 題](../small-project/s1-02-data-repr/quiz.md#3-sizeofasizeofasizeof字-在本機各是多少分別解釋為什麼)

```
1byte

2 byte

4byte

'A' 是char類型 1byte

"A" 字符串類型,陣列以\0字元結爲 所以2byte

"字" 字符串類型,字用了3個字元char + \0 所以4byte
```

> **批改**：**不完整**（盒子 1 → 1）。`"A"` 2、`"字"` 4 對，理由也對（「字」是 3 個 byte）。`sizeof('A')` **錯**，跟 10-04 那次錯在同一個地方：答案是 **4**，不是 1。在 C 裡，單引號的字元常數 `'A'` 型別是 **`int`**，不是 `char`；C++ 才是 `char`。記法：`'A'` 只是寫數字 65 的另一種方式，而 C 裡沒有後綴的整數常數都是 `int`。
>
> **參考答案**【[第三節](../c/字元是什麼-char就是1byte的整數與ASCII和UTF-8.md#三c-的字元常數單引號而且型別是-int)、[第四節](../c/字元是什麼-char就是1byte的整數與ASCII和UTF-8.md#四中文字一個-byte-裝不下utf-8-用-3-個-byte)】`sizeof('A')` = 4：在 C 裡，字元常數 `'A'` 的型別是 `int`（C++ 才是 `char`）。`sizeof("A")` = 2：`'A'` 加上結尾的 `'\0'`。`sizeof("字")` = 4：UTF-8 用 3 byte 表示「字」，再加上 `'\0'`。
