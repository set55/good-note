## 字元：[字元是什麼-char就是1byte的整數與ASCII和UTF-8](../html/c/字元是什麼-char就是1byte的整數與ASCII和UTF-8.html)

### 字元 5. 有人說「『字』是 3 個字元」，另一個人說「是 1 個字元」，誰對？`strlen("字")` 和 `mbstowcs(NULL, "字", 0)` 各會得到多少？如果程式忘了呼叫 `setlocale`，後者會得到什麼，那個數字是怎麼來的？

> 盒子 1｜過去的作答：[s1-02 quiz.md 第 5 題](../small-project/s1-02-data-repr/quiz.md#5-有人說字是-3-個字元另一個人說是-1-個字元誰對strlen字-和-mbstowcsnull-字-0-各會得到多少如果程式忘了呼叫-setlocale後者會得到什麼那個數字是怎麼來的)、[10-04 複習](./2026-10-04-字元-C資料-objdump-hello-ELF.md)

```
如果字元是指char類型, 那就是3個char
如果是指unicode字元,那就是1個
所以都對

strlen: 3
mbstowcs: 1

如果setlocale沒有用LC_ALL,那就使用C函式庫默認,那最後就是3
c默認的是1個byte大小,所以3就是這樣來的
```

> **批改**：**不完整**（盒子 1 → 1）。前兩問**對**：以 `char`（byte）算是 3 個、以 Unicode 字元算是 1 個；`strlen` = 3、`mbstowcs` = 1（呼叫過 `setlocale` 之後）。第三問**錯**：忘了 `setlocale` 時「用 C 函式庫預設的 locale」方向對，但結果不是 3。`"C"` locale 只認 ASCII，看到 `0xe5` 這種大於 127 的 byte 不是「當成 1 個字元」，而是**看不懂、回報錯誤**。10-04 這一問也沒答出數字。
>
> **參考答案**【[第五節](../html/c/字元是什麼-char就是1byte的整數與ASCII和UTF-8.html#五那字是-3-個字元嗎看你說的是哪一種字元)】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. 兩個人都對：以 `char`（byte）算是 **3** 個，以 Unicode 字元算是 **1** 個。
> 2. `strlen("字")` = 3；呼叫 `setlocale` 之後 `mbstowcs` = 1。
> 3. 忘了 `setlocale` → 用 `"C"` locale，看不懂 UTF-8 → 回傳 `(size_t)-1`，也就是 **18446744073709551615**（2⁶⁴ − 1）。
>
> **詳細說明**：「字」在 UTF-8 是 3 個 byte（`e5 ad 97`），碼位是 U+5B57。`strlen` 數的是 byte；`mbstowcs` 數的是字元，但它要先知道編碼，必須呼叫 `setlocale(LC_ALL, "")` 讀進環境變數 `LANG`（例如 `zh_TW.UTF-8`）。沒呼叫時，不管 `LANG` 設什麼，程式都用預設的 `"C"` locale，只認 ASCII（0～127），看到 `0xe5` 就判定是無效的多位元組序列，回傳 `(size_t)-1`。`size_t` 在本機是 8 byte 無號，`-1` 轉成無號就是全部位元為 1。

## C資料：[C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號](../html/c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.html)

### C資料 9. 情境題：有人寫了 `if (len - used > 0)` 判斷「緩衝區還有沒有剩餘空間」，`len`、`used` 都是 `size_t`，用 `-Wall -Wextra` 編譯沒有任何警告。這個判斷在什麼情況下會出錯？為什麼 gcc 對 `len - used < 0` 會警告、對 `> 0` 卻不會？另外，為什麼 `int sum = x + y; if (sum < x)` 這種溢位檢查在 `-O2` 下可能完全失效？

> 盒子 1｜過去的作答：[s1-02 quiz.md 第 9 題](../small-project/s1-02-data-repr/quiz.md#9-情境題有人寫了-if-len---used--0-判斷緩衝區還有沒有剩餘空間lenused-都是-size_t用--wall--wextra-編譯沒有任何警告這個判斷在什麼情況下會出錯為什麼-gcc-對-len---used--0-會警告對--0-卻不會另外為什麼-int-sum--x--y-if-sum--x-這種溢位檢查在--o2-下可能完全失效)、[10-04 複習](./2026-10-04-字元-C資料-objdump-hello-ELF.md)

```
size_t是unsigned long,無號相減發生溢位 這個判斷會出錯 也就是len < used 結果還是>0,也就是無論如何這個判斷永遠爲真

因爲len 與 used都是無號, 結果也是無號,所以小於0會發warn, 但是 > 0 是對於unsigned是合理的

因爲溢位在gcc 是UB(gcc根本沒有定義溢位的情況),所以-O2 的話 認爲int相加 sum不可能<x 必爲假
```

> **批改**：**不完整**（盒子 1 → 1）。
> - 第一問大致對：`len < used` 時相減回繞成很大的正數，誤判有空間。但「無論如何這個判斷永遠為真」不對：`len == used` 時結果是 0，`> 0` 為假。無號數的 `> 0` 等於 `!= 0`。
> - 第二問**對**。
> - 第三問**錯，跟 10-04 錯在同一處**：「UB」答出來了，但 gcc 不是把 `sum < x` 當成「必為假」。gcc 假設溢位不會發生，在這個假設下 `x + y < x` 等於 **`y < 0`**，檢查被改寫成「`y` 是不是負的」。真的溢位時（`y` 是正的），這個檢查就抓不到。
>
> **參考答案**【[第七節](../html/c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.html#七陷阱有號和無號混在一起比較)〈`-Wtype-limits` 只抓「永遠成立／永遠不成立」的比較〉、[第八節](../html/c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.html#八溢位無號回繞有號是未定義行為)〈另一種寫法：`x + y < x` 被改寫成 `y < 0`〉】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. `len < used` 時，`len - used` 回繞成很大的正數，判斷誤以為「還有空間」。
> 2. 無號數 `< 0` 永遠為假，所以 gcc 警告；`> 0` 等於 `!= 0`，結果不固定，是合法寫法，所以不警告。
> 3. 有號溢位是 UB，gcc 假設它不會發生，把 `x + y < x` 改寫成 **`y < 0`**；真的溢位時（`y` 是正的），這個檢查抓不到。
>
> **詳細說明**：`len == used` 時結果是 0，`> 0` 為假，所以不是「永遠為真」，只有 `len < used` 這種情況會出錯。警告來自 `-Wtype-limits`（`-Wextra` 會開啟），它只抓「永遠成立／永遠不成立」的比較。溢位那一問：gcc 不是把檢查當成「必為假」直接刪掉，而是在「不會溢位」的假設下，把它化簡成等價的 `y < 0`。正確的溢位檢查要在運算**之前**，用不會溢位的式子判斷，例如 `y > 0 && x > INT_MAX - y`。

## objdump：[objdump能不能代替ldd找依賴庫-需求單與實際載入](../html/c/objdump能不能代替ldd找依賴庫-需求單與實際載入.html)

### objdump 3. 一支程式連結時用了 `-L./lib -lfoo`，編譯成功；執行時卻出現 `error while loading shared libraries: libfoo.so`。用「連結時」與「執行時」分別是誰在找檔案，解釋為什麼連結找得到、執行卻找不到。這時 `objdump -p` 與 `ldd` 各會顯示什麼？

> 盒子 1｜過去的作答：[s1-01 quiz.md 第 3 題](../small-project/s1-01-hello-compile/quiz.md#3-一支程式連結時用了--llib--lfoo編譯成功執行時卻出現-error-while-loading-shared-libraries-libfooso用連結時與執行時分別是誰在找檔案解釋為什麼連結找得到執行卻找不到這時-objdump--p-與-ldd-各會顯示什麼)、[10-04 複習](./2026-10-04-字元-C資料-objdump-hello-ELF.md)

```
連接時, ld 會把這個庫寫入需求單,libfoo.so會寫入needed
執行時, interpreter會去讀這個庫,並把程式碼載入執行檔,實際讀這個檔案
找得到不代表可以讀, 所以如果這個庫不能讀可能就會噴這個錯

objdump -p 會顯示這個執行檔的needed
ldd 會噴 error while loading shared libraries: libfoo.so, 因爲ldd就是用interpreter去載入需求的庫
```

> **批改**：**錯**（盒子 1 → 1）。題目的關鍵是「連結時和執行時**是不同的程式、用不同的路徑**在找」，答案裡沒有提到。
> - 「找得到不代表可以讀，庫不能讀就會噴錯」不是原因。執行時是**動態載入器**在找，它根本不知道當初連結時給的 `-L./lib`，只找自己的預設路徑，所以**找不到**這個檔案，不是讀不了。
> - `objdump -p` 列出 `NEEDED libfoo.so`，**對**。補一句：它看不出有問題。
> - `ldd` 不會噴 `error while loading shared libraries`，它印的是 **`libfoo.so => not found`**。
>
> **參考答案**【[第四節](../html/c/objdump能不能代替ldd找依賴庫-需求單與實際載入.html#四找不到函式庫時兩者各看到什麼)、[第二節](../html/c/objdump能不能代替ldd找依賴庫-需求單與實際載入.html#二為什麼會差這麼多兩者看的是不同時間點)】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. 連結時是 **`ld`** 在找：照 `-L./lib` 找到 `libfoo.so`，在執行檔寫下 `NEEDED libfoo.so`，**只有名字、沒有路徑**。
> 2. 執行時是**動態載入器**在找：它不知道當初的 `-L`，只找自己的預設路徑（加上 `LD_LIBRARY_PATH` 等），所以找不到。
> 3. `objdump -p` 照樣列出 `NEEDED libfoo.so`（看不出問題）；`ldd` 顯示 `libfoo.so => not found`。
>
> **詳細說明**：`-L` 只影響連結時的 `ld`，不會被記進執行檔。執行時找函式庫的是另一個程式（`ld-linux-x86-64.so.2`），它的搜尋順序是：執行檔裡的 `RUNPATH`、`LD_LIBRARY_PATH`、`/etc/ld.so.cache`、預設目錄（`/lib`、`/usr/lib`）。所以修法是在連結時加 `-Wl,-rpath,…` 把路徑寫進執行檔，或執行時設 `LD_LIBRARY_PATH`。`objdump -p` 只讀檔案，看到的是需求單；`ldd` 是請載入器實際找一次，所以才看得到 `not found`。

### objdump 4. 情境題：同事傳來一支 ARM 開發板用的執行檔，問你「它需要哪些函式庫」。你在自己的 x86-64 電腦上該用哪個工具？用 `ldd` 會發生什麼事，為什麼？

> 盒子 1｜過去的作答：[s1-01 quiz.md 第 4 題](../small-project/s1-01-hello-compile/quiz.md#4-情境題同事傳來一支-arm-開發板用的執行檔問你它需要哪些函式庫你在自己的-x86-64-電腦上該用哪個工具用-ldd-會發生什麼事為什麼)、[10-04 複習](./2026-10-04-字元-C資料-objdump-hello-ELF.md)

```
可以用objdump -p or readelf -d去找dynamic section裏面 需要動態載入的庫(needed)

用ldd會發生 not found的錯誤,因爲arm 的interpreter 與 x86不一樣, kernel找不到
```

> **批改**：**不完整**（盒子 1 → 1）。
> - 工具：`readelf -d` **對**。`objdump -p` 不一定行：開發板上的檔案常被剝掉區段標頭，`objdump -p` 找不到 `.dynamic`；`readelf -d` 能透過程式標頭的 `DYNAMIC` 找到同一份資料。
> - `ldd`：「x86 跟 ARM 的載入器不一樣」方向對，但結果和原因都不精確。`ldd` 印的不是 `not found`，而是誤導人的 **`not a dynamic executable`**。原因是 `ldd` 要靠**本機的 x86-64 載入器**實際載入這個檔案，而本機載入器處理不了 ARM 的檔案。這不是「kernel 找不到」。**跟 10-04 錯在同一處**（`ldd` 那一半）。
>
> **參考答案**【[第三節](../html/c/objdump能不能代替ldd找依賴庫-需求單與實際載入.html#三ldd-會執行東西這是它的代價)、[第五節](../html/c/objdump能不能代替ldd找依賴庫-需求單與實際載入.html#五怎麼選)】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. 用 **`readelf -d`** 看 `NEEDED`：只讀檔案、不執行，任何架構的 ELF 都讀得了。
> 2. `ldd` 要靠**本機的 x86-64 載入器**實際載入，處理不了 ARM 的檔案，於是印出誤導人的 **`not a dynamic executable`**。
>
> **詳細說明**：`objdump -p` 平常也行，但開發板上的檔案常被剝掉區段標頭，`objdump -p` 就找不到 `.dynamic`；`readelf -d` 能透過**程式標頭**的 `DYNAMIC` 找到同一份資料，所以比較保險。`ldd` 的訊息之所以誤導，是因為那個檔案明明是動態連結的。直接執行它則會看到核心的 `exec format error`（檔頭的 `Machine` 不是本機 CPU）。

### objdump 1. `objdump -p /usr/bin/curl` 只列出 3 個 `NEEDED`，`ldd` 卻列出 33 行。多出來的是哪幾類東西？為什麼 `objdump` 看不到？

### hello 5. 情境題：你把一支動態連結的程式複製到另一台機器，執行時出現找不到 `libc.so.6` 某個版本符號的錯誤。從本課的哪個階段可以解釋這件事？如果改用 `-static` 編譯，這個問題還會發生嗎？

> 盒子 1｜過去的作答：[s1-01 quiz.md 第 5 題](../small-project/s1-01-hello-compile/quiz.md#5-情境題你把一支動態連結的程式複製到另一台機器執行時出現找不到-libcso6-某個版本符號的錯誤從本課的哪個階段可以解釋這件事如果改用--static-編譯這個問題還會發生嗎)、[10-04 複習](./2026-10-04-字元-C資料-objdump-hello-ELF.md)

```
執行時,kernel 會先去 載入interpreter, interpreter在根據dynamic section 的需求單needed載入需要載入的庫 與確認對應的版本信息
,如果這個時候本地電腦不支持對應版本的庫,就會噴錯

不會 因爲static在ld連接階段就會把那個版本庫的程式碼直接補上 .text的洞
```

> **批改**：**大致對**（盒子 1 → 1）。核心對：**執行時**由 kernel 先載入 interpreter，再由 interpreter 照需求單載入函式庫、檢查版本，本機的 `libc.so.6` 沒有那個版本就報錯。`-static` 不會發生，也對。缺的跟 10-04 一樣：「要哪個版本」是**連結時** `ld` 寫進執行檔的（`readelf -V` 看得到 `GLIBC_2.34`），完整的說法是「連結時記下要求、執行時才被檢查」。另外，`-static` 不是「補上 `.text` 的洞」，而是把 libc 的程式碼**整份複製進執行檔**，執行時根本不需要外部的 `libc.so.6`。
>
> **參考答案**【[第九節](../html/c/hello.c怎麼變成能跑的程式-編譯的四個階段.html#九作業解說四題背後的原因)〈自我測驗第 5 題延伸：「找不到版本符號」是怎麼回事〉】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. **連結時**：`ld` 把需要的符號版本（例如 `GLIBC_2.34`）寫進執行檔。
> 2. **執行時**：動態載入器檢查目標機器的 `libc.so.6` 有沒有提供這個版本，沒有就報 `` version `GLIBC_2.34' not found ``。
> 3. `-static` 不會發生：libc 的程式碼已經整份複製進執行檔，不再找外部的 `libc.so.6`。
>
> **詳細說明**：一句話：「連結時記下要求、執行時才被檢查」。`readelf -V hello` 看得到版本需求；本機的真正門檻是 2.34（`__libc_start_main`），不是 `puts` 的 2.2.5。`-static` 的代價是檔案大，而且 libc 的安全修補要重新編譯才會帶進去。

```
因爲動態編譯的,所有元素的內存分配是相對位址,也就是virtual address,而執行的時候 才會真的分配實際在記憶體的位址(相對位置不變)
```

>
> 靜態版「位址在連結時就固定了」這部分**對**。
>
> **參考答案**【[第三節](../html/c/ELF是什麼-可執行與可連結格式的兩種視角.html#三一種格式四種檔案)〈DYN／EXEC 跟「有沒有動態連結」無關：兩個反例〉】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. 本機 gcc 預設產生 **PIE**（位置無關執行檔），每次執行被放在隨機位址（ASLR），跟共享函式庫一樣「可以放在任意位址」，所以是 DYN。
> 2. `-static` 版是傳統的**固定位址**執行檔，所以是 EXEC。
>
> **詳細說明**：`Type` 只看「是不是 PIE」，**跟有沒有動態連結無關**，兩個反例：`-no-pie` 照樣動態連結，`Type` 卻是 EXEC；`-static-pie` 是靜態連結，`Type` 卻是 DYN。所以「因為是動態編譯的」不是原因。

### ELF 4. 區段（section）和載入段（segment）差在哪？為什麼核心載入時要把很多區段打包成少數幾個載入段？

> 盒子 1｜過去的作答：[s1-01 quiz.md 第 4 題](../small-project/s1-01-hello-compile/quiz.md#4-區段section和載入段segment差在哪為什麼核心載入時要把很多區段打包成少數幾個載入段)、[10-04 複習](./2026-10-04-字元-C資料-objdump-hello-ELF.md)

```
section 是給連接器ld看的, 連接器根據section給的每個元素的權限 合併成同權限的分頁
segment是給 interpreter看的,根據segment的分頁實際把各分頁的資料實際分配到真實的記憶體位址

因爲記憶體位址分頁的規則需要依據權限分,同一個記憶體位址不能同時有兩種權限例如不能同時是 r_xp, 與 rwxp
```

> **批改**：**對**（改判，盒子 1 → 2；原判大致對，2026-10-08 改用「答到核心關鍵就算對」的標準後改判）。比 10-04 進步：這次講出了「權限以分頁為單位，同一頁不能有兩種權限」。兩處要修：
> 以下兩點是細節，不影響對錯：
> - 載入段主要是給 **kernel** 看的（`execve` 時照 `LOAD` 把執行檔映射進記憶體），動態載入器則用它來載入函式庫。只寫「給 interpreter 看」少了 kernel。
> - 「`ld` 把同權限的區段合併成**分頁**」不精確：合併成的是**載入段**，載入段再依分頁對齊。
>
> **參考答案**【[第四節](../html/c/ELF是什麼-可執行與可連結格式的兩種視角.html#四名字的關鍵兩種視角)】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. 區段（section）是**連結視角**，給 `ld`、`nm`、`objdump` 用，切得很細。
> 2. 載入段（segment）是**執行視角**，給**核心與動態載入器**載入時用，描述哪一塊放進記憶體、權限是什麼。
> 3. 記憶體權限**最小以分頁為單位**設定，同一頁不能有兩種權限，所以把權限相同的區段打包成少數幾個載入段。
>
> **詳細說明**：`hello` 有 31 個區段，卻只有 4 個 `LOAD` 載入段。`execve` 時是核心照執行檔的 `LOAD` 把它映射進記憶體；動態載入器則用同樣的方式載入各個函式庫。打包完，核心只要做幾次映射、每塊設一種權限。合併成的是**載入段**，載入段再依分頁（4096 byte）對齊。


### 陣列 4. 越界的三種下場

#### 陣列 4-1. 越界存取有三種下場：安靜出錯、`stack smashing detected`、segfault。分別是什麼決定會落到哪一種？

> 盒子 1｜過去的作答：[s1-03 quiz.md 4-1](../small-project/s1-03-arrays-pointers/quiz.md#4-1-越界存取有三種下場安靜出錯stack-smashing-detectedsegfault分別是什麼決定會落到哪一種)

```
安靜出錯: 程式執行的時候 指標讀取的還是在相同的權限分頁, 或者還沒有觸碰到金絲雀標籤的那個記憶體位址,這個時候執行不會有問題

stack smashing detected: 當你指標存取到金絲雀的標籤的時候就會噴出這個錯誤,但還沒存取到沒有權限的分頁,這個是gcc噴的錯誤

segfault: 存取到了沒有權限的分頁,這個是kernel會噴的
```

> **批改**：**大致對**。三種的分界都對：位址還在可存取的記憶體 → 安靜出錯；改到金絲雀 → `stack smashing detected`；分頁沒有對映或權限不允許 → segfault（kernel 送 `SIGSEGV`）。兩處要修：
> - 金絲雀是被越界**寫入**改掉的，而且**函式返回前**才檢查，所以發現得比犯錯晚。只讀不寫的話，金絲雀不會被改到。
> - 噴錯的不是 gcc 本身：gcc 在編譯時**插入**檢查碼，錯誤是程式執行時由那段檢查碼（呼叫 glibc 的 `__stack_chk_fail`）報出來的。

#### 陣列 4-2. 為什麼「程式沒當掉」不能證明沒有越界？

> 過去的作答：[s1-03 quiz.md 4-2](../small-project/s1-03-arrays-pointers/quiz.md#4-2-為什麼程式沒當掉不能證明沒有越界)

```
程式執行的時候 指標讀取的還是在相同的權限分頁, 或者還沒有觸碰到金絲雀標籤的那個記憶體位址,這個時候執行不會有問題
kernel沒辦法抓到越界,gcc也沒辦法
```

> **批改**：**大致對**。「落在還能存取的記憶體時，kernel 和金絲雀都抓不到」對。缺了後果和根本原因：越界是**未定義行為**、C 不檢查邊界。這時程式會讀到垃圾、或寫壞別人的資料，照常結束（`oob.c` 的結束狀態是 0），錯誤可能很久以後才在別處出現。
> **陣列 4 記為大致對**（盒子 1 → 1）。
>
> **參考答案**【[第五節](../html/c/陣列、字串與指標運算-C不檢查邊界與用gdb找segfault.html#五c-不檢查邊界越界的三種下場)開頭的表格、〈下場一：安靜地出錯〉、〈下場二：被堆疊保護抓到〉】
>
> **核心關鍵**（答到這幾點就算對）：
>
> 1. 4-1：位址還在可存取的記憶體 → **安靜出錯**；越界**寫入**改掉金絲雀、函式返回前檢查 → **`stack smashing detected`**；分頁**沒有對映或權限不允許** → **segfault**。
> 2. 4-2：C 不檢查邊界（越界是未定義行為），落在還能存取的記憶體時沒有任何機制會報錯。
>
> **詳細說明**：金絲雀是 gcc 放在區域陣列後面的檢查值，返回前才檢查，所以發現得比犯錯晚；只讀不寫不會改到它。報錯的是 gcc 插入的檢查碼（呼叫 glibc 的 `__stack_chk_fail`），segfault 則是核心送出的 `SIGSEGV`。「沒當掉」的時候，程式可能讀到垃圾、寫壞別人的資料，照常結束（`oob.c` 結束狀態 0），錯誤很久以後才在別處出現。
