### 字元 5. 有人說「『字』是 3 個字元」，另一個人說「是 1 個字元」，誰對？`strlen("字")` 和 `mbstowcs(NULL, "字", 0)` 各會得到多少？如果程式忘了呼叫 `setlocale`，後者會得到什麼，那個數字是怎麼來的？

```

```

> **批改**：**不完整**（盒子 1 → 1）。第一問「看『字元』指哪一種，都對」**對**；`strlen` = 3 **對**。

## C資料：[C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號](../c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.md)

### C資料 9. 情境題：有人寫了 `if (len - used > 0)` 判斷「緩衝區還有沒有剩餘空間」，`len`、`used` 都是 `size_t`，用 `-Wall -Wextra` 編譯沒有任何警告。這個判斷在什麼情況下會出錯？為什麼 gcc 對 `len - used < 0` 會警告、對 `> 0` 卻不會？另外，為什麼 `int sum = x + y; if (sum < x)` 這種溢位檢查在 `-O2` 下可能完全失效？

> 盒子 1｜過去的作答：[s1-02 quiz.md 第 9 題](../small-project/s1-02-data-repr/quiz.md#9-情境題有人寫了-if-len---used--0-判斷緩衝區還有沒有剩餘空間lenused-都是-size_t用--wall--wextra-編譯沒有任何警告這個判斷在什麼情況下會出錯為什麼-gcc-對-len---used--0-會警告對--0-卻不會另外為什麼-int-sum--x--y-if-sum--x-這種溢位檢查在--o2-下可能完全失效)

```
len < used

因爲len 與 used都是無號,無號的相加減,在編譯器看還是無號, 而小於0 對編譯器纔是不合理的 無號不能小於0

因爲編譯器不能確定 x + y 最後是否能 大於 x, 因此他不會去檢查, -O2 會直接認爲sum < x一定是錯的
```

> **批改**：**不完整**（盒子 1 → 1）。
> - 第一問 `len < used` **對**，關鍵句要再補一句結果：相減**回繞成很大的正數**，判斷變成「還有空間」。
> - 第二問 **對**：無號數 `< 0` 永遠為假，所以 gcc 警告（`-Wtype-limits`）；`> 0` 等於 `!= 0`，是合法寫法。
> - 第三問 **錯**：漏了關鍵字「**未定義行為**」。不是「編譯器不能確定所以不檢查」，而是**有號溢位是 UB，gcc 假設它不會發生**；
>   在這個假設下 `x + y < x` 等價於 `y < 0`，檢查被改寫成「`y` 是不是負的」，不是「一定是錯的」。
>
> **參考答案**【筆記[第八節](../c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.md#八溢位無號回繞有號是未定義行為)〈另一種寫法：`x + y < x` 被改寫成 `y < 0`〉】：
> `len < used` 時 `len - used` 回繞成很大的正數，誤判有空間。無號 `< 0` 永遠為假，gcc 警告；`> 0` 結果不固定，不警告。
> 有號溢位是 UB，gcc 假設不發生，把 `sum < x` 改寫成 `y < 0`，真的溢位時檢查照樣不成立。溢位檢查要在運算**之前**做（例如 `y > 0 && x > INT_MAX - y`）。

```

exec 是他們已經把所有程式碼都編譯進去執行擋了,不會有interpreter
```

> **批改**：**錯**（盒子 1 → 1）。又是「因為動態連結所以是 DYN」——筆記在 9/29 複習後特地為這個誤會補了一小節。**`Type` 跟有沒有動態連結無關，只看是不是 PIE**：
> `-no-pie` 照樣動態連結、有 interpreter，`Type` 卻是 EXEC；`-static-pie` 是靜態連結，`Type` 卻是 DYN。
>
> **參考答案**【筆記[第三節](../c/ELF是什麼-可執行與可連結格式的兩種視角.md#三一種格式四種檔案)〈DYN／EXEC 跟「有沒有動態連結」無關：兩個反例〉】：本機 gcc 預設產生 **PIE**（Position-Independent Executable，位置無關執行檔），
> 每次執行被放在不同的隨機位址（ASLR），跟共享函式庫「可以放在任意位址」的性質相同，所以都是 DYN。`-static` 版是傳統的固定位址執行檔，所以是 EXEC。

### ELF 4. 區段（section）和載入段（segment）差在哪？為什麼核心載入時要把很多區段打包成少數幾個載入段？

> 盒子 1｜過去的作答：[s1-01 quiz.md 第 4 題](../small-project/s1-01-hello-compile/quiz.md#4-區段section和載入段segment差在哪為什麼核心載入時要把很多區段打包成少數幾個載入段)

```
section是告訴ld有哪些元件需要載入,
同時ld會去把它整理稱segment, 依據section寫的 每個元件的flag,相同的打包在一起

因爲核心與記憶體的運作模式就是以此爲記憶體分頁,所以是爲了配合核心的記憶體運作方式而做成這樣
```

> **批改**：**大致對**（盒子 1 → 1）。「`ld` 把旗標（權限）相同的區段打包成載入段」、「配合分頁」都對。兩處要講清楚：
> - 區段是給**誰**看的、載入段是給**誰**看的：區段是連結視角（`ld`、`nm`、`objdump`），載入段是執行視角（**核心與動態載入器**），描述哪一塊放進記憶體、權限是什麼。
> - 「以此為記憶體分頁」太含糊，關鍵句是：**記憶體權限最小只能以分頁（4096 byte）為單位設定**，同一頁不能一半可執行、一半可寫。
>
> **參考答案**【筆記[第四節](../c/ELF是什麼-可執行與可連結格式的兩種視角.md#四名字的關鍵兩種視角)】：區段切得細（`hello` 有 31 個），給連結相關工具用；載入段很少（4 個 `LOAD`），給核心與載入器用。
> 核心載入時只在乎權限，而權限以分頁為單位設定，所以 `ld` 把權限相同的區段排在一起、打包成一個載入段，核心用少數幾次映射、每塊設一種權限。
