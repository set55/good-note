### C資料 6. `printf("%p")` 印出 `0x7ffe50b23624`，只有 12 位十六進位。指標到底佔幾個 byte？印出來為什麼比較短？如果在 kernel 的錯誤訊息裡看到 `0xffff888102a4c000`，從位址的長相你能判斷什麼？

> 盒子 1｜過去的作答：[s1-02 quiz.md 第 6 題](../small-project/s1-02-data-repr/quiz.md#6-printfp-印出-0x7ffe50b23624只有-12-位十六進位指標到底佔幾個-byte印出來為什麼比較短如果在-kernel-的錯誤訊息裡看到-0xffff888102a4c000從位址的長相你能判斷什麼)、[10-07 複習](./2026-10-07-GNU-C資料-hello-objdump-字元.md)、[10-11 複習](./2026-10-11-字元-C資料-objdump-GNU-陣列.md)

```
8byte

前面4位都是0的話會省略掉

這是kernel的記憶體位址
```

> **批改**：**大致對**（盒子 1 → 1）。8 byte 對；kernel 位址對，而且這次把 `0xffff888102a4c000` 當成**一整個**位址（10-11 拆成兩段、說成 `signed long`，這次改正了）。缺的是兩個「為什麼」：
> - 上面 4 位十六進位為什麼一定是 0：x86-64 的虛擬位址只用 **48 bit**，使用者空間的位址上面 16 bit 一定全是 0；`%p` 不補前導零，所以只印 12 位。
> - 為什麼看得出是 kernel：上面 16 bit **全是 1**，代表它在位址空間的核心那一半。
>
> **參考答案**【[第二節](../html/c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.html#二指標就是位址)〈位址看起來只有 6 byte？——`%p` 不補零，而且最上面 2 byte 一定是 0〉】
>
> 核心關鍵：
> 1. 指標佔 8 byte。
> 2. x86-64 虛擬位址只用 48 bit，使用者空間的位址上面 2 byte 一定是 `00 00`，`%p` 不補前導零，所以只印出 12 位。
> 3. `0xffff888102a4c000` 整個是一個位址；上面 16 bit 全是 1，表示它在位址空間的核心那一半，所以是 kernel 的位址。
>
> 詳細說明：canonical address 規定上面 16 bit 必須跟第 47 bit 相同，所以合法的位址只有兩段：`0x0000000000000000`～`0x00007fffffffffff`（使用者空間）與 `0xffff800000000000`～`0xffffffffffffffff`（核心），中間那一大段不合法。形式上像把第 47 bit 往上複製，但這是 CPU 對位址格式的規定，跟 C 的有號、無號型別無關。

> 盒子 1｜過去的作答：[s1-02 quiz.md 第 9 題](../small-project/s1-02-data-repr/quiz.md#9-情境題有人寫了-if-len---used--0-判斷緩衝區還有沒有剩餘空間lenused-都是-size_t用--wall--wextra-編譯沒有任何警告這個判斷在什麼情況下會出錯為什麼-gcc-對-len---used--0-會警告對--0-卻不會另外為什麼-int-sum--x--y-if-sum--x-這種溢位檢查在--o2-下可能完全失效)、[10-04 複習](./2026-10-04-字元-C資料-objdump-hello-ELF.md)、[10-08 複習](./2026-10-08-字元-C資料-objdump-hello-ELF-陣列.md)、[10-11 複習](./2026-10-11-字元-C資料-objdump-GNU-陣列.md)

```
當len - used >= 0, 都不會有問題, 但是小於0 會超出size_t也就是unsigned long 的範圍, 溢位然後會發現len-used只能>= 0,他的錯就是永遠判別不了還有沒有剩餘空間

因爲c認爲unsigned long 之間運算類型還是unsigned long不會小於0, unsigned long運算永遠大於等於0,所以<0會警告,>0不會

c 沒有定義溢位,所以用O2 sum一定大於x, 故if (sum <x)的判斷會永遠爲false 沒效果了
```

> **批改**：**不完整**（盒子 1 → 1）。
> - 第一問方向對（`len < used` 時回繞），但結論錯：回繞的結果是**很大的正數**，`> 0` 成立，程式誤以為「還有很多空間」。不是「永遠判別不了」——`len == used` 時結果是 0，`> 0` 為假，判斷正確；只有 `len < used` 會出錯。
> - 第二問只答了一半：`< 0` 永遠為假所以警告，對；但沒說 `> 0` 為什麼**不**警告——無號數的 `> 0` 等於 `!= 0`，結果不固定（是 0 就假、不是 0 就真），是合法寫法。
> - 第三問又寫成「永遠為 false」，跟 10-08、10-11 錯在同一處（第三次）。gcc 不是把它變成常數假，而是把 `x + y < x` **代數化簡成 `y < 0`**（不溢位時兩者等價）。真的溢位時 `y` 是正的，`y < 0` 為假，所以抓不到；但 `y` 是負數時這個判斷照樣會成立，不是「永遠」為假。
>
> **參考答案**【[第七節](../html/c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.html#七陷阱有號和無號混在一起比較)〈`-Wtype-limits` 只抓「永遠成立／永遠不成立」的比較〉、[第八節](../html/c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.html#八溢位無號回繞有號是未定義行為)〈另一種寫法：`x + y < x` 被改寫成 `y < 0`〉】
>
> 核心關鍵：
> 1. `len < used` 時，`len - used` 回繞成很大的正數，判斷誤以為「還有空間」。
> 2. 無號數 `< 0` 永遠為假，所以 gcc 警告；`> 0` 等於 `!= 0`，結果不固定，是合法寫法，所以不警告。
> 3. 有號溢位是 UB，gcc 假設它不會發生，把 `x + y < x` 改寫成 **`y < 0`**；真的溢位時（`y` 是正的），這個檢查抓不到。
>
> 詳細說明：警告來自 `-Wtype-limits`（`-Wextra` 會開啟）。記法：「`x + y < x`」在數學上（沒有溢位）跟「`y < 0`」完全等價，gcc 只是做了這個代數化簡，而這個化簡只在「不會溢位」時才成立。正確的溢位檢查要在運算**之前**，用不會溢位的式子判斷，例如 `y > 0 && x > INT_MAX - y`。

### C資料 10. `long a = -1; unsigned int b = 1;` 與 `int c = -1; unsigned long d = 1;`，`a < b` 和 `c < d` 各是真還是假？兩邊各被轉成什麼型別，依據的是哪一條規則？為什麼 gcc 只對其中一個發出 `-Wsign-compare` 警告？

**題目用到的程式**（把題目的兩組宣告寫成可以編譯的完整程式 `cmp.c`，`-Wall -Wextra` 編譯）：

```c
#include <stdio.h>

int main(void)
{
    long a = -1;
    unsigned int b = 1;

    int c = -1;
    unsigned long d = 1;

    printf("a < b: %d\n", a < b);
    printf("c < d: %d\n", c < d);
    return 0;
}
```

```sh
gcc -Wall -Wextra cmp.c -o cmp && ./cmp
```

> 盒子 2｜過去的作答：[s1-02 quiz.md 第 10 題](../small-project/s1-02-data-repr/quiz.md#10-long-a---1-unsigned-int-b--1-與-int-c---1-unsigned-long-d--1a--b-和-c--d-各是真還是假兩邊各被轉成什麼型別依據的是哪一條規則為什麼-gcc-只對其中一個發出--wsign-compare-警告)、[10-05 複習](./2026-10-05-gcc-陣列-GNU-C資料-字元.md)、[10-09 複習](./2026-10-09-陣列-gcc-GNU-C資料-interp-ELF.md)

```
a < b true 轉爲long
c < d false 轉爲unsigned long

因爲long等級大於int所以用long
同樣unsigned long 的等級也大於int, 故轉unsigned long

因爲c < d 是有號轉無號, c會從負值變成正值
```

> **批改**：**對**（盒子 2 → 3）。真假、轉成的型別都對；警告的理由這次直接寫出「有號轉無號、負值變正值」，就是核心關鍵 3（比 10-09 的「來源類型是 signed」清楚）。
> 小提醒（不扣分）：`a < b` 是 `long` 對 `unsigned int`，不是對 `int`；而且規則不只「等級比較高」，還要 `long` **裝得下所有 `unsigned int` 的值**——在 `long` 只有 4 byte 的 32 位元平台，`a < b` 會改成轉 `unsigned long`、變成假。
>
> **參考答案**【[第四節](../html/c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.html#四無號整數二進位與回繞)〈怎麼確定一個常數的型別？比較時以誰為準？〉】
>
> 核心關鍵：
> 1. `a < b` 為**真**：`long` 裝得下所有 `unsigned int` 的值 → 兩邊轉成 `long`，值不變，−1 < 1。
> 2. `c < d` 為**假**：無號那邊（`unsigned long`）的等級 ≥ 有號那邊（`int`）→ 兩邊轉成 `unsigned long`，−1 變成 18446744073709551615。
> 3. 只對 `c < d` 警告：只有它**把有號的值轉成無號**，負數的值會變；`a < b` 轉成 `long`，值不變。
>
> 詳細說明：要看的是**轉換的方向**，不是「`<` 兩邊有一邊是 signed」（`a < b` 的 `a` 也是 signed，卻沒有警告）。有號轉無號不是 UB：位元不變，換成無號的讀法（[第六節](../html/c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.html#六有號與無號之間的轉換位元不變換個讀法)）；UB 是有號溢位。

> 盒子 3｜過去的作答：[s1-02 quiz.md 第 8 題](../small-project/s1-02-data-repr/quiz.md#8-signed-char-c---1-unsigned-int-u--c-之後-u-是多少擴展時新補的高位是-0-還是-1由哪個型別決定如果把-c-改宣告成-unsigned-char-c--0xffu-又是多少)、[10-05 複習](./2026-10-05-gcc-陣列-GNU-C資料-字元.md)

```
u = 2^31 -1
是1, 由來源型別也就是char決定

u = 0x000000ff = 255 unsigned 擴展直接補0
```

> **批改**：**不完整**（盒子 3 → 1）。第二問（補 1、由來源型別 `signed char` 決定）和第三問（零擴展、255）都對，但第一問的**值算錯**：補 1 之後是 `0xffffffff`，32 個 bit 全是 1，以無號讀是 **2³² − 1 = 4294967295**。你寫的 2³¹ − 1 = 2147483647 是 `0x7fffffff`（`INT_MAX`），最高位是 0，跟你自己說的「補 1」矛盾。
> 記法：n 個 bit 全是 1 ＝ 2ⁿ − 1。`unsigned int` 是 32 bit，所以是 2³² − 1；2³¹ − 1 是「有號 `int` 的最大值」，那時最高位要留給符號。
>
> **參考答案**【[第六節](../html/c/C的資料在記憶體裡長怎樣-位元組、指標、位元組順序與有號無號.html#六有號與無號之間的轉換位元不變換個讀法)】
>
> 核心關鍵：
> 1. `u` = **4294967295**（`0xffffffff`，2³² − 1）。
> 2. 擴展時補什麼由**原本的型別**決定：`signed char` 是有號的，做符號擴展，符號位是 1 就補 1；補完再以無號讀。
> 3. 改成 `unsigned char c = 0xff`：原本的型別無號 → 零擴展補 0 → `0x000000ff` = **255**。
>
> 詳細說明：順序是「先依來源型別擴展到 32 bit，再換成目標型別的讀法」。目標型別 `unsigned int` 是無號的，並不會讓擴展改成補 0——同樣是 `-1`，來源 `signed char` 就補 1。`c` 在記憶體裡都是 `0xff`，兩個 `u` 不同完全是來源型別造成的。

>   NEEDED               libc.so.6
> $ ldd main

> 	libfoo.so => not found
> 	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x000077ec76a00000)
> 	/lib64/ld-linux-x86-64.so.2 (0x000077ec76d40000)

> 1. 用 `gcc -g -fsanitize=address`（ASan）重新編譯再重現，第一次越界讀寫時就停下報告。
>
> 詳細說明：順便檢查 `parse` 有沒有拿到 `buf` 的長度、有沒有檢查 `k`。ASan 的報告會寫出是讀還是寫、幾個 byte、哪一行、越過了哪個變數。限制：要重新編譯、沒執行到的程式路徑抓不到、程式會變慢，所以用在開發與測試。

**自我練習**（不批改）

```

### gcc 3. 在 `-O2` 下，`answer()` 連呼叫 `sum_to` 這件事都不見了，直接回傳 5050。編譯器做了哪兩件事才能做到？

**題目用到的程式**：`sumto.c`（檔案：[`sumto.c`](../small-project/s1-01-hello-compile/sumto.c)），
用 `gcc -O0 -S sumto.c` 與 `gcc -O2 -S sumto.c` 產生組合語言（`-S`：只編譯到組合語言 `.s` 就停）。

```c
#include <stdio.h>

int sum_to(int n)
{
    int total = 0;
    for (int i = 1; i <= n; i++)
        total += i;
    return total;
}

int answer(void)
{
    return sum_to(100);
}

int main(void)
{
	printf("answer:%d\n", answer());
	return 0;
}
```

`-O0` 與 `-O2` 的 `answer`（本機 gcc 13.3 實際輸出，刪掉組譯指示）：

```asm
# -O0
answer:
	endbr64
	pushq	%rbp
	movq	%rsp, %rbp
	movl	$100, %edi         # 第一個參數 = 100
	call	sum_to             # 呼叫 sum_to
	popq	%rbp
	ret                        # 回傳值就是 sum_to 留在 %eax 的結果

# -O2
answer:
	endbr64
	movl	$5050, %eax        # 回傳值直接設成 5050
	ret
```

> 盒子 2｜過去的作答：[s1-01 quiz.md 第 3 題](../small-project/s1-01-hello-compile/quiz.md#3--o2-下-answer-直接變成-movl-5050-eax編譯器做了哪兩件事才能做到)、[10-05 複習](./2026-10-05-gcc-陣列-GNU-C資料-字元.md)、[10-09 複習](./2026-10-09-陣列-gcc-GNU-C資料-interp-ELF.md)

```
第一件事,他把代码内嵌,
然后把符号扩展,直接算出来
```

> **批改**：**大致對**（盒子 2 → 2）。第一件事「內嵌」對；第二件事「直接算出來」意思對，但**名字錯成「符號擴展」**。符號擴展（sign extension）是把有號數加寬時高位補符號位（C資料 8 那題），跟這裡無關。正確的名字是**常數摺疊**（constant folding）：內嵌後 `n` 變成常數 100，所有數字在**編譯時**都已知，編譯器在編譯時就把迴圈算完、得到 5050。
>
> **參考答案**【[第二節](../html/c/gcc最佳化等級-O0到O3差在哪.html#二實驗同一段程式不同等級編出什麼)〈「內嵌」是什麼〉】
>
> 核心關鍵：
> 1. **內嵌（inline）**：把 `sum_to` 的函式本體整段複製進 `answer()`，取代「呼叫」，參數 `n` 換成常數 100。
> 2. **常數摺疊（constant folding）**：內嵌後所有數字在編譯時都已知，編譯器在**編譯時**就把迴圈算完，得到 5050。
>
> 詳細說明：兩步缺一不可。單看 `sum_to(int n)`，`n` 要到執行時才知道，沒辦法事先算；是內嵌把 100 帶進來，才算得出來。給別人呼叫的那份 `sum_to` 仍然保留迴圈。

**自我練習**（不批改）

```
1. 首先把sumto 內嵌到answer, 所以在編譯階段就已經知道全部代碼,而參數也知道是100,換常數摺疊,編譯時就直接把他算完
```

### gcc 4. 「最佳化等級越高，程式越小」對嗎？`-O2`／`-O3` 和 `-Os`／`-Oz` 的目標各是什麼？為什麼追求速度反而可能讓程式變大？

（2026-10-09 改寫的題目：原題「用本篇的數字說明」要求背數字，闔上筆記作答時無從引用。不用寫出確切的 byte 數。）

**題目用到的程式**：同上一題 gcc 3 的 `sumto.c`。同一份 `sumto.c` 用不同的最佳化等級各編成 `.o`，比 `.text` 區段（放機器碼的區段）的大小，例如：

```sh
gcc -O2 -c sumto.c -o sumto_O2.o   # -c：編譯成目的檔就停，不連結
size -A sumto_O2.o                 # -A：逐個區段列出大小，看 .text 那一列
```

> 盒子 2｜過去的作答：[s1-01 quiz.md 第 4 題](../small-project/s1-01-hello-compile/quiz.md#4-最佳化等級越高程式越小對嗎用本篇的數字說明)、[10-05 複習](./2026-10-05-gcc-陣列-GNU-C資料-字元.md)、[10-09 複習](./2026-10-09-陣列-gcc-GNU-C資料-interp-ELF.md)

```
部队, 假如是提高速度的最佳化,代码可能变多,

2是多写回圈提升速度
3则是用更多的回圈去提升速度

0s
0z都是牺牲速度换取空间

可能是有些东西可以直接记下,少了需要计算的时间
```

> **批改**：**大致對**（盒子 2 → 2）。「不對」、`-O2`／`-O3` 求速度、`-Os`／`-Oz` 犧牲速度換空間都對（是字母 `-Os`，不是數字 `0s`）。第三問沒答到：
> - 「多寫迴圈」「更多的迴圈」說反了。迴圈展開（loop unrolling）是把迴圈本體**複製好幾份**、一圈做好幾次的工作，圈數變**少**、指令變**多**——少做幾次「`i <= n` 判斷＋跳回去」，換來更長的程式碼。
> - 「直接記下、少了計算」比較像 `answer()` 直接回傳 5050（常數摺疊），那反而讓程式變小，不是變大的原因。變大的原因是：展開迴圈、向量化（一條指令處理好幾個數）、內嵌（把函式本體複製到每個呼叫處），都是**用更多指令換更少的判斷與呼叫**，空間換時間。
>
> **參考答案**【[第二節](../html/c/gcc最佳化等級-O0到O3差在哪.html#二實驗同一段程式不同等級編出什麼)〈大小（`.text` 區段，`size -A` 實測）〉、〈`-O2`：答案在編譯時就算好了〉】
>
> 核心關鍵：
> 1. 不對：`-O2`／`-O3` 編出來的程式可能比 `-O0` 還大。
> 2. `-O2`／`-O3` 的目標是**速度**；`-Os`／`-Oz` 的目標才是**大小**。決定大小的是最佳化的目標，不是等級的數字。
> 3. 為了跑得快，編譯器會改寫迴圈（展開、一次處理好幾個元素、向量化）、內嵌函式，用更多指令換來更少的迴圈判斷與呼叫，也就是用空間換時間。
>
> 詳細說明：本機 `sumto.c` 的 `.text` 大小：`-Oz` 30、`-Os` 35、`-O0` 70、`-O2` 90、`-O3` 234 byte。`-O2` 版的 `sum_to` 一圈加兩個數，進迴圈前還要先處理奇偶，所以比 `-O0` 長。

**自我練習**（不批改）

```
不對,一般來說假如是提高速度的最佳化,迴圈展開程式碼變多,檔案反而變大

-O2,O3 是以空間換取時間, -Os,-Oz是以時間換取空間

因爲把迴圈直接展開, 內嵌函式,向量化雖然程式碼增加,但這意味着迴圈的判斷減少,減少cpu的計算時間
```
